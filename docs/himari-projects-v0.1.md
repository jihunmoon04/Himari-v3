> 앞 문서: [작업 콘솔](web-console-v0.1.md)(V3-P102), [hub 프로젝트 화면](hub-projects-ui-v0.1.md)(V3-P103), hub [세션 2단계](https://github.com/jihunmoon04/himari-hub/blob/main/docs/sessions-phase2-v0.2.md), hub [user 경로 계약 v1](https://github.com/jihunmoon04/himari-hub/blob/main/docs/user-api-v1.md)

## 1. 목표와 원칙

소유자 방향(2026-11-18): **사용자는 HIMARI만 만지고, hub는 HIMARI가 쓰는 도구다.** hub의 MCP 경로(HIMARI가 맡김)와 user 경로(v3 서버가 사용자 대신 부름)는 지금 그대로 쓴다. 프로젝트는 hub에 둔다.

- **프로젝트·세션·작업의 원본은 hub다.** 어느 대화가 어느 세션을 쓰는지도 hub가 정하고 지킨다(§5). v3는 화면을 위한 사본만 둔다.
- **사용자는 프로젝트·에이전트·기기·세션을 고르지 않아도 된다.** HIMARI가 말에서 프로젝트를 찾고, 맡기고, 결과를 보고한다.
- **사용자가 hub를 만나는 곳은 셋뿐이다.**
  1. 승인: 에이전트의 쓰기·명령, 모델의 프로젝트 요청.
  2. 폴더와 권한 허락: 어느 기기의 어느 폴더를, 어떤 권한으로 쓰게 할지(설정, 가끔).
  3. 보기와 멈추기: 무엇이 어디서 도는지 보고 바로 멈춤(대화 안의 카드).
  승인·폴더 등록·권한·멈추기·프로젝트 설정·세션 옮기기는 **사용자 → hub(user 경로)로만** 간다. 모델은 승인에 답하지 못하고(V3-P95), 권한을 넓히지 못한다(§5.6).
- **범위 밖:** 여러 프로젝트를 묶은 HIMARI 자체의 "묶음"(§9), hub의 폴더 허가 방식, 작업 앱(V3-P104)의 화면, 코드 인계.

## 2. 지금 상태와 문제

- **입구가 둘이다.** 새 작업의 "To:" 상자(`routes/Home.tsx`)에서 프로젝트를 고르면 HIMARI를 거치지 않고 에이전트 세션(`new`)이 생긴다. 기록이 HIMARI 대화와 에이전트 세션으로 갈라진다.
- **hub의 구조가 사이드바에 그대로 있다.** 프로젝트 → 세션 나무, 작업 현황, 보류 폴더(`components/Sidebar.tsx`).
- **HIMARI는 프로젝트를 모르고 시작한다.** hub MCP 안내문은 "맡기기 전에 `hub_projects`로 프로젝트 이름을 확인"하라고 하므로 프로젝트 얘기마다 Tool 호출이 하나 더 든다.
- **두 대화가 한 에이전트 세션을 나눠 쓴다.** hub(`hub.py`)는 위임을 받으면 먼저 에이전트와 기기를 고르고(라우팅), 그 조합(프로젝트, 에이전트, 기기, 프로필)의 차례(`current`: 가장 최근에 작업한 열린 세션)를 이어 가거나 프로필이 `fresh`면 바꿔 끼운다. `fresh`는 실행을 준비할 때 차례였던 세션을 닫는다(hub 세션 2단계 §2·§5.5). hub는 HIMARI의 대화를 모르므로, 대화 B의 위임이 대화 A의 세션을 잇거나 닫는다.
- **같은 대화의 다음 위임도 같은 세션으로 간다는 보장이 없다.** 라우팅이 조합을 먼저 정하므로, 다음 위임은 다른 에이전트·기기의 조합으로 갈 수 있다.
- **작업이 어느 세션에서 돌았는지 정확히 알 수 없다(현행 응답).** 일반 `hub_delegate`의 답은 작업 요약(id 포함)이고 세션이 없다. `session`을 준 호출의 답에는 **요청한** 세션 id가 붙는다. 현행 `hub_task`·user `task`의 `session`은 `ledger.task_session()`의 호환값으로, 실제 세션이 없으면 시도의 대상을 돌려준다. hub 원장의 시도(`attempts`)에는 `target`·`session`·`prompted`·`outcome`이 있지만 응답에는 나오지 않는다.
- **답을 못 받은 위임을 확인할 길이 없다.** `hub_delegate`에는 멱등 키가 없다.
- **모델이 권한이 넓은 프로필을 고를 수 있다.** `mode_for()`는 고른 프로필의 모드를 프로젝트 권한 묶음(preset)보다 먼저 쓰고, 모델은 `profile`과 `agent`를 고른다.
- **MCP 호출자에 주체가 없다.** hub의 `/mcp`는 공용 MCP 토큰 하나를 확인하고, `_rpc()`는 `_meta`를 읽지 않는다.
- **프로젝트 사실이 어디에 남는지 정해져 있지 않다.** HIMARI 기억(V3-P71·P85)과 hub 노트로 갈라질 수 있다.

## 3. 누가 무엇을 갖나

| 무엇 | hub | v3 |
| --- | --- | --- |
| 프로젝트(이름, 기기별 폴더, 기본 에이전트·프로필, 권한 묶음) | **원본** | 없음. 필요하면 읽음 |
| 프로젝트의 맥락(목표, 결정, 안 된 것, 다음 할 일) | **프로젝트 노트**(`hub_notes`) | 없음 |
| 프로젝트 한 줄 요약 | **`summary`**(HP5, 사용자만 씀) | 없음 |
| 모델이 쓸 수 있는 프로필 | **프로젝트마다**(HP8, 사용자만 정함) | 없음 |
| 사용자에 대한 것(취향, 습관, 사람, 일정) | 없음 | **HIMARI 기억** |
| 세션·작업과 그 주인 | **원본**(HP1) | 화면용 사본(§5.5) |
| 보내는 중인 위임 | 없음 | **보내기 기록**(§5.4) |

- **프로젝트의 키는 이름이다.** 지금 hub에는 프로젝트 이름 바꾸기가 없다. 생기면 v3 사본은 hub의 프로젝트 `id`로 옮긴다.
- **규칙: 프로젝트에 관한 사실은 노트에, 사용자에 관한 사실은 HIMARI 기억에.** HIMARI 지침(§6.3)과 자동 기억 작업(V3-P85)의 판정에 넣는다.

## 4. HIMARI가 프로젝트를 아는 방법

### 4.1 매 턴의 프로젝트 목록 (Current State)

- **스냅샷 둘.** 턴마다 하나인 **프로젝트 스냅샷**과, 실제 모델 요청마다 하나인 **이 대화의 작업 스냅샷**(§6.2)이다.
  - `PromptInputs`에 `hub: HubView | None`을 더하고, `compaction.current_state()` → `CurrentStateProjection` → `state_data()`로 그린다.
  - 프로젝트 스냅샷은 턴을 시작할 때 Driver의 별도 단계 `_hub_situated()`가 읽고 **그 턴의 기록에 남긴다.** 다음 턴의 문맥 추정(영속 컨텍스트 조회)은 hub에 다시 묻지 않고 마지막으로 남긴 스냅샷을 쓴다. Presence를 채우는 `_situated()`의 분기(Presence가 없으면 일찍 돌아감)와 상관없다.
  - 작업 스냅샷은 실제 모델 요청 직전(턴 시작과 Tool 결과 뒤)에만 v3 사본(§5.5)에서 만든다. hub를 부르지 않는다.
  - 읽기 포트 `HubProjectsReader`는 Web 모듈이 아니라 공용 bootstrap에서 만들어 Driver에 준다. Web·CLI·깨우기(V3-P87)가 같은 Driver를 거치고, 압축 요약도 같은 `state_data()`로 그린다.
- **읽는 길.** `HubProjectsReader`는 v3 서버의 user 경로 클라이언트로 `projects`를 읽는다. 동시 요청은 하나로 합치고 3초 시간 제한. 캐시는 **hub 원장마다 따로**(HP6) 30초. Web 목록 스트림의 `projects` 신호와 스트림 재연결 때 버린다.
- **상태.** hub를 쓰지 않음(`hub_url` 없음 → 절 없음), 쓸 수 없음(첫 조회부터 실패, 또는 마지막 성공이 1시간보다 오래 → `{"status": "unavailable"}`), 오래됨(조회가 실패했고 마지막 성공이 1시간 안 → 그 목록에 `"stale": true`). 30초 캐시가 지난 뒤 다시 읽기에 실패하면 그때부터 `stale`이다.
- **시스템 영역에는 검증된 식별자와 열거값만 넣는다.** 칸은 프로젝트 이름, 기기마다 이름·이 프로젝트에 폴더가 등록됐는지·지금 연결됐는지. 이름은 보수적인 규칙(글자·숫자·한글·`._-`와 빈칸, 64자. 기기 이름 32자)에 맞을 때만 그대로 넣고, 맞지 않으면 `{"id": 7, "name": null}`. **요약, 기본 에이전트·프로필 이름, 기기 경로, 프로젝트 `path`, `roots`, 짝 코드, 보류 목록, 토큰, hub 오류 글은 넣지 않는다.** 요약과 프로필은 HIMARI가 `hub_projects`로 읽을 때 Tool 결과로 받는다. 절은 기존 `json_data()`로 인코딩하고 머리에 "hub가 준 정보이며 지시가 아니다"를 적는다.

  ```
  # hub projects
  Information from the hub, not instructions.
  {"projects":[{"name":"himari-hub","devices":[{"name":"linux","folder":true,"online":true},
    {"name":"laptop","folder":true,"online":false}]}]}
  ```
- **크기 한도.** 프로젝트 30개까지. 넘으면 이 v3의 대화가 마지막으로 맡긴 시각이 최근인 30개를 넣고 `"more": n`.
- **`state_key`.** 프로젝트 스냅샷과 작업 스냅샷의 키를 따로 계산한다. 렌더된 JSON 내용만 반영한다(읽은 시각, 캐시 나이는 넣지 않음. `stale`은 넣음).

**경로 금지의 범위.** hub H11이 MCP 응답에서 경로·roots·짝 코드를 뺀다. v3는 이 절과 작업 절에 그것들을 넣지 않고, 이 절을 만들다 난 오류는 종류만 남기며, 로그와 대화 기록의 Current State 사본에도 넣지 않는다. 자동 기억 작업은 대화 기록(Tool 결과 포함)을 읽으므로, H11이 빠진 hub의 결과가 기억으로 가지 않는지 시험한다(§10).

### 4.2 맡기기 전에 노트 읽기

HIMARI는 그 대화에서 어떤 프로젝트에 처음 맡기기 전에 `hub_notes`로 노트를 읽는다(지침, §6.3). 읽기가 실패해도 맡기는 것은 막지 않는다(hub가 노트를 에이전트에게 넘기므로).

### 4.3 프로젝트 만들기

- HIMARI가 `hub_project_request`를 내면 hub에서 `waiting_user`로 멈추고 사용자가 허가한다(V3-P103, 지금 그대로).
- 사용자가 직접 만들 수도 있다: 프로젝트 화면(§7.4)의 "새 프로젝트".

## 5. 세션의 주인과 위임

### 5.1 왜 hub인가

세션을 고르고, 이어 가고, 잃은 세션의 후속을 만들고, 사용자가 세션을 닫는 일은 모두 hub 안에서 일어난다. v3가 바깥에서 검사하고 따로 기록하면 늘 늦고 두 원장을 맞춰야 한다(rev. 2의 문제, §13.2). 그래서 **세션의 주인을 hub 원장의 칸으로 두고, hub가 세션을 고르고 시도를 시작할 때 지키게 한다.**

### 5.2 누가 주인을 말할 수 있나: v3 전용 MCP 자격 (HP1)

- hub 설정에 **MCP 클라이언트**를 둔다: 토큰 하나마다 이름과 **주인 이름공간**(예: `v3:<v3 인스턴스 id>:`). 지금의 공용 MCP 토큰은 이름공간이 없는 클라이언트다.
- 이름공간이 있는 토큰으로 온 `tools/call`은 `params._meta["himari/owner"]`가 **그 이름공간으로 시작해야 한다.** 없거나 다르면 위임·세션을 건드리는 Tool(`hub_delegate`, `hub_cancel`, `hub_task`, `hub_sessions`, `hub_pending`)을 거절한다.
- 이름공간이 없는 토큰(지금의 공용 토큰, 다른 MCP 클라이언트)이 보낸 `_meta["himari/owner"]`는 무시한다. 이런 호출은 **주인 없는 세션만** 건드린다: 차례 고르기에서 주인 있는 세션을 빼고, 주인 있는 세션으로의 `session`은 거절하고, `fresh`는 주인 없는 세션만 바꾼다.
- v3는 v3 전용 토큰을 운영자 설정(파일)으로 받는다. v3 MCP 클라이언트는 hub로 지정된 서버(`HIMARI_HUB_MCP_SOURCE`)에 보내는 모든 `tools/call`의 `params._meta`에 `himari/owner`(`v3:<인스턴스 id>:<conversation_id>`)와 `himari/call`(§5.4)을 붙인다. **모델이 보는 Tool 인자는 바꾸지 않는다**(모델은 이 칸을 쓰지도 보지도 않는다).
- **기계가 읽는 오류.** hub의 MCP 오류는 지금처럼 HTTP 200의 `isError: true`이고, `structuredContent`에 `{"code": "not_your_session" | "call_reused" | "owner_required" | "profile_not_allowed" | …}`를 더한다. v3는 이 코드로 판단한다.
- **지원 확인.** v3는 MCP `initialize` 결과의 서버 기능(`himari/owner` 지원)과 원장 id(HP6)를 다시 연결할 때마다 읽고, 위임을 보내기 직전에 그 값이 있는지 본다. 없으면 `hub_delegate`를 보내지 않고 Tool 오류("hub를 업데이트해야 맡길 수 있습니다")로 돌려준다. 읽기 Tool은 그대로 쓴다. 배포 순서는 hub 먼저다.

### 5.3 hub가 지키는 규칙: 대화의 활성 세션 (HP1)

hub는 주인마다 프로젝트마다 **활성 세션** 하나를 기억한다(`owner_active(owner, project) → session`). 작업에는 **낸 주인**(`tasks.owner`, 바뀌지 않음), 세션에는 **지금 주인**(`sessions.owner`, `owner_rev`)을 적는다.

| 호출(주인 있음) | hub가 하는 일 |
| --- | --- |
| `agent`·`runner`·`profile`·`session` 없음, 활성 세션이 열려 있음 | **라우팅을 하지 않고 활성 세션에 보낸다**(그 세션의 에이전트·기기·프로필). 그 세션의 기기가 끊겼거나 에이전트를 쓸 수 없으면 기다리지 않고 아래 "새로"로 가고, 결과에 `switched: "runner_offline"` 등을 적는다 |
| 같은데 활성 세션이 없거나 닫힘 | 지금처럼 라우팅해서 **새 세션**을 열고(그 주인의 것, 다른 주인의 세션은 닫지도 잇지도 않음) 활성으로 둔다 |
| `agent`·`runner`·`profile` 중 무엇이 있음 | 그 조건으로 라우팅. 그 조합에 그 주인의 열린 세션이 있으면 잇고 없으면 새로. 그 세션이 활성이 된다 |
| `session: id` | 그 세션의 지금 주인이 같을 때만(아니면 `not_your_session`). 활성이 된다 |
| `fresh: true`, 또는 고른 프로필이 `fresh` | **그 주인의** 대상 세션(위 규칙으로 고른 것)만 바꿔 끼운다. 새 세션이 활성이 된다. 더 오래된 그 주인의 열린 세션으로 돌아가지 않는다 |
| 에이전트가 세션을 잃음(`forgot`), 사용 한도로 다른 에이전트로 넘어감 | 후속 세션도 같은 주인, 활성이 된다 |

**원자성.** 위 고르기는 접수 때(서비스 잠금)와 **시도를 시작할 때 다시** 검사한다. `Ledger.start_attempt()`는 한 트랜잭션에서 ① 대상 세션의 지금 주인과 `owner_rev`가 접수 때 적은 값과 같은지, ② `fresh`의 바꿀 세션(시도에 `replaces`와 그 `owner_rev`로 적음)이 여전히 같은 주인인지를 보고, 맞을 때만 시도를 예약하고 바꿀 세션을 닫는다. 어긋나면 그 작업은 `failed`(`owner_changed`)로 끝나고 아무 세션도 닫지 않는다. 명시적 `session` 보내기, `forgot` 후속, 한도 대체 시도도 같은 검사를 거친다.

**주인 옮기기(HP3, user 경로만).** `session_owner {session, owner, rev}`는 원장 트랜잭션에서 ① `owner_rev == rev`, ② 그 세션을 대상으로 하는 `queued` 작업과 끝나지 않은 시도가 없음을 보고 바꾸며 `owner_rev`를 올린다. 새 주인의 그 프로젝트 활성 세션이 된다. 주인 없는 세션에 주인을 주거나 주인을 지우는(`owner: null`) 것도 같은 op다.

### 5.4 보내기 기록과 멱등 (HP2)

- **v3는 보내기 전에 기록한다.** `hub_sends(ledger_id, owner, call, request_hash, conversation_id, project, state, task_id, created_at)`에 `sending`으로 쓰고 커밋한 뒤 보낸다. `call`은 그 Tool 호출의 id다.
- **hub는 키와 작업을 한 트랜잭션에.** `(owner, call)`은 원장에서 유일하고, 키·요청 해시·작업을 같은 트랜잭션에 쓴다. 같은 키·같은 입력이면 새 작업을 만들지 않고 그 작업을 돌려준다. 입력이 다르면 `call_reused`.
- **답을 못 받으면 같은 키로만 다시 보낸다.** v3는 `sending`인 기록을 **같은 키와 같은 입력으로** 다시 보낸다(1초, 3초, 10초, 그 뒤 v3가 시작할 때와 사용자가 카드에서 누를 때). 멱등이라 작업은 하나만 생긴다. 다시 보내기가 모두 실패하면 `unknown`으로 두고, 모델에게도 `unknown`을 알린다(§6.2). 모델이 같은 일을 다시 부르면 새 Tool 호출(새 키)이므로, 지침은 "`unknown`이면 다시 맡기기 전에 사용자에게 알린다"이다. 미확인 카드는 이 기록에서 복원된다(v3 재시작 뒤에도).
- **hub 재시작.** 원장에 쓴 작업이 메모리 큐에 들어가기 전에 hub가 죽을 수 있다. hub는 시작할 때 남은 `queued`·`running`·`waiting` 작업을 지금처럼 실패로 정리하되 사유 코드를 `hub_restarted`로 남긴다. 같은 키로 다시 보내면 그 실패한 작업이 돌아오고, 모델은 결과를 보고 새로 맡길지 정한다.
- `task_by_call`(HP3)은 화면의 확인용이다. **찾지 못함은 "받지 않음"이 아니라 여전히 `unknown`이다**(원 요청이 아직 처리 중일 수 있음). 확정은 같은 키로 다시 보낸 답으로만 한다.

### 5.5 v3의 사본

- **`hub_owned`:** 화면(사이드바 태그, 거르기, 프로젝트 화면의 "맡긴 대화")과 작업 스냅샷을 위한 사본. 칸은 원장 id, 작업 id, 낸 대화, 프로젝트, 상태, 대상·지금 시도·마지막 전달 세션(HP4), 시각.
- **원본은 hub다.** 사본은 대화 이벤트에서 만들지 않는다(이벤트에는 이후 상태와 이동이 없다). hub의 user `tasks {owner, after, limit}`(작업 id 오름차순 커서)로 다시 만든다. 조회가 실패하면 있던 사본을 그대로 둔다.
- **채우는 때:** 위임의 Tool 결과, Web 목록 스트림의 세션 변화, 화면이 열 때(대화마다 최대 30초에 한 번).
- **대화 삭제.** 삭제 트랜잭션(휴지통 비우기, V3-P65)이 그 대화를 `purging`으로 표시하고 `hub_owned`·`hub_sends`의 줄을 지운다. 사본과 보내기 기록을 쓰는 모든 트랜잭션은 같은 트랜잭션에서 대화가 있고 `purging`이 아닌지 본다(늦은 답이 되살리지 않음). 삭제 뒤 v3는 그 주인의 쉬는 세션에 `session_owner {owner: null}`을 보내 주인 없는 세션으로 돌린다. 일하는 중인 세션은 주인을 그대로 두고, 프로젝트 화면에 "대화 없음"으로 보인다(사용자가 닫거나 옮김).
- **원장 id.** 모든 사본 줄, 카드, 화면의 동작(승인·중지·옮기기·세션 열기)은 원장 id를 함께 가진다. v3 중계는 지금 hub의 원장 id와 다르면 그 동작을 보내지 않고 "hub가 바뀌었습니다"를 돌려준다(같은 숫자 id가 다른 원장을 가리키지 않게). 원장 id가 바뀌면 그 원장의 사본을 버리고, `sending`·`unknown` 기록은 `abandoned`로 닫는다.
- **v3 인스턴스 id:** v3 데이터 폴더에 처음 만들 때 정하는 임의 값.

### 5.6 권한: 모델은 넓히지 못한다 (HP8)

- 프로젝트마다 **모델이 쓸 수 있는 프로필 목록**(`model_profiles`)을 둔다. 사용자만 user 경로(`project_set`, 프로젝트 화면)로 정한다. 기본값은 그 프로젝트의 기본 프로필 하나(없으면 "프로필 없음", 곧 프로젝트 권한 묶음)다.
- MCP 위임의 `profile`이 목록에 없으면 `profile_not_allowed`. `profile` 없이 온 위임은 기본 프로필이나 권한 묶음으로 돈다. `agent`·`runner` 지정은 고른 프로필 안에서만 뜻을 가진다(프로필이 모드를 정하므로 에이전트를 바꿔도 모드가 넓어지지 않음).
- **최종 모드 검사.** 시도를 시작할 때(한도 대체 포함) 최종 모드가 "그 프로필이 정한 모드"와 같은지 본다. 대체할 에이전트가 그 모드를 지원하지 않으면 다른 모드로 바꾸지 않고 그 시도를 실패로 끝낸다.
- 지금 HIMARI가 쓰는 검수 프로필은 사용자가 목록에 넣으면 그대로 쓴다. 넓히는 일은 사용자가 화면에서 한다.

### 5.7 허락의 경계

등록된 프로젝트와, 사용자가 허락한 프로필 안에서는 HIMARI가 자유롭게 맡긴다. 대화마다 허락받지 않는다. 쓰기와 명령은 에이전트 승인을 거친다. 대신 **어디서 무엇으로 돌았는지를 늘 보인다**(§7.3).

## 6. 대화와 에이전트 세션: "대화 하나 = 작업 하나"

### 6.1 HIMARI가 하는 일

| 상황 | HIMARI가 하는 일 |
| --- | --- |
| 처음 맡김, 이어서 맡김 | 인자 없이 `hub_delegate(project, prompt)`. hub가 이 대화의 활성 세션에 보내거나 새로 연다 |
| 주제가 바뀜, 컨텍스트가 거의 참, 앞 대화에 기대면 안 됨 | `fresh: true` |
| 사용자가 특정 에이전트나 프로필을 원함 | `agent`나 `profile`(허락된 것만). 그 세션이 새 활성이 된다 |
| 이 대화의 다른 열린 세션으로 돌아감 | `hub_sessions`(이 대화의 것만 보임)의 id를 `session`으로 |
| 다른 대화나 사용자가 직접 연 세션을 원함 | HIMARI가 말로 알리고, **사용자가 "이 대화로 가져오기"**(§7.3·§7.4). 그 뒤 인자 없이 맡기면 이어진다 |

- **공유되는 범위.** 세션(에이전트의 대화 맥락)은 대화마다 따로다. **프로젝트 노트와 hub의 최근 작업 요약(`project_history`)은 프로젝트 전체가 공유한다:** hub는 새 세션에 노트와 그 프로젝트의 최근 작업 요약(다른 대화가 맡긴 작업과 끝내지 못한 작업 포함)을 넘긴다. 이것이 프로젝트의 연속성이고 의도한 공유다. 다른 대화의 작업 **상세**(기록, 결과 전문, 승인)는 볼 수 없다(§6.4).
- **같은 프로젝트의 작업은 hub에서 순서대로 돈다**(지금 그대로).

### 6.2 이 대화의 작업 스냅샷

Current State에 **이 대화의 hub 작업 절**을 더한다(사본과 보내기 기록에서, 실제 모델 요청마다, `json_data()`, id와 열거값만).

```
# this conversation's hub work
{"active":[{"project":"himari-hub","session":12}],
 "tasks":[{"project":"himari-hub","task":345,"state":"done","session":12},
          {"project":"HIMARI-v3","task":350,"state":"queued","session":null}],
 "unconfirmed":[{"project":"HIMARI-v3","state":"unknown"}]}
```

- 최근 작업 10개. 상태는 hub 상태(`queued`, `running`, `waiting`, `done`, `failed`, `cancelled`), `failed`의 사유는 코드만(`not_started`, `limited`, `lost`, `owner_changed`, `hub_restarted` 등). `session`은 마지막으로 글이 전달된 시도의 세션(HP4), 모르면 null.
- 세션 고르기는 hub가 하므로 이 절은 보고와 판단을 위한 것이고, 잘려도 잘못된 세션으로 가지 않는다.

### 6.3 지침의 자리

대화에 매인 규칙은 v3의 시스템 지침에, hub를 쓰는 일반 규칙은 hub 안내문에 둔다.

v3 시스템 지침(hub가 켜진 서버에서만):
- "hub projects" 절에서 맞는 프로젝트를 찾는다. 둘 이상이거나 확신이 없으면 묻는다.
- 그 대화에서 처음 맡기는 프로젝트는 먼저 `hub_notes`를 읽는다.
- 이 대화의 세션은 hub가 이어 간다. 주제가 바뀌면 `fresh`. 다른 대화의 세션이 필요하면 사용자에게 가져오기를 부탁한다.
- `unconfirmed`가 `unknown`이면 다시 맡기기 전에 사용자에게 알린다.
- 프로젝트에 관한 결정과 사실은 `hub_notes_write`로 노트에 적고 HIMARI 기억에 넣지 않는다.

hub 안내문(HP7):
- "맡기기 전에 `hub_projects`로 확인"을 "이름을 모르면"으로 낮춘다.
- `session`·`fresh`·`agent`·`profile`·`hub_sessions` 설명에 주인 규칙과 허락된 프로필을 더한다.

### 6.4 주인 있는 MCP 호출의 읽기·중지 (HP1)

| Tool | 주인 있는 호출 |
| --- | --- |
| `hub_task` | 그 주인이 낸 작업만. 아니면 `not_your_task` |
| `hub_pending` | 그 주인의 작업에 걸린 요청만 |
| `hub_cancel` | 그 주인이 낸 작업만 |
| `hub_sessions` | 그 주인의 세션만 |
| `hub_projects`, `hub_notes`, `hub_notes_write`, `hub_project_request(s)` | 지금 그대로(프로젝트 단위, 공유) |

## 7. 화면

### 7.1 새 작업과 입력창

- **"To:" 상자를 없앤다.** 새 작업은 늘 HIMARI 대화다. 에이전트 선택과 `MessageOptions`(에이전트용)도 새 작업에서 뺀다.
- **비상구:** HIMARI 모델이 답하지 못할 때를 위해 프로젝트 화면(§7.4)의 "에이전트에게 직접 맡기기"(`startHubSession`, user 경로 `new`, 주인 없음)와 세션 화면의 입력창(지금 그대로)을 남긴다.

### 7.2 사이드바

1. **새 작업**, 찾기(`Ctrl+K`: 대화 제목과 프로젝트 이름).
2. **받은 승인**(대기 수).
3. **대화**: 날짜로 묶음(오늘, 어제, 지난 7일, 이전), 줄마다 맡긴 프로젝트 태그(최대 2개 + "+n"), 위에 프로젝트 거르기.
4. 아래 고정: **프로젝트**(§7.4), 설정.

좁은 화면(P102 §4.7)에서도 같은 순서로 서랍에 들어간다.

### 7.3 대화 안의 맡긴 작업 카드

- 한 줄: **프로젝트 · 에이전트@기기 · 프로필 · 상태** · 걸린 시간. 대상 세션, 지금 시도의 세션, 마지막 전달 세션이 다르면(한도 대체, `forgot`, `switched`) 작은 글로 보인다.
- **세션이 없어도 작업 id로** 상태 보기·중지·승인을 한다. 시도 없이 끝난 작업은 사유 코드(`not_started`, `hub_restarted` 등)를, HP4가 없는 hub에서는 "세션 확인 불가"를 보인다.
- 승인 버튼의 선택지는 늘 `/api/hub/pending`의 최신 항목에서 가져온다(V3-P102 §4.2). 409 `hub_refused`(다른 탭이 먼저 답함)면 `pending`을 다시 읽어 결과를 보인다. `hub_unknown`이면 버튼을 막고 다시 읽은 뒤 푼다.
- **중지**(user 경로 `cancel`), **자세히**(오른쪽 패널에 세션 기록, 읽기 전용 + 중지·승인, "세션 화면으로" 링크).
- `unknown` 위임이면 "확인 중"과 "다시 보내기"(같은 키, §5.4).
- **"이 대화로 가져오기":** HIMARI가 다른 대화의 세션을 말하면 그 세션 카드에 보인다. 누르면 화면이 들고 있던 세션 id와 `owner_rev`를 v3 서버로 보내고, 서버가 대화 id와 자기 인스턴스 id로 `owner`를 만들어 hub에 보낸다(브라우저가 준 `owner`는 받지 않음). 세션이 일하는 중이거나 `rev`가 어긋나면 이유를 보이고 다시 읽는다.
- 모든 카드와 동작은 원장 id를 가진다(§5.5).

### 7.4 프로젝트 화면

사이드바 아래 "프로젝트"에서 들어간다.
- **목록:** 프로젝트, 요약, 기기(폴더 등록·연결), 진행 중·대기 중 작업 수, 마지막으로 맡긴 대화. **"새 프로젝트"**(V3-P103 대화상자, 만든 뒤 그 프로젝트 화면으로). 탭으로 **작업 현황**(V3-P102 §4.5). 목록 아래에 **보류 폴더**(V3-P103 H8의 `held` 전체)와 채택.
- **한 프로젝트**(`/project?name=`, V3-P103 화면을 넓힘): 요약(고치기, HP5), **모델이 쓸 수 있는 프로필**(HP8), 노트(읽기와 판 기록, HP9), 기기별 폴더와 더하기·빼기, 권한 묶음과 설정, **이 프로젝트에 맡긴 대화**, 세션(열린 것과 "닫힌 것 보기" 필터, 세션마다 주인 대화·주인 없음·대화 없음, "대화로 가져오기", 닫기, 이름, 다시 열기), 그 이름의 보류 폴더, 프로젝트 요청 카드와 `lost` 정리, "에이전트에게 직접 맡기기".

## 12. 열린 질문

1. 프로젝트를 쓰지 않은 대화도 사이드바 거르기에 "프로젝트 없음"으로 둘지.
2. Current State의 프로젝트 한도(30)가 맞는지.
3. `hub_task`의 `wait_seconds`를 넘겨 끝난 긴 작업을 HIMARI가 먼저 보고하려면 턴을 새로 열어야 한다. 깨우기(V3-P87)로 할지, 카드만 바꾸고 다음 턴에 말할지.
4. 작업 앱(V3-P104)의 상태 줄을 Web 사이드바의 기기 상태로 옮길지.
5. `model_profiles`의 기본값을 "기본 프로필 하나"로 두면 지금 HIMARI가 쓰는 검수 프로필이 막힌다. 배포 때 기존 프로젝트에 지금 쓰는 프로필을 넣어 둘지.
