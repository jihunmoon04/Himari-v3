## 1. 목표와 원칙

소유자 방향(2026-11-18): **사용자는 HIMARI만 만지고, hub는 HIMARI가 쓰는 도구다.** hub의 MCP 경로(HIMARI가 맡김)와 user 경로(v3 서버가 사용자 대신 부름)는 지금 그대로 쓴다. 프로젝트는 hub에 둔다.

- **프로젝트의 원본은 hub 하나다.** v3는 프로젝트를 복사하지 않고 이름으로 가리킨다.
- **사용자는 프로젝트·에이전트·기기·세션을 고르지 않아도 된다.** HIMARI가 말에서 프로젝트를 찾고, 맡기고, 결과를 보고한다.
- **사용자가 hub를 만나는 곳은 셋뿐이다.**
  1. 승인: 에이전트의 쓰기·명령, 모델의 프로젝트 요청.
  2. 폴더 허락: 어느 기기의 어느 폴더를 쓰게 할지(설정, 가끔).
  3. 보기와 멈추기: 무엇이 어디서 도는지 보고 바로 멈춤(대화 안의 카드).
  셋 모두 HIMARI 화면의 모양으로 보이지만, 승인과 멈추기는 **사용자 → hub(user 경로)로 바로** 간다. 모델은 지금처럼 승인에 답하지 못한다(V3-P95).
- **범위 밖:** 여러 프로젝트를 묶은 HIMARI 자체의 "묶음"(§9), hub의 허가 방식, 작업 앱(V3-P104)의 화면, 코드 인계.

## 2. 지금 상태와 문제

- **입구가 둘이다.** 새 작업의 "To:" 상자(`routes/Home.tsx`)에서 HIMARI를 고르면 HIMARI 대화, 프로젝트를 고르면 HIMARI를 거치지 않고 에이전트 세션(`new`)이 생긴다. 사용자가 보낼 때마다 경로를 정하고, 기록이 HIMARI 대화와 에이전트 세션으로 갈라진다.
- **hub의 구조가 사이드바에 그대로 있다.** 프로젝트 → 세션 나무, 작업 현황, 보류 폴더(`components/Sidebar.tsx`). 대화 목록 아래에 있어 대화가 많으면 보이지 않는다.
- **HIMARI는 프로젝트를 모르고 시작한다.** 매 턴의 문맥에 프로젝트가 없다. hub MCP 안내문(서버 안내 절)은 "맡기기 전에 `hub_projects`로 프로젝트 이름을 확인"하라고 하므로, 사용자가 프로젝트를 말할 때마다 Tool 호출이 하나 더 든다. 사용자가 이름을 정확히 말하지 않으면 HIMARI가 그 말이 프로젝트 얘기인지부터 알기 어렵다.
- **두 대화가 한 에이전트 세션을 나눠 쓴다.** `hub_delegate`는 `session`을 주지 않으면 조합(프로젝트, 에이전트, 기기, 프로필)의 차례(`current`: 가장 최근에 작업한 열린 세션)를 이어 간다. 그래서 HIMARI 대화 A와 B가 같은 프로젝트에 맡기면 A의 맥락이 B의 작업에 섞인다. `fresh`로 피하면 더 나쁘다: `fresh`는 **바꿔 끼우기**라 차례인 세션을 닫으므로(hub 세션 2단계 §2·§5.5), B의 `fresh`가 A의 세션을 닫고 A는 그 세션에 다시 보낼 수 없다. 조합에 세션을 하나 더 여는 `new`는 user 경로에만 있다(같은 문서 §5.6, "새 대화는 MCP에 넣지 않는다"). hub MCP 안내문도 "방향을 바꿔 다시 맡기면 같은 세션에서 이어진다"고 차례 규칙을 전제한다.
- **프로젝트 사실이 어디에 남는지 정해져 있지 않다.** HIMARI 기억(V3-P71·P85)에 "hub는 Python 3.12"가 들어가면 hub 프로젝트 노트와 둘로 갈라진다. 노트는 에이전트들도 받지만 HIMARI 기억은 HIMARI만 본다.

## 3. 누가 무엇을 갖나

| 무엇 | hub | v3 |
| --- | --- | --- |
| 프로젝트(이름, 기기별 폴더, 기본 에이전트·프로필) | **원본** | 없음. 필요하면 읽음 |
| 프로젝트의 맥락(목표, 결정, 안 된 것, 다음 할 일) | **프로젝트 노트**(`hub_notes`) | 없음 |
| 프로젝트 한 줄 요약 | **`summary`**(HP2, 사용자만 씀) | 없음 |
| 사용자에 대한 것(취향, 습관, 사람, 일정) | 없음 | **HIMARI 기억** |
| 에이전트 세션과 작업 | **원본** | 대화가 쓴 세션·작업의 id만 |
| 대화와 프로젝트의 연결 | 없음 | **대화–프로젝트 색인**(§5) |

- **프로젝트의 키는 이름이다.** hub의 `projects.name`은 유일하고, 지금 hub에는 프로젝트 이름 바꾸기가 없다. hub가 이름 바꾸기를 넣으면 v3 색인은 hub의 프로젝트 `id`로 옮긴다(§9).
- **규칙: 프로젝트에 관한 사실은 노트에, 사용자에 관한 사실은 HIMARI 기억에.** HIMARI 지침(§6.3)과 자동 기억 작업(V3-P85)의 판정에 넣는다.

## 4. HIMARI가 프로젝트를 아는 방법

### 4.1 매 턴의 프로젝트 목록 (Current State)

Driver가 턴을 시작할 때 Current State에 **hub 프로젝트 절**을 넣는다. 기기 절(`PresenceView`, V3-P83 §6.2)과 같은 방식으로 `CurrentStateProjection`에 `projects: HubProjectsView | None`을 더한다.

```
hub projects (as of 11:42):
- himari-hub — "에이전트 실행 hub (Python)" · linux ●, laptop ○ · default claude
- HIMARI-v3 — "HIMARI 서버와 Web" · linux ●
- test · linux ●
```

- **출처:** v3 서버가 user 경로 `projects`로 읽는다(V3-P102 중계가 이미 씀). 30초 동안 캐시하고, 목록 스트림의 `projects` 신호가 오면 버린다.
- **모델 뷰만 넣는다.** 이름, `summary`(HP2), 기기 이름과 연결 여부, 기본 에이전트. **기기 경로, 프로젝트 `path`, `roots`, 짝 코드, 보류 목록은 넣지 않는다**(hub H11과 같은 원칙: user 뷰에는 있지만 모델에게 가지 않는다). 칸마다 길이를 자른다(이름 64자, 요약 120자).
- **크기 한도:** 프로젝트 30개까지. 넘으면 최근 7일에 쓴 것 30개를 넣고 "그 밖 n개: `hub_projects`로 찾음" 한 줄을 붙인다.
- **hub가 답하지 않으면** "hub projects: not answering" 한 줄. 꺼져 있으면(`hub_url` 없음) 절을 넣지 않는다.
- **글은 데이터로 넣는다.** 이름과 요약은 따옴표 안에 넣고, 시스템 영역의 다른 절처럼 지시로 읽지 않는다고 적는다. 요약을 사용자만 쓰게 하는 것(HP2)도 이 때문이다: 노트 첫 줄은 에이전트가 고칠 수 있어서, 그것을 매 턴 시스템 영역에 넣으면 에이전트가 HIMARI에게 글을 심는 길이 된다.

### 4.2 맡기기 전에 노트 읽기

HIMARI는 **그 대화에서 어떤 프로젝트에 처음 맡기기 전에** `hub_notes`로 노트를 읽는다(지침, §6.3). 노트는 hub가 에이전트에게도 넘기므로, HIMARI가 읽는 목적은 프롬프트에 무엇을 더 담을지와 사용자에게 무엇을 물을지 정하는 것이다.

### 4.3 프로젝트 만들기

- 사용자가 "새 프로젝트 만들어줘"라고 하면 HIMARI가 `hub_project_request`를 낸다. 모델의 요청이므로 hub에서 `waiting_user`로 멈추고, 사용자가 대화 안의 카드나 받은 승인에서 허가한다(V3-P103, 지금 그대로).
- 사용자가 직접 만들 수도 있다: 프로젝트 화면(§7.4)의 "새 프로젝트"(user 경로, 사용자 요청은 자기 허가).

## 5. 대화와 프로젝트

**한 대화는 여러 프로젝트를 쓰고, 한 프로젝트는 여러 대화에서 쓰인다.** 사용자가 대화에 프로젝트를 미리 붙이지 않는다.

### 5.1 대화–프로젝트 색인

v3에 테이블 하나를 더한다. 원본은 대화의 이벤트이고, 이 테이블은 **이벤트에서 다시 만들 수 있는 색인**이다.

```
conversation_projects(
  conversation_id, project,         -- 키
  first_at, last_at,                -- 처음·마지막으로 맡긴 시각
  PRIMARY KEY (conversation_id, project))
conversation_sessions(
  conversation_id, project, session_id, agent, runner, profile,
  last_task_id, last_at,
  PRIMARY KEY (conversation_id, session_id))
```

- **기록하는 때:** hub로 지정된 MCP 서버(`HIMARI_HUB_MCP_SOURCE`)의 `hub_delegate` 호출이 작업 id를 돌려받았을 때 `conversation_projects`에 쓴다. 세션은 작업이 실제로 돈 세션이 알려진 때 쓴다: `hub_task` 결과의 `session`, 또는 v3 서버가 user 경로 `task`(H1)로 읽은 값. 턴을 시작할 때 이 대화에서 세션을 모르는 작업이 있으면 `task`로 읽어 채운다(최대 10개).
- `hub_notes`·`hub_sessions` 같은 읽기는 기록하지 않는다. `hub_project_request`(만들기)는 그 프로젝트가 생긴 뒤 첫 `hub_delegate` 때 기록된다.
- **다시 만들기:** 스키마 판이 오를 때와 운영자 명령(`himari reindex-projects`)으로, 대화 이벤트의 hub Tool 호출을 처음부터 읽어 다시 쓴다. 세션은 다시 만들 때 hub `task`로 읽고, 읽지 못하면 비워 둔다.
- 대화를 지우면(휴지통 비우기, V3-P65) 그 줄도 지운다.

### 5.2 허락의 경계는 hub 등록이다

등록된 프로젝트는 HIMARI가 자유롭게 맡긴다. 대화마다 프로젝트 연결을 허락받지 않는다.
- 쓰기와 명령은 어차피 에이전트 승인을 거친다(권한 묶음과 hub 승인).
- 폴더를 쓰게 하는 결정은 등록 때 사람이 이미 했다(hub 허가 방식, V3-P103).
- 대신 **어디서 돌았는지를 늘 보인다**(§7.3 카드). 잘못 짚었으면 사용자가 바로 보고 멈춘다.

## 6. 대화와 에이전트 세션: "대화 하나 = 작업 하나"

### 6.1 규칙

| 상황 | HIMARI가 하는 일 |
| --- | --- |
| 이 대화가 그 프로젝트에 처음 맡김 | **새 세션**(HP1 `new_session: true`). 다른 대화의 세션을 닫지 않는다 |
| 이 대화에서 이어서 맡김 | 이 대화의 그 세션을 **`session`으로 지정** |
| 이 대화의 세션의 컨텍스트가 거의 참, 또는 주제가 바뀜 | 새 세션(HP1). 이 대화의 이전 세션은 열린 채 둔다 |
| 사용자가 "어제 하던 거 이어서" | 색인과 `hub_sessions`로 그 세션을 찾아 `session`으로 지정. 못 찾거나 여럿이면 묻는다 |
| 검수처럼 앞 대화에 기대면 안 되는 일 | 지금처럼 `fresh` 프로필(바꿔 끼우기)을 쓴다 |

- **프로젝트의 연속성은 세션이 아니라 노트와 최근 작업 요약이 맡는다.** hub는 새 세션에 프로젝트 노트와 최근 작업 요약(`project_history`, 끝내지 못한 작업 포함)을 넘긴다. 그래서 새 대화가 새 세션에서 시작해도 프로젝트 맥락은 이어진다.
- 이 규칙에서 차례(`current`)는 HIMARI에게 거의 쓰이지 않는다. 사용자가 user 경로로 직접 연 세션은 지금처럼 차례 규칙을 따른다.
- **같은 프로젝트의 작업은 hub에서 순서대로 돈다**(지금 그대로). 두 대화가 같은 프로젝트에 맡기면 뒤의 것은 기다리고, 카드가 "대기 중"을 보인다.

### 6.2 모델에게 알리는 것

Current State에 **이 대화의 hub 작업 절**을 더한다(§5.1 색인에서, 이 대화만).

```
this conversation's hub work:
- himari-hub · claude@linux · session 12 · last task #345 done (11:30)
- HIMARI-v3 · codex@linux · session 15 · task #350 running
```

세션 줄은 열린 세션만, 최대 5줄. 닫히거나 잊힌 세션(`forgot`)은 "closed"로 한 번 보이고 다음 턴부터 뺀다.

### 6.3 지침의 자리

지금 hub를 쓰는 방법은 hub MCP 서버의 안내문(서버 안내 절, `mcp.py`의 `instructions`)이 HIMARI에게 알린다. hub는 HIMARI의 대화를 모르므로, **대화에 매인 규칙은 v3의 시스템 지침에, hub를 쓰는 일반 규칙은 hub 안내문에** 둔다. 문구는 구현 때 다듬는다.

v3 시스템 지침(hub가 켜진 서버에서만):
- 사용자가 프로젝트 이름을 말하지 않아도 "hub projects" 절에서 맞는 프로젝트를 찾는다. 둘 이상이 맞거나 확신이 없으면 묻는다. 절에 있는 이름은 `hub_projects`로 다시 확인하지 않아도 된다.
- 그 대화에서 처음 맡기는 프로젝트는 먼저 `hub_notes`를 읽는다.
- 세션은 §6.1의 표대로 고른다. 이 대화의 세션은 "this conversation's hub work" 절에 있다.
- 프로젝트에 관한 결정과 사실은 `hub_notes_write`로 노트에 적고 HIMARI 기억에 넣지 않는다.

hub 안내문(HP3):
- "방향을 바꿔 다시 맡기면 같은 세션에서 이어진다"를 "이어 갈 세션은 `session`으로 지정하고, 새 일은 `new_session`으로 연다. `fresh`는 앞 세션을 닫는다"로 바꾼다.
- "맡기기 전에 `hub_projects`로 프로젝트 이름을 확인"은 "이름을 모르면"으로 낮춘다(클라이언트가 목록을 이미 줄 수 있으므로).
- 끝난 뒤 결과를 전하는 규칙(지금 있음)은 그대로 둔다.

**강제하지 않는다.** v3의 MCP 클라이언트가 `hub_delegate` 인자를 고쳐 쓰지 않는다(모델이 보는 호출과 실제 호출이 달라짐). 지침과 Current State로 시작하고, 실제 모델 시험(§10)에서 규칙을 어기는 비율을 본다. 자주 어기면 hub 쪽 기본값(HP4, §9)을 검토한다.

## 7. 화면

### 7.1 새 작업과 입력창

- **"To:" 상자를 없앤다.** 새 작업은 늘 HIMARI 대화다. 에이전트 선택 상자와 `MessageOptions`(에이전트용)도 새 작업 화면에서 뺀다.
- **비상구:** HIMARI 모델이 답하지 못할 때(예: provider 결제 문제)를 위해 에이전트에게 직접 맡기는 길은 남긴다. 프로젝트 화면(§7.4)의 "에이전트에게 직접 맡기기"(지금의 `startHubSession`, user 경로 `new`)와 세션 화면의 입력창(지금 그대로)이다. 첫 화면에는 두지 않는다.

### 7.2 사이드바

위에서부터:
1. **새 작업**, 찾기(`Ctrl+K`: 대화 제목과 프로젝트 이름).
2. **받은 승인**(대기 수). 에이전트 승인과 프로젝트 요청을 함께(지금 그대로).
3. **대화**: 날짜로 묶음(오늘, 어제, 지난 7일, 이전). 줄마다 쓴 프로젝트를 작은 태그로(색인, 최대 2개 + "+n"). 위에 **프로젝트 거르기**(색인으로 그 프로젝트를 쓴 대화만).
4. 아래 고정: **프로젝트**(프로젝트 화면 목록, §7.4), 설정.

빠지는 것: 프로젝트 → 세션 나무, 사이드바의 작업 현황, 보류 폴더, 대화 아래에 들여 쓴 세션(V3-P102 §5.1). 모두 프로젝트 화면이나 대화 안의 카드로 간다.

### 7.3 대화 안의 맡긴 작업 카드

지금의 `DelegationCard`를 보강한다.
- 한 줄: **프로젝트 · 에이전트@기기 · 상태**(대기 중, 작업 중, 승인 기다림 n, 끝남, 실패) · 걸린 시간.
- 승인을 기다리면 카드 안에 승인 버튼(지금의 승인 카드와 같은 컴포넌트, user 경로).
- **중지**(user 경로 `cancel`).
- **자세히:** 페이지를 옮기지 않고 오른쪽 패널에 그 세션의 기록을 연다(세션 화면의 기록 컴포넌트, 읽기 전용 + 중지·승인). "세션 화면으로" 링크도 둔다.
- 대화 머리줄에 이 대화가 쓴 프로젝트 태그(색인).

### 7.4 프로젝트 화면

사이드바 아래의 "프로젝트"에서 들어간다. 사용자가 hub의 기반 구조를 보는 곳은 여기뿐이다.
- 목록: 프로젝트, 요약, 기기 연결, 진행 중·대기 중 작업 수, 마지막으로 다룬 대화. "새 프로젝트"(V3-P103 대화상자).
- 한 프로젝트(`/project?name=`, V3-P103 화면을 넓힘): 요약(고치기, HP2), 노트(읽기, 판 기록), 기기별 폴더와 더하기·빼기, 설정, **이 프로젝트를 다룬 대화**(색인), 열린 세션(지금의 사이드바 나무를 여기로), 보류 폴더, "에이전트에게 직접 맡기기".
- 작업 현황(V3-P102 §4.5)은 프로젝트 목록의 탭으로 옮긴다.

## 8. V3-P102에서 바뀌는 것

| V3-P102 | 바뀜 |
| --- | --- |
| §4.1 새 작업이 받는 쪽을 고름 | 늘 HIMARI. 직접 맡기기는 프로젝트 화면으로(§7.1) |
| §4.1 사이드바의 프로젝트 → 세션, 작업 현황 | 프로젝트 화면으로(§7.2, §7.4) |
| §4.3 새 작업 입력창의 에이전트·모델·모드 | 새 작업에서 뺌(세션 화면에는 남음) |
| §5.1 사이드바에서 대화 아래에 맡긴 세션 | 대화 머리줄의 프로젝트 태그와 카드의 "자세히"로 |

바뀌지 않는 것: 서버 중계(`/api/hub/…`)와 SSE, 세션 화면, 받은 승인, 승인 원칙, V3-P103의 요청 흐름.

## 9. hub에 필요한 것

| id | 무엇 | 왜 |
| --- | --- | --- |
| HP1 | `hub_delegate`에 `new_session`(bool): user 경로 `new`와 같이 조합에 세션을 하나 더 열고, 열린 세션을 닫지 않는다. `session`·`fresh`와 함께 줄 수 없다. 세션 고르기 우선순위는 세션 2단계 §3 그대로(보내기 → 새 대화 → `fresh` → 프로필 `fresh` → 차례) | 대화마다 세션을 따로 두려면 다른 대화의 세션을 닫지 않고 새 세션을 열어야 함(§2, §6.1). 지금 MCP에는 바꿔 끼우는 `fresh`뿐 |
| HP2 | 프로젝트에 `summary`(한 줄, 120자): user `projects`·MCP `hub_projects`에 넣고, user `project_set`으로만 바꾼다(MCP로는 바꾸지 않음) | 매 턴 문맥에 넣을 한 줄 설명(§4.1). 에이전트가 고칠 수 있는 노트 첫 줄을 쓰지 않기 위해 |
| HP3 | MCP 안내문의 세션 문장과 `hub_projects` 확인 문장 고치기(§6.3), `hub_delegate`의 `session`·`fresh` 설명을 HP1에 맞추기 | 지금 안내문은 차례 규칙을 전제함 |

없는 hub에서: HP1 없음 → 지침은 "이 대화의 세션이 있으면 `session`, 없으면 지정하지 않음(차례)"으로 낮추고, 두 대화가 섞일 수 있음을 알고 간다. HP2 없음 → 요약 없이 이름과 기기만. HP3 없음 → v3 지침과 hub 안내문이 세션에서 다르게 말하므로 HP1과 함께 넣는다.

나중에 검토(이번 범위 밖): HP4 위임의 기본을 "세션을 지정하지 않으면 새 세션"으로 바꾸기(지침을 자주 어길 때), 프로젝트 이름 바꾸기와 v3 색인의 `id` 전환, 여러 프로젝트를 묶은 "묶음".

## 10. 단계와 확인

| 단계 | 내용 | 확인 |
| --- | --- | --- |
| H | hub HP1·HP2·HP3 | hub 테스트(가짜 에이전트): `new_session`이 차례 세션을 닫지 않음, `session`·`fresh`와 함께 주면 거절, `summary`가 MCP로 바뀌지 않음 |
| S1 | v3 색인 두 테이블, 이벤트에서 다시 만들기, 턴 시작 때 세션 채우기 | pytest(가짜 hub): 위임 → 색인, 다시 만들기가 같은 결과, 휴지통 비우기 |
| S2 | Current State의 hub 프로젝트 절과 이 대화의 hub 작업 절, HIMARI 지침 | pytest: 경로·roots·짝 코드가 절에 없음, 30개 한도, hub 꺼짐·응답 없음. 실제 모델 시험: 두 대화가 같은 프로젝트에 맡겨도 세션이 섞이지 않음, 프로젝트 이름 없이 "hub의 그 버그"로 맞는 프로젝트를 찾음, 첫 위임 전에 노트를 읽음 |
| W1 | 새 작업에서 "To:" 제거, 사이드바 재배치(날짜 묶음, 프로젝트 태그·거르기, 찾기) | Vitest, Playwright(`scripts/web_next_hub.py`) |
| W2 | 맡긴 작업 카드(승인·중지·자세히 패널), 대화 머리줄 태그 | Vitest, Playwright |
| W3 | 프로젝트 화면 넓히기(목록, 요약, 다룬 대화, 세션, 직접 맡기기, 작업 현황 탭) | Vitest, Playwright |
| M | 자동 기억 판정에 "프로젝트 사실은 기억하지 않음" | 기억 작업 테스트 |

W1은 S2와 함께 내보낸다: "To:"를 없앤 뒤 HIMARI가 프로젝트를 모르면 일이 막힌다.

## 11. 위협과 대응

| 위협 | 대응 |
| --- | --- |
| 기기 경로가 모델 문맥에 들어감 | Current State 절은 모델 뷰만 만든다(§4.1). 시험으로 막음 |
| 에이전트가 쓴 글이 매 턴 시스템 영역에 들어가 HIMARI를 조종 | 요약은 사용자만 쓰는 칸(HP2), 노트는 HIMARI가 Tool로 읽을 때만(Tool 결과로) |
| HIMARI가 엉뚱한 프로젝트에 맡김 | 카드에 프로젝트·기기를 늘 보임, 중지, 쓰기는 승인 |
| 다른 대화의 세션을 닫음 | HP1(`new_session`), `fresh`는 `fresh` 프로필에만 |
| 색인이 이벤트와 어긋남 | 색인은 다시 만들 수 있음(§5.1), 화면의 원본은 여전히 hub |

## 12. 열린 질문

1. 프로젝트를 쓰지 않은 대화도 사이드바 거르기에 "프로젝트 없음"으로 둘지.
2. Current State의 프로젝트 한도(30)와 "최근 7일" 기준이 맞는지.
3. 지금 HIMARI는 맡긴 뒤 `hub_task`의 `wait_seconds`로 같은 턴 안에서 기다린다(hub 안내문). 그 기다림을 넘겨 끝난 긴 작업을 사용자가 묻지 않아도 보고하려면 턴을 새로 열어야 한다. 지금의 깨우기(V3-P87)로 할지, 카드만 바꾸고 다음 턴에 말할지.
4. 작업 앱(V3-P104)의 상태 줄을 Web 사이드바의 기기 상태로 옮길지(앱 다듬기와 함께).
