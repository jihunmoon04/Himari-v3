# 작업 진행 줄 v0.1

> 2026-10-23 · **PROPOSED (V3-P68)** · rev. 2 — 소유자 설계 검수 NOT_READY(B1; C1·C2) 반영(§12). rev. 1: 설계 초안.
>
> 소유자 방향(2026-10-23): 모델이 일하는 동안 지금 어떤 단기 목표로 움직이는지(코드 조사 중, 설계 중, 구현 중) 알 수 있어야 한다. Tool 호출마다 설명할 필요는 없다. Web에서는 흐린 진행 줄로 보이다가, 최종 응답이 나오면 최종 응답만 보인다. 대화에서 정한 것(§9): 방식 A(프롬프트 지시 + 기존 commentary), Tool 줄은 남기되 하나로 접기 — 모두 권고대로.
>
> 앞선 결정: Tool 호출과 함께 온 글은 commentary로 같은 `assistant_tool_calls` Event에 보존하고 final 신호로 보지 않는다(V3-P16). 단계마다 모델이 바뀌면 처음 보이는 것에 이름을 붙인다(V3-P64 §7, PR #53 검수 B1). MCP 앱 화면(V3-P57/P58), 건넨 파일(V3-P66 §9), Tool 이미지(V3-P67 §8).

## 1. 왜, 그리고 범위

지금은 모델이 Tool을 여러 번 부르는 동안 사용자가 볼 수 있는 것이 Tool 줄(`inside/run_command · running`)뿐이다.
- 모델이 Tool 호출과 함께 글을 보내면 받아서 보존하고(`provider/openrouter.py`, V3-P16) Web·CLI가 보여준다. 하지만 그렇게 하라는 지시가 없어 대부분의 모델은 글 없이 호출만 보낸다.
- 글이 와도 Web은 최종 답과 같은 말풍선으로 그린다(`app.js` `renderEvent`). 작업이 끝나면 진행 글과 Tool 줄 수십 개가 최종 답 위에 그대로 쌓인다.

| 포함 | 제외 (이후) |
| --- | --- |
| 모델에게 "단기 목표가 바뀔 때만 한 줄" 지시 | 실시간 스트리밍(글이 쓰이는 대로 보이기) |
| Web: 작업 묶음 하나에 흐린 진행 줄, 끝나면 `N tool calls`로 접기 | 진행 전용 Tool(`set_status`) — §8 |
| Web: 앱 화면·건넨 파일·Tool 이미지는 접지 않음 | plan(할 일 목록)과의 연결 — plan 패킷에서 |
| CLI: commentary를 답이 아니라 진행 한 줄로 | CLI에서 지난 줄 지우기 |

Data·API·Provider는 바꾸지 않는다. 바뀌는 것은 고정 지시문 한 단락과 Web·CLI 표시뿐이다.

## 2. 다른 호스트

- **Codex CLI:** 시스템 프롬프트가 Tool 호출 전에 짧은 preamble(무엇을 하려는지 한두 문장)을 쓰게 하고, 관련된 호출은 한 번에 묶어 설명하게 한다. 글은 Tool 호출과 같은 응답에 담긴다.
- **Claude Code:** Tool 호출 사이의 글을 그대로 남긴다. 작업 단계는 별도 할 일 목록(TodoWrite)으로 보인다.
- **claude.ai·ChatGPT:** Tool 사용과 중간 생각을 한 줄 요약으로 접고, 펼치면 자세히 보인다. 최종 답이 화면의 중심이다.

HIMARI는 Codex처럼 지시로 짧은 글을 받고(§3), claude.ai처럼 끝나면 접는다(§5). 할 일 목록은 plan 패킷에서 다룬다.

## 3. 모델에게 주는 지시

고정 지시문에 한 단락(`PROGRESS_NOTE`)을 더한다. `ATTACHMENT_NOTE`·`TOOL_IMAGES_NOTE`처럼 운영자 지시문 뒤에 붙고, 늘 붙는다(`bootstrap/application.py`).

```text
While you work with tools, let the user follow your current short-term goal. When you start a new
stage of the task (for example: looking through the code, designing, implementing, testing), write
one short sentence about it, in the user's language, in the same reply as that stage's first tool
calls. Do not write anything with tool calls that keep working toward the same goal. These lines are
hidden once you give your final answer, so put everything the user needs to know in that answer.
```

- **단계마다, 호출마다가 아님:** 같은 목표의 호출에는 글을 붙이지 말라고 한다. 모델이 더 자주 써도 Web은 마지막 한 줄만 진행 줄에 보이므로(§5.2) 화면은 어긋나지 않는다.
- **사용자의 언어:** 진행 줄은 사용자가 읽는 글이다.
- **최종 답에 모든 것을:** 진행 글은 접혀 숨으므로(§5.4) 사용자가 알아야 할 것을 진행 글에만 두면 안 된다고 알린다.
- `ask_user` 질문은 진행 글이 아니다. 질문은 지금처럼 Tool 인자로 가고 화면에 질문으로 보인다. `ask_user`와 함께 온 글은 질문의 앞말로 보인다(§5.1).
- 프롬프트 캐시: 고정 앞부분이 한 번 바뀐다(배포 직후 첫 요청). 이후는 같다.

## 4. 기록과 Provider — 바뀌지 않음

- 진행 글은 V3-P16 그대로 `assistant_tool_calls` Event의 commentary 블록이다. 새 Event 종류를 만들지 않는다.
- 다음 요청에도 대화 기록으로 모델에게 간다(assistant 메시지의 `content`). 모델은 자기가 무엇을 하던 중이었는지 안다. 크기 추정과 압축도 지금과 같다.
- Web API의 `assistant_tool_calls` 보기에는 이미 `text`가 있다(`interfaces/web/app.py`). 새 필드가 필요 없다.

## 5. Web

### 5.1 작업 묶음

**작업 묶음**은 화면에 보이는 메시지 사이에 이어진 Tool 단계들이다.
- 보이는 메시지: 사용자 메시지(질문에 대한 답 포함), `ask_user` 질문, 최종 답, 알림 줄("Question closed without an answer").
- 그 사이의 `assistant_tool_calls`와 `tool_result`는 하나의 묶음으로 들어간다. Run이 여러 번이어도, 일시정지 뒤 계속해도, 그 사이에 보이는 메시지가 없으면 같은 묶음이다.
- **예외: 압축 경계.** 묶음은 압축 경계를 넘지 않는다(§5.6).
- 묶음은 `<details>` 하나다. 요약 줄(summary)과 펼친 내용(진행 글과 Tool 줄을 원래 순서대로)으로 이루어진다.

**`ask_user`가 있는 단계(검수 C2):**
- 그 단계의 글은 진행 글이 아니라 **질문의 앞말**이다. 지금처럼 보통 assistant 글로, 질문 바로 앞에 보인다. 모델은 흔히 질문에 필요한 맥락(무엇을 찾았는지, 왜 묻는지)을 이 글에 쓰므로 접거나 지우지 않는다.
- `ask_user`만 있는 단계는 묶음을 만들지 않는다(빈 `1 tool calls` 묶음이 없다). 질문은 보이는 메시지이므로 앞 묶음은 거기서 끝난다.
- `ask_user`와 다른 Tool이 함께 있는 단계(V3-P15): 다른 Tool 줄은 질문 앞의 묶음에 들어가고, 글은 질문의 앞말이다.

### 5.2 실행 중: 흐린 진행 줄

- 요약 줄은 흐린 글씨로 **지금까지 받은 마지막 진행 글**과 Tool 호출 수를 보인다(예: `코드를 살펴보는 중 · 3 tool calls`). 새 진행 글이 오면 그 자리의 글만 바뀐다. 줄이 쌓이지 않는다.
- 진행 글이 아직 없으면 `Working · 3 tool calls`.
- **수는 모델이 요청한 Tool 호출 수다(검수 C1).** 실행 여부와 결과는 각 Tool 줄이 말한다(`running`·`done`·`failed`). 1개면 `1 tool call`.
- 실행 중임은 요약 줄의 작은 움직이는 점으로 알린다(기존 `topbar-state-dot`과 같은 모양).
- 묶음은 **닫힌 채로** 시작한다(Q1). 사용자가 펼치면 Tool 줄이 지금처럼 하나씩 보이고, 사용자가 연 것은 열린 채로 둔다.
- 펼친 내용 안의 진행 글은 흐린 한 줄씩, 그 단계의 Tool 줄 앞에 있다. Markdown은 지금의 `renderAssistantText`로 그린다(새 HTML 경로 없음).

### 5.3 결과물은 접지 않는다

사용자에게 주려고 나온 것은 묶음 밖, 묶음 바로 뒤에 온 순서대로 놓는다.
- **MCP 앱 화면이 있는 Tool 줄:** 화면 자리(`app-view-slot`)가 Tool 줄 안에 있으므로 그 Tool 줄째로 묶음 밖에 둔다. 호출 때 `app_view`를 알면 처음부터 밖에, 결과 때 알게 되면 그때 밖으로 옮긴다.
- **건넨 파일 카드**(`presentedCard`)와 **Tool 이미지**(`toolImages`).

그래서 묶음 뒤의 결과물 순서는 지금과 같지만, 사이사이에 있던 Tool 줄이 빠져 묶음 하나로 모인다.

### 5.4 끝났을 때

- **최종 답이 오면:** 요약 줄이 `7 tool calls`로 바뀌고 진행 글은 요약에서 사라진다. 묶음은 닫힌다(사용자가 연 것이라도 — 최종 답이 화면의 중심). 펼치면 진행 글과 Tool 줄이 그대로 있다.
- **최종 답 없이 멈추면**(일시정지·취소·예산·오류): 요약 줄은 같은 `7 tool calls`가 되고 진행 줄은 사라진다. 왜 멈췄는지는 지금처럼 멈춤 패널과 상태 줄이 말한다. Continue하면 그 묶음이 다시 실행 중이 된다(§5.1).
- **실행되지 않은 호출(검수 C1):** 일시정지로 결과 없이 남은 호출이 있고 작업이 멈춰 있으면, 요약 줄에 그 수를 붙인다: `4 tool calls · 2 not run`. 취소로 닫힌 호출은 결과(`cancelled`)가 있으므로 그 Tool 줄이 `failed`로 말한다.
- **`ask_user` 질문이 오면:** 앞 묶음은 끝난 것으로 접히고 질문(앞말 포함, §5.1)이 보인다. 답 뒤의 Tool 단계는 새 묶음이다.
- **최종 답이 비었으면:** 접은 뒤 보일 새 글이 없다. 묶음은 펼칠 수 있게 남는다.
- **Tool 하나 없이 진행 글만 있는 단계는 없다:** commentary는 늘 Tool 호출과 함께 온다(V3-P16).

### 5.5 모델 이름

V3-P64 §7의 "단계마다 한 번, 처음 보이는 것에" 규칙에서, 처음 보이는 것이 진행 글이나 Tool 줄이면 이제 그 자리는 **묶음 요약 줄**이다. 기존 `.item-step` 머리줄(Tool 호출만 있는 단계 위에 모델 이름)은 요약 줄 앞의 모델 이름으로 바뀐다. 한 묶음 안에서 모델이 바뀌면 펼친 내용의 그 단계 앞에 이름이 있다. 최종 답과 질문은 지금과 같다.

### 5.6 압축 경계 (검수 B1)

지금 Web은 압축 구분선을 타임라인의 최상위 노드 중 `data-sequence`가 `covered_through_sequence`보다 큰 첫 노드 앞에 놓는다(`placeDivider`). 묶음 안의 단계 사이에 경계가 있으면 구분선을 놓을 자리가 없고, 어느 작업부터 모델 문맥에 원문으로 남아 있는지 잘못 보인다.

- **묶음은 경계를 넘지 않는다.** 경계가 묶음 안에 걸리면 그 자리에서 묶음을 둘로 나누고, 구분선은 두 묶음 사이에 놓는다. 앞 묶음은 끝난 것으로 접히고(`N tool calls`), 실행 중이면 뒤 묶음이 진행 줄을 이어받는다.
- 경계는 늘 Tool 단계 사이에 온다. 압축은 Tool 그룹과 그 결과를 나누지 않는다(`prompt/compaction.py`). 그래서 한 단계의 Tool 줄이 두 묶음으로 갈라지지 않는다.
- 묶음 노드의 `data-sequence`는 그 첫 Event의 sequence다. 묶음 안의 노드도 각자 sequence를 가지므로 경계 뒤 첫 노드를 찾아 나눌 수 있다.
- **언제나 같은 규칙:** 처음 그릴 때, 새로고침, 지난 대화 열기, 실행 중 압축(경계가 생긴 뒤 오는 Event는 경계 앞 묶음에 들어가지 않음), 추가 압축(구분선이 옮겨가면 새 경계에서 다시 나눔).
- 추가 압축으로 구분선이 옮겨가면, 이전 경계에서 나뉜 두 묶음은 다시 합치지 않는다. 새로고침하면 하나로 그려진다. 사이에 구분선이 없는 두 묶음일 뿐 잘못 알리는 것은 없다.

### 5.7 새로고침과 지난 대화

같은 규칙을 모든 Event에 적용한다. 새로고침하면 끝난 묶음은 접힌 `N tool calls`로, 실행 중인 묶음은 마지막 진행 글로 그려진다.

지난 대화의 commentary(이 지시 전 모델이 쓴 긴 글 포함)도 묶음 안에 접힌다. 내용은 펼치면 그대로 있다.

## 6. CLI

터미널은 지난 줄을 지울 수 없다(로그처럼 남는다). 그래서 숨기지 않고 **답과 다르게** 찍는다.
- commentary는 `HIMARI:` 블록이 아니라 들여쓴 진행 한 줄이다: `  » 코드를 살펴보는 중`(`»`를 못 쓰는 출력은 `>`, `Symbols` 규칙).
- 여러 줄이면 첫 줄과 `…`만(Q2). `--verbose`면 전부.
- 모델 이름 규칙(V3-P64 §7)은 그대로다. 진행 줄이 처음 보이는 것이면 그 위에 `HIMARI (model):`.
- Tool 줄(`  → tool …`, `  ← tool ✓`)은 지금과 같다.

## 8. 하지 않는 것과 이유

- **진행 전용 Tool(`set_status`):** 형식은 확실하지만, Tool을 한 번에 여러 개 부르지 못하는 모델은 단계가 바뀔 때마다 모델 호출이 한 번 더 든다. 프롬프트 지시로 시작하고, 모델들이 잘 따르지 않으면 그때 다시 본다.
- **스트리밍:** 글이 쓰이는 대로 보이려면 Provider 응답, 저장, Web 전송을 모두 바꿔야 한다. 지금도 진행 글은 그 단계의 Tool이 실행되기 전에 보이므로(응답이 오면 Event가 먼저 기록됨) 오래 걸리는 Tool 동안 무엇을 하는지는 보인다.
- **Tool 줄을 아예 숨기기:** 무엇을 했는지 확인할 길이 없어진다. 접어 둔다.
- **plan과 연결:** 단기 목표는 나중의 plan(할 일 목록)의 현재 단계와 이어질 수 있다. plan 패킷에서 정한다.

## 9. 소유자 결정

대화에서 정한 것(2026-10-23, "전부 추천대로 괜찮아"):
- 실행 중 흐린 진행 줄, 최종 응답이 나오면 최종 응답만 보인다.
- 방식은 A: 프롬프트 지시 + 기존 commentary. 진행 전용 Tool(B)은 모델이 잘 따르지 않을 때 다시 본다.
- 최종 응답 뒤 Tool 줄은 숨기지 않고 하나로 접는다(rev. 2부터 요약 줄은 `N tool calls`, 검수 C1).
- 고정 프롬프트는 별도 패킷으로 이어서 한다.

## 10. 위협과 대응

- **진행 글은 모델이 쓴 글:** 지금 assistant 글과 같은 `renderAssistantText`로 그린다. 새 HTML 경로를 만들지 않는다.
- **모델이 진행 글에만 무언가를 남김:** 접혀도 지워지지 않으며 펼치면 보인다. 지시문이 최종 답에 모든 것을 두라고 한다.
- **결과물이 묶음에 숨음:** 앱 화면·건넨 파일·Tool 이미지는 묶음 밖이다(§5.3). 회귀 테스트로 지킨다(§11).

## 11. 검증 계획

- **Prompt/Bootstrap:** 지시문에 `PROGRESS_NOTE`가 운영자 지시문 뒤에 늘 들어간다(`tests/bootstrap`).
- **CLI:** commentary가 `  » …` 한 줄로, 여러 줄이면 첫 줄과 `…`, `--verbose`면 전부, ASCII 출력은 `>`. 진행 줄만 있는 단계의 모델 이름(`tests/interfaces/test_cli*.py`).
- **브라우저 스모크(`scripts/ui_smoke.py`) 새 시나리오:** 대본 모델이 "진행 글 + Tool" 두 단계, 진행 글 없는 Tool 단계, 파일을 건네는 Tool, 최종 답.
  - 실행 중: 요약 줄에 마지막 진행 글, 묶음은 닫힘, 진행 글이 쌓이지 않음.
  - 끝난 뒤: `N tool calls`, 진행 글이 요약에 없음, 건넨 파일 카드는 묶음 밖.
  - 새로고침해도 같음. 모델이 바뀐 단계의 이름이 요약 줄에.
  - `ask_user`(검수 C2): 글과 함께 온 질문 단계는 묶음 없이 앞말 + 질문으로 보이고, 앞뒤 묶음이 나뉜다. 다른 Tool과 함께 온 질문 단계는 그 Tool 줄만 앞 묶음에.
  - 실행되지 않은 호출(검수 C1): Tool 호출 둘 중 하나를 실행하는 동안 일시정지 → `2 tool calls · 1 not run`. Continue 뒤 끝나면 `· not run`이 사라짐. 취소로 닫힌 호출은 그 Tool 줄이 `failed`.
  - 압축 경계(검수 B1): 첫 Tool 단계 뒤에 압축되는 대본(작은 문맥 예산) — 구분선이 두 묶음 사이에 있음. 새로고침·대화 다시 열기·추가 압축 뒤에도 구분선이 묶음 안에 있지 않음.
  - 앱 화면이 있는 Tool 줄은 묶음 밖(기존 MCP 앱 시나리오에 확인 추가).
- **실모델 확인(배포 뒤 소유자):** 코드 작업 하나를 시켜 단계마다 한 줄이 오는지, 호출마다 오지는 않는지 본다. 잘 따르지 않는 모델이 많으면 §8의 B를 다시 본다.
