# 작성 중인 것 지키기 v0.1

> 2026-10-26 · **PROPOSED (V3-P78)** · rev. 1: 설계 초안. 소유자 결정 Q1~Q4 권고대로(§9).
>
> 소유자 방향(2026-10-26): 지금까지 구현한 Web을 사용자 경험 쪽에서 점검했고(화면 확인 + 코드 검토), 찾은 항목을 우선순위 높은 것부터 차례로 진행한다. 이 패킷은 첫 묶음, **사용자가 쓴 것을 잃는 경우**를 다룬다.
>
> 앞선 결정: 입력창 하나를 홈과 대화가 같이 쓴다(홈에서 쓴 글로 대화를 시작). 보내기 결과를 모르면 초안을 남기고 다시 보내지 않는다. 업로드는 서버에 대화별로 먼저 올리고 메시지가 그 id를 가리킨다(V3-P66). 편집기는 명시적 저장, `identity`로 충돌을 감지한다(V3-P75 §7). 저장 안 한 필기는 IndexedDB에 임시로 남긴다(V3-P77 §4.5, 2c).

Data·Provider·runner는 바꾸지 않는다. 서버는 Web 경로 하나를 더한다(§4.2).

## 2. 다른 앱

- **ChatGPT·claude.ai:** 대화마다 초안이 따로 남는다. 다른 대화로 갔다 오면 쓰던 글이 그대로 있고, 새로고침해도 남는다(브라우저 저장소).
- **Slack:** 채널마다 초안을 두고, 사이드바에 "Drafts"로 모아 보인다.
- **VS Code(웹 포함)·Obsidian:** 저장 안 한 편집을 "hot exit"로 보관해, 창을 다시 열면 저장 안 한 상태로 되살린다. 디스크 파일이 그 사이 바뀌었으면 비교를 연다.
- **Google Docs류:** 서버에 바로 저장하므로 해당 없음.

HIMARI는 ChatGPT처럼 자리마다 초안을 두고(§3), VS Code처럼 편집기 글을 되살리며 바뀐 판이면 지금의 충돌 흐름으로 넘긴다(§4).

## 3. 입력창 초안

### 3.1 자리마다 초안

- **자리**는 홈 하나와 대화마다 하나다. 입력창은 한 번에 한 자리의 것이다.
- 초안은 `{ text, attachments, references, at }`이다.
  - `attachments`: 올리기가 끝난(`ready`) 파일만 `{ fileId, name, size }`. 서버에 이미 있으므로 id만 기억한다.
  - `references`: 편집기에서 붙인 참조 칩 그대로(경로, identity, 범위, 해시). 보낼 때 서버가 다시 확인하므로(V3-P76 §3) 오래된 칩은 그때 `reference_stale`로 알려진다.
- 자리를 **떠날 때**(다른 대화 열기, 홈, 휴지통·설정 화면, 로그인 화면) 지금 자리의 초안을 저장하고 입력창을 비운다.
- 자리에 **들어갈 때** 그 자리의 초안을 입력창에 되돌린다.
- **홈에서 대화 시작:** 홈의 초안은 새 대화로 옮겨 가고 홈은 비워진다. 지금처럼 그 글이 새 대화의 첫 메시지로 간다.
- **보내기가 받아들여지면**(202) 그 자리의 초안에서 보낸 것만 지운다(지금처럼 보내는 사이에 고친 글은 남는다). 결과를 모르면 남긴다.
- 휴지통으로 옮긴 대화의 초안은 지운다. 복원은 드물고, 영구 삭제된 대화의 글을 브라우저가 들고 있지 않게 하기 위해서다.

### 3.2 올리는 중에 떠날 때 (Q1)

지금은 올리던 파일이 말없이 취소된다. 권고: **떠나기 전에 묻는다.** "A file is still uploading. Leave and cancel it?" — Leave / Stay. 편집기의 `mayLeave`와 같은 자리에서 묻는다.

다른 안: 떠나도 백그라운드에서 계속 올리고, 끝나면 그 대화의 초안에 붙인다. 큰 파일에는 더 편하지만, 상태가 화면 밖에 있게 되고(실패를 어디에 알릴지), 로그아웃·대화 삭제와 엮인다. 첫 단계에서는 묻기로 하고, 불편하면 바꾼다.

### 3.3 브라우저 보관

- 입력할 때마다(0.4초 모아서) 그리고 떠날 때·`pagehide`·`visibilitychange`(hidden) 때 저장한다. iPad Safari가 탭을 내리기 전에 오는 것은 `visibilitychange`다.
- 저장소는 §5의 IndexedDB `himari-local`의 `drafts`다. 키는 `home` 또는 대화 id.
- 한도(Q3): 글은 32,000자(메시지 한도)까지 그대로, 넘으면 그 길이까지만 보관하고 입력창에는 그대로 둔다. 자리 50개, 30일. 넘치면 오래된 것부터 지운다.
- 저장소를 쓸 수 없으면(사설 모드, 용량) 조용히 페이지 메모리만 쓴다. 자리 사이 이동은 그래도 지켜진다.

## 4. 편집기

### 4.1 저장 안 한 글의 임시 보관

- 편집기의 글이 저장된 글과 다르면(`dirty`) 1초 모아서 `{ path, base, text, lineBreak, at }`을 §5의 `unsaved`에 둔다. `base`는 그 글을 읽었을 때의 `identity`다. 키는 경로.
- 저장하면, 서버 판을 불러오면, 또는 사용자가 "Leave without saving"을 고르면 지운다.
- **같은 파일을 다시 열 때** 보관된 글이 있으면:
  - `base`가 지금 파일의 identity와 같으면: 보관된 글을 편집기에 넣고 저장 안 한 상태로 연다. 막대: "Unsaved changes from 10:42 were restored." — Discard them.
  - 다르면(그 사이 파일이 바뀜): 보관된 글을 넣되 `identity`는 `base`로 둔다. 그러면 지금의 충돌 막대가 바로 뜬다("This file was changed on the server since you opened it. Your text is still here." — Compare, Load the server's version, Save mine over it). 새 흐름을 만들지 않고 이미 검수된 충돌 흐름을 쓴다.
  - 파일이 없으면: §4.2의 막대.
- 한도(Q3): 1 MiB(편집기 한도), 파일 20개, 30일.

### 4.2 파일이 사라졌을 때

- 저장이 `changed`로 거부되거나 5초 확인이 `not_found`를 받으면 `stat`으로 확인한다. 파일이 없으면 충돌 막대 대신 이 막대를 보인다.
  - "This file is no longer on the server (deleted or moved). Your text is still here."
  - **Save it here again** — 같은 경로에 내 글로 새 파일을 만든다(Q4).
  - **Download my text** — 브라우저에서 바로 `.txt`가 아닌 원래 이름으로 내려받는다(서버를 거치지 않음).
- "Save it here again"은 새 경로 `POST /api/machine/file/install` `{ path, content }`를 부른다. 서버는 이미 있는 `MachineExplorer.install`(V3-P76 §4.1: 이름이 비어 있을 때만 한 번에 놓기)을 쓴다.
  - 그 사이 같은 이름의 파일이 생겼으면 `changed`: 지금의 충돌 막대로 넘긴다(그 파일의 identity로).
  - 폴더도 없으면 `not_found`: "The folder is gone too; download your text." 그리고 Download만 남긴다.
  - 쓰기 정책은 저장과 같다: 숨김 목록·`writable_under`는 막고, 1 MiB.
  - 만들면 새 identity로 저장된 상태가 되고 보관된 글은 지운다.
- 이전 판은 없다(없던 파일을 만드는 것이므로). 지워졌던 파일 자체의 이전 판은 Previous versions → Deleted에 그대로 있다.

## 5. 브라우저 저장소 하나

- IndexedDB 데이터베이스 `himari-local`(판 1), 객체 저장소 둘:
  - `drafts`: 입력창 초안(§3). 키는 자리.
  - `unsaved`: 파일의 저장 안 한 것. 키는 경로, 값에 `kind`(`text`). V3-P77 2c의 필기는 같은 저장소에 `kind: "ink"`로 들어간다(2c 설계의 "키는 경로와 identity"는 값의 `base`로).
- 작은 모듈 `static/local_store.js`가 열기·읽기·쓰기·한도 정리를 맡고, 모든 호출은 실패해도 예외를 밖으로 내지 않는다.
- **로그아웃(Q2):** Sign out은 이 저장소를 비운다. 보관된 것이 있으면 확인 창에서 알린다("Unsaved drafts kept in this browser (3) will be deleted."). 세션 만료·서버 재시작으로 로그인 화면이 뜨는 것은 로그아웃이 아니므로 지우지 않는다. 바로 그때 지켜야 하기 때문이다.
- 이 저장소는 그 브라우저의 프로필에 평문으로 남는다. HIMARI는 소유자 한 사람의 도구이고, 다른 사람이 쓰는 기기에서는 Sign out으로 지운다(§8).

## 6. 로그인 화면

- `showLogin()`은 로그인 화면이 이미 보이면 아무것도 하지 않는다. 토큰 칸을 비우고 포커스하는 것은 처음 보일 때만이다.
- 로그인 화면으로 갈 때 파일 패널과 Files 화면의 5초 확인·PDF 확인을 멈춘다. 다시 로그인하면 열려 있던 파일의 확인이 다시 돈다.
- 로그인 화면으로 가기 전에 지금 자리의 초안과 편집기 글을 저장한다(§3.3, §4.1). 그래서 다시 로그인한 뒤 그 대화를 열면 글이 돌아온다.

## 7. 계약 변경 (Proposed)

- Web API: `POST /api/machine/file/install` `{ path, content }` → 201 `{ path, identity }`. 오류는 저장(`PUT /api/machine/file`)과 같은 형식이고, 더해지는 뜻은 `changed`(이름이 참)·`not_found`(폴더 없음)·`unsupported`(한 번에 놓을 수 없는 파일시스템)다.
- Web 화면: 위의 동작. 새 정적 파일 `local_store.js`.
- Data·Provider·runner·CLI: 바뀌지 않음.

## 10. 검증 계획

- 서버: `POST /api/machine/file/install`의 성공, 이름이 찬 경우 `changed`, 폴더 없음 `not_found`, 숨김·크기 거부(pytest, 지금의 explorer 테스트 옆).
- 브라우저 스모크 `drafts`(`scripts/ui_smoke.py`):
  1. 대화 A에 글 + 첨부 칩 → 대화 B: 입력창이 비어 있음 → A로 돌아오면 글과 칩이 그대로.
  2. 홈에서 쓴 글로 대화 시작: 새 대화의 첫 메시지가 되고 홈은 빔.
  3. 새로고침 → 로그인 → A를 열면 글이 돌아옴. Sign out 뒤 다시 로그인하면 없음.
  4. 올리는 중에 다른 대화로: 묻고, Stay면 그대로.
  5. 편집기에 글 → 새로고침 → 같은 파일 열기: "restored" 막대와 저장 안 한 상태. 그 사이 파일을 바꾸면 충돌 막대.
  6. 편집 중 파일을 서버에서 지움 → 저장: "no longer on the server" 막대 → Save it here again이 파일을 만들고 Saved.
  7. 서버 재시작(세션 지움) 상태에서 파일이 열린 채 로그인 화면: 토큰을 적고 6초 기다려도 남아 있음.
  8. 좁은 화면(390px)에서 1, 5, 6의 막대.
- iPad 실기기(소유자): 앱 전환으로 탭이 내려간 뒤 돌아와 초안과 편집 글이 남는지.
