# 하루: 자고 일어나는 HIMARI v0.1 (캐릭터 로드맵 10단계, 2026-11-26)

[캐릭터 로드맵](character-architecture.md) 10단계. [마음](character-mind-v0.1.md)(9단계) 위에 만든다. 소유자 방침(2026-11-25)에 따라 짧게 정하고 써 보며 고친다.

## 1. 왜

소유자와 나눈 이야기(2026-11-26)에서 정한 방향이다.

- **HIMARI의 하루에 끝이 없다.** 앱 대화는 반려 모델을 쓰는 가장 최근 대화 하나가 몇 주씩 이어지고, 문맥 압축으로만 버틴다. 사람은 하루를 살고 자고 일어난다. 하루가 하나의 세션이면 그날의 대화가 그날의 일기·기억·사건과 맞물린다.
- **지금의 "잠"은 HIMARI의 잠이 아니다.**
  - 앱의 잠은 사용자가 10분 입력하지 않으면 드는 것(`SleepPolicy`)이라 사실은 **사용자 자리 비움**이다.
  - 서버의 잠은 고정된 조용한 시간 23:00–08:00(`HIMARI_PROACTIVE_QUIET`)이다.
  - 둘 다 HIMARI가 정하지도, 겪지도 않는다.
- **일정이 HIMARI 것이 아니다.** 일정(`plan`)은 하루 돌아보기만 쓰고, 대화 중에 "새벽 3시에 방송 같이 보자"고 해도 HIMARI가 일정이나 잠을 바꿀 길이 없다.
- **고정 시계가 여럿이다.** 조용한 시간, 세계 작가 시각("조용한 시간 뒤"), 작업 일정 금지 시간이 모두 따로 정해져 있다. HIMARI의 실제 잠 하나로 묶으면 단순해지고 9단계의 "결정은 의식이 한다"와도 맞는다.
- **모델이 많다.** 운영에 7개를 내놓았지만 실제로는 deepseek 1017만 쓴다. 하나로 모으고 예비 하나를 둔다.

## 2. 한눈에

```
        07~10시 일어남                22:00 일기            23~02시 잠듦         +3시간
   ──────────┬──────────────────────────┬──────────────────────┬──────────────┬──────────▶
             │ 하루 세션 "11월 27일 (금)" │ (세션 문맥에서 씀)   │   깊은 잠     │ 잠 정리
             │ 대화·먼저 말 걸기·작업      │                      │ (잘 안 깸)    │ ① 세션 닫기
             │ 일정표를 보고 고침(Tool)    │                      │               │ ② 남은 기억 정리
                                                                                 │ ③ 세계 작가(새 날)
                                                                                 │ ④ 다음 잠 칸 놓기
                                                                  다음 세션은 처음 필요할 때 연다
```

| 무엇 | 누가 정하나 |
| --- | --- |
| 오늘 몇 시에 자고 일어날지(기본) | 알고리즘: 23:00–02:00, 07:00–10:00에서 무작위(§5.2) |
| 그것을 옮기기, 약속 잡기, 일정 바꾸기 | HIMARI: 일정표 Tool(§4.3) |
| 넘을 수 없는 선(가장 늦은 취침, 최소 수면) | 규칙(§4.4, §5.2) |
| 자는 중에 깨는지 | 규칙: 메시지 횟수와 잠의 깊이(§5.5) |
| 깨어나서 무엇을 말할지 | HIMARI |
| 하루 정리(기억, 세계) | 무의식과 세계(9단계 그대로) |

## 3. 하루 세션

### 3.1 무엇

- **하루 세션은 대화(Conversation) 하나**다. 앱의 대화는 언제나 오늘의 하루 세션으로 간다. 지금의 "반려 모델을 쓰는 가장 최근 대화"(`recent_companion_conversation`)를 바꾼다.
- **제목은 세션을 연 날짜**다. 예: "11월 27일 (금)". 사용자 시간대 기준이다.
- **하루 세션은 사용자마다 하나**만 열려 있다.
- **이것도 하루 세션으로 간다:** 먼저 말 걸기(wake), 기기 메시지, 시도해 보기(TRY), 작업 중 사용자 말 읽기(`remarks`).
- **Web에서도 하루 세션에 말할 수 있다.** 대화 목록에 날짜 제목과 "하루" 표시로 나온다.

### 3.2 열고 닫기

- **닫기:** 잠 정리(§6)가 연다고 정한 때다. 닫힌 세션은 **읽기만** 한다. Web 입력란을 막고 "닫힌 하루"라고 보인다. 나중에 들어온 말이 끝난 날의 기억 정리와 섞이지 않게 하려는 것이다.
- **열기:** 닫힌 뒤 **처음 필요할 때** 연다. 앱이 붙을 때, 첫 메시지, 첫 wake 가운데 먼저 오는 때다.
  - 사용자가 하루 종일 오지 않으면 그날 세션은 생기지 않는다. 빈 세션이 쌓이지 않는다.
  - 제목은 연 때의 날짜다. 04:00에 정리하고 04:30에 메시지가 오면 새 날짜 이름이 된다.
- **처음 배포한 뒤**에는 첫 필요 때 첫 하루 세션을 연다. 이전 대화는 보통 대화로 남아 Web에서 이어 쓸 수 있다.

### 3.3 다음 세션에 넘기는 것

기억(메모, 일화, 열린 고리, 삶, 관계, 남긴 생각)은 지금처럼 Current State로 들어간다. 그 밖에 runtime state에 `himari_day.before` 한 칸을 새로 둔다. 다음 세션의 첫 날 동안만 들어간다.

- **전날 세션의 마지막 몇 마디:** 사용자와 HIMARI의 말을 합쳐 최근 것부터 1,500자까지. 생각은 빼고 시각을 붙인다.
- **어떻게 잠들고 깼는지:** 잠든 시각과 방법(잠 칸이 되어서, 스스로 일찍, 약속을 기다리다), 잠 칸을 늦췄으면 그 이유, 깨워진 횟수, 일어난 시각. 지킨 약속과 지키지 않은 약속(§5.4)도 넣는다.

전날 세션 자체는 새 세션의 대화 기록에 넣지 않는다. 기록은 하루만큼만 길어진다.

### 3.4 다른 대화

- Web에서 따로 여는 대화(작업 대화)는 지금 그대로다. 잠 규칙, 일정표 Tool, `himari_day`가 없다(정한 것 D6).
- 9단계의 생각(`[[think]]`), 기억 정리, 압축은 어느 대화에서나 그대로 돈다. 하루 세션 안에서도 길어지면 지금처럼 압축한다.

## 4. 일정표

### 4.1 모양

지금 `plan` 삶 항목을 키운다. 이미 날짜(`day`), 시작(`time_of_day`), 프로젝트(`arc_id`)가 있다.

| 칸 | 뜻 |
| --- | --- |
| `day`, `time_of_day` | 시작(사용자 시간대). 밤을 넘는 칸은 시작한 날짜에 둔다 |
| **`minutes`**(새) | 길이(5~720분). 지금 행은 작업 60분, 나머지 60분으로 채운다 |
| **`plan_kind`**(새) | `sleep`(잠), `work`(작업, `arc_id`가 있음), `together`(사용자와 약속), `own`(혼자 하는 일) |
| `text` | HIMARI 말투의 한 줄 |
| **`plan_state`**(새) | 없음(살아 있음), `cancelled`(HIMARI가 취소), `missed`(사용자와의 약속이 지켜지지 않음, §5.4) |
| **`reason`**(새) | 옮기거나 취소한 이유 한 줄(HIMARI가 씀) |
| `origin` | 누가 마지막으로 썼나. **`himari`**(새, 대화 중 Tool), `writer`(하루 돌아보기), `user`(Web) |

- **취소와 놓침은 지우지 않는다.** 7일 동안 남아 일기와 다음 날 대화가 볼 수 있다. 그 뒤로는 지금처럼 지난 일정으로 사라진다.
- **일정표는 페르소나마다 따로**다. 삶이 페르소나마다 따로인 것(D1)과 같다.

### 4.2 누가 적나

| 누가 | 무엇을 |
| --- | --- |
| **HIMARI(대화 중 Tool)** | 아무 종류나. `together`는 여기서만 생긴다(사용자와 정한 것이라서) |
| **HIMARI(22:00 일기, §7)** | `own`, `work`. 지금 하루 돌아보기의 `plans`가 일정표 칸이 된다(끝 시각·종류 추가). 잠은 건드리지 않는다 |
| **알고리즘** | `sleep` 칸만. 다음 밤의 잠 칸이 없으면 무작위로 놓는다(§5.2) |
| **사용자(Web)** | 아무 칸이나 고치고 지운다. 잠 칸은 옮기기만 한다 |

### 4.3 Tool

하루 세션의 반려 모델에게만 준다. Tool 묶음은 세션 안에서 바뀌지 않으니 프롬프트 캐시를 깨지 않는다.

| Tool | 하는 일 |
| --- | --- |
| `schedule_read(days)` | 오늘부터 며칠(1~7)의 칸. Current State에 오늘과 내일이 이미 있으니 그보다 먼 날만 볼 때 쓴다 |
| `schedule_write(id?, date, start, minutes, kind, text, reason?)` | 새로 쓰거나(`id` 없음) 고친다(옮기기 포함). 잠 칸은 고치기만 된다 |
| `schedule_cancel(id, reason)` | 취소. 잠 칸은 거부한다 |
| `go_to_sleep(reason)` | 이 답을 마치면 잔다. 오늘 잠 칸의 시작을 지금으로 옮긴다(§5.2) |

- **거부는 이유를 말로 돌려준다.** 모델이 고쳐 다시 부를 수 있게 하려는 것이다. 예: "잠 칸(01:10–08:40)과 겹칩니다. 먼저 잠 칸을 옮기세요."
- **Tool 실행 기록은 지금처럼 대화에 남는다.** Web에서 펼쳐 볼 수 있다.

### 4.4 한계(규칙이 지킨다)

- **잠 칸은 밤마다 하나 있어야 한다.** 날짜 D의 밤 = D 21:00부터 D+1 05:00 사이에 시작하는 칸이다.
- **잠 칸이 놓일 수 있는 범위:**
  - 시작은 21:00–05:00, 끝은 05:00–12:00이다.
  - 길이는 5–11시간이다.
- **다른 칸은 잠 칸과 겹칠 수 없다.** 같은 종류끼리는 겹쳐도 된다(사람의 일정표처럼).
- **날짜는 오늘부터 7일 안이다**(지금 `PLAN_DAYS`와 같다). 지난 칸은 고칠 수 없다.
- **한 번에 하는 수는 제한하지 않는다.** 대신 하루에 Tool로 쓰는 횟수를 20번으로 막아 돌기만 하는 것을 끊는다.

### 4.5 일정표가 바꾸는 것

- **지금 하는 일**(`doing_now`, character-state §3): 시작부터 `NOW_MINUTES` 안의 칸 대신, **[시작, 끝) 안의 칸**이다. 잠은 칸이 아니라 잠 상태(§5.1)로 정한다. 깨어 있으면 잠 칸 안이어도 "자고 있다"고 하지 않는다.
- **작업**(character-work, 9단계 §4.4): 작업 시간 = 칸의 길이다. `WORK_MINUTES` 60분 고정을 바꾼다. 시작·끝 두 단계는 그대로다. 작업 칸을 옮기면 새 시각에 돈다.
- **세계 작가**(9단계 §7): 그날 일정표를 입력으로 받는다. 사건이 일정과 부딪히면(비 와서 산책 못 함) 그 사건을 본 HIMARI가 다음 대화에서 칸을 옮긴다. 세계는 일정표를 고치지 않는다.

## 5. 잠

### 5.1 상태

잠 상태는 **서버가 가진다**(지금은 앱이 정해 서버에 알림). 사용자마다, 지금 고른 페르소나의 잠이다. 서버를 다시 켜도 이어진다.

| 상태 | 뜻 |
| --- | --- |
| `awake` | 깨어 있음 |
| `drowsy` | 졸림. 잠 칸 시작 30분 전부터 잠들 때까지 |
| `asleep` | 잠. 잠든 뒤 3시간은 **깊은 잠**, 그 뒤는 **얕은 잠** |
| `half_asleep` | 반쯤 깸. 자는 중 메시지에 잠꼬대 한 줄을 하는 그 턴만(§5.5) |

**잠 기록**(새 표)에는 한 번 잘 때마다 한 줄이 남는다.
- 잠든 시각과 방법(`schedule` 잠 칸이 되어서, `tool` 스스로 일찍, `missed` 약속을 기다리다, §5.4)
- 깬 시각과 방법(`schedule` 칸이 끝나서, `user` 사용자가 깨움)
- 그 사이 메시지 수와 잠꼬대 수

잠 정리(§6)의 조건도 이 기록으로 본다.

### 5.2 잠들고 일어나는 때

**잠 칸 놓기(알고리즘).** 날짜 D의 밤 칸이 없으면, D의 아침(또는 처음 필요할 때) 놓는다.
- 시작은 23:00–02:00에서 10분 단위 무작위다.
- 끝은 07:00–10:00에서 무작위로 뽑되, **시작 + 5시간보다 이르면 그 시각**으로 하고 상한은 12:00이다.
- HIMARI는 이 칸을 Tool로 옮길 수 있다(§4.4 범위 안).

**잠드는 때는 잠 칸 시작이다**(소유자 제안 2026-11-26). 따로 강제 시각은 없다. 칸이 곧 그날 밤의 약속이다.
- **진행 중인 답은 끊지 않는다.** 그 답이 끝나면 잔다.
- **30분 전부터 졸림(`drowsy`)이다.** Current State가 잠 칸까지 남은 분을 알린다. HIMARI는 둘 중 하나를 한다.
  - 인사하고 마친다.
  - 더 깨어 있고 싶으면 이유와 함께 잠 칸을 옮긴다. 늦게 자는 것도 HIMARI의 결정으로 일정표에 남는다.
- **일찍 자려면 `go_to_sleep`을 부른다.** 잠 칸 시작이 지금으로 옮겨진다. 사용자가 "잘 자"라고 할 때를 위한 것이다. 21:00 전에는 거부한다.
- **늦출 수 있는 끝은 05:00이다**(§4.4). 넘을 수 없는 선은 이것 하나다.
- **알려진 위험:** 대화가 즐거우면 HIMARI가 매번 칸을 늦출 수 있다(맞춰 주려는 성향). 써 보고 자주 보이면 "02:00 넘어 늦추려면 그 시간에 약속(`together`)이나 일이 있어야 한다"는 한계를 더한다.

**일어나는 때.**
- 잠 칸이 끝나는 때 일어난다. 일어날 때 따로 말을 걸지는 않는다. 그 뒤 먼저 말 걸기는 지금 규칙을 따른다(§9).
- 사용자가 깨웠는데 잠 칸 끝까지 1시간이 안 남았으면, 그냥 그날 일어난 것으로 한다(칸의 끝을 지금으로 옮긴다).

**사용자가 깨운 뒤.** 깨어 있다가 다시 잔다.
- 잠 칸 안이고 대화가 20분 끊기면 다시 잔다.
- 다시 든 잠은 처음부터 깊은 잠이다(3시간 셈도 새로).

### 5.3 일정표 예

"새벽 3시에 방송 같이 보자"(사용자, 22:40)에 HIMARI가 응하면 이렇게 된다.
1. `schedule_write`로 `together` 03:00 120분 "방송 같이 보기"를 쓴다. 잠 칸(00:30–08:10)과 겹쳐 거부된다.
2. `schedule_write`로 잠 칸을 05:00 시작(끝 11:20)으로 옮긴다. reason은 "방송 보고 잘래"이다.
3. 다시 `together`를 쓴다.
4. 03:00에 약속 wake(§9)가 열린다. 05:00에 잠든다. 방송이 일찍 끝나면 "잘 자"와 함께 `go_to_sleep`으로 먼저 잔다.

### 5.4 지키지 않은 약속

`together` 칸 시작부터 30분 동안 사용자 말이 하나도 없으면 그 칸을 `missed`로 표시한다(규칙).

- **기다리다 잠든다.** 오늘 밤 잠 칸의 시작이 그 약속 시각보다 뒤면(약속 때문에 늦췄으면) 시작을 지금으로 당긴다. 사용자가 없으니 HIMARI가 정할 턴이 없어서, 몸이 잠드는 것으로 규칙이 한다. reason은 "약속을 기다리다 잠듦"이고 잠 기록의 방법은 `missed`이다.
- **기록이 남는다.** 그날 일기 입력, 다음 세션의 `himari_day.before`, 지금 일정표에 보인다. 서운해할지, 넘어갈지는 HIMARI가 말로 정한다.

### 5.5 깨우기

**셈.** 자는 중 사용자 메시지 하나가 1이다. 앱에서 자는 HIMARI를 클릭(쿡 찌르기)해도 1이다. 10분 동안 아무것도 없으면 셈이 0으로 돌아간다(다시 깊이 잠듦).

| 잠 | 1번째 | 2번째 | 3번째 |
| --- | --- | --- | --- |
| **깊은 잠**(잠든 뒤 3시간 안) | 무반응 | 잠꼬대 | 깸 |
| **얕은 잠** | 잠꼬대 | 깸 | — |

- **무반응:** 메시지는 대화에 남지만 Run이 없다. 앱의 HIMARI는 뒤척이기만 한다.
- **잠꼬대:** 반쯤 깬(`half_asleep`) 턴이다.
  - Current State에 반쯤 깼다고 적고 Tool은 주지 않는다. 짧게 웅얼거리는 한 줄을 낸다(규칙 `SLEEP_RULE`).
  - 잠꼬대는 잠을 끊지 않는다. 3시간 셈도 이어진다.
- **깸:** 보통 턴이다. 잠 기록에 "사용자가 깨움"으로 남는다. Current State에 "방금 깨어남(03:12, 잠든 지 2시간 10분)"을 넣는다. 억지로 깨운 것에 투덜거릴지는 HIMARI가 정한다.

### 5.6 자는 동안 온 말

- 자는 동안 온 메시지는 대화에 그대로 남고, "자는 동안 받음" 표시가 붙는다(Web에서 주인에게 보임, 모델에게는 시각 줄과 함께 그 표시).
- **깨워졌을 때:** 자기를 깨운 마지막 말에 잠이 덜 깬 채로 반응한다. 앞의 말들은 흐릿하게만 안다("…계속 불렀어요?").
- **아침에 저절로 깼을 때:** 밤사이 말에 하나하나 답할 의무가 없다. 다음 턴의 Current State가 "자는 동안 메시지 3개(02:10–02:14)"라고 알리고, 꺼낼지는 HIMARI가 정한다.
- 이 두 가지는 규칙 글(`SLEEP_RULE`)로 알린다. 코드는 메시지를 지우거나 숨기지 않는다.

## 6. 잠 정리

**조건:** 지난 정리 뒤에 시작한 한 번의 잠이 **깨지 않고 3시간**이 되었을 때다. 잠꼬대는 끊김이 아니다. 열린 하루 세션이 없으면(사용자가 오지 않은 날) 1·3을 건너뛰고 2·4만 한다.

- 사용자가 깨워 3시간을 못 채우면 정리하지 않고 그 하루가 이어진다.
- 다시 잠들어 3시간이 차면 그때 한다.
- **안전장치:** 지난 정리 뒤 36시간이 넘으면 조건이 1시간으로 줄어든다. 이틀 내리 깨워도 하루가 끝없이 길어지지 않게 하려는 것이다.
- 서버가 그때 꺼져 있었으면 다음 실행 때, 기록으로 조건이 찼는지 보고 한다.

**순서:** LLM이 없는 것을 먼저 한다.

1. **세션 닫기:** 지금 하루 세션을 닫고(읽기 전용), 넘길 것(§3.3)을 만든다. LLM 없음.
2. **다음 잠 칸 놓기:** 새 날짜의 밤 칸이 없으면 놓는다. LLM 없음.
3. **남은 기억 정리:** 닫힌 세션에서 아직 읽지 않은 부분을 기다리지 않고 바로 정리한다(9단계 기억 정리 그대로). 하루 중에는 지금처럼 대화가 10분 쉬면 조금씩 정리한다. 그래서 정리가 밀려도 기억을 잃지 않는다.
4. **세계 작가:** 새 날짜의 사건(9단계 §7)을 정한다. "조용한 시간이 끝난 뒤"를 바꾼다.

3·4가 실패하면 지금처럼 다음 회차에 다시 한다(삶 작업의 `ATTEMPTS_PER_DAY`, 기억 정리의 재시도).

**정리가 없었던 날**(3시간 잠이 없었음)에도 세계는 정오에 그날 사건을 정한다. 하루의 사건이 통째로 빠지지 않게 하려는 것이다.

## 7. 일기 (22:00)

지금 22:00 하루 돌아보기(9단계 §4.3)를 **하루 세션 문맥에서 쓰는 일기**로 바꾼다.

- **입력:** 하루 세션의 다음 턴 입력과 같다. 시스템 글, Current State, 그 세션의 대화 기록(압축되었으면 압축된 대로)이다. 거기에 맨 끝 사용자 차례로 `<diary>` 과제(지금의 `REVIEW_TASK`를 고침)가 붙는다.
  - 그날 실제로 나눈 말을 보며 쓰니 일화 요약(`episodes`)은 오늘 것을 뺀다.
  - 앞부분이 대화와 같아 프롬프트 캐시가 맞는다.
- **출력:** 지금과 같다. 생각, 그리고 JSON 하나(일기, 일정 0~3개, 기분, 줄거리 움직임)다. 일정은 일정표 칸(`own`, `work`, 끝 시각과 함께)이 된다.
- **대화에는 남기지 않는다.** 과제도 답도 세션 기록에 넣지 않고 삶 기록(`life_writes`)에만 남는다. Web의 그 세션 타임라인에는 주인에게만 "22:00 일기를 씀"이라는 접힌 줄로 보인다. 모델은 다음 턴부터 `himari_life.days`로 자기 일기를 안다.
- **Tool은 없다.** 잠 칸은 여기서 바꾸지 않는다.
- **때:**
  - 22:00(`HIMARI_LIFE_WRITE_AT`)이다. 대화가 한창이어도 뒤에서 돌고 대화를 끊지 않는다.
  - **22:00 전에 잠들면 잠들 때 쓴다.**
  - 하루 세션이 없는 날(사용자가 오지 않음)은 대화 기록 없이 지금처럼 쓴다.
- **정사 추리기**(9단계 §5.3)는 그대로 일기 뒤에 돈다.

## 8. 프롬프트

**runtime state.** 하루 세션에서만 들어간다.
- `himari_schedule`: 오늘과 내일의 칸. id, 시각, 길이, 종류, 글이 들어가고, 취소·놓침과 그 이유도 들어간다.
- `himari_sleep`: 지금 상태(`awake`·`drowsy`와 잠 칸까지 남은 분·`half_asleep`), 오늘 밤 잠 칸, 마지막 잠(잠든 때와 방법, 깬 때와 방법, 깨워진 횟수, 자는 동안 받은 메시지 수와 시각 범위).
- `himari_day.before`(§3.3): 새 세션의 첫 날 동안만.
- `himari_now`는 그대로다. `asleep`은 잠 상태에서 온다.

**규칙(반려 절, `LIFE_RULE` 뒤).**
- **`SCHEDULE_RULE`:** 일정표는 네 수첩이다.
  - 사용자와 시각을 정하면 `together`로 적는다.
  - 그 시각이 잠과 겹치면 잠을 옮긴다. 잠을 없앨 수는 없다.
  - 바꿀 때는 이유를 네 말로 쓴다.
  - 일정표를 읽어 주거나 Tool 이야기를 하지 않는다.
- **`SLEEP_RULE`:**
  - 졸리면(`drowsy`) 그게 말에 묻어난다. 잠 칸이 되면 잠든다. 더 깨어 있고 싶으면 이유와 함께 잠 칸을 옮긴다.
  - "잘 자" 같은 끝인사에는 `go_to_sleep`을 부른다.
  - 반쯤 깼으면 짧게 웅얼거리는 한 줄만 한다.
  - 깨어났으면 깨운 말에 반응하고 그 앞의 말은 흐릿하게만 안다.
  - 아침에는 밤사이 말에 하나하나 답하지 않아도 된다.
- **지금 규칙의 "자고 있으면 짧게, 막 깬 듯이"**(`LIFE_RULE`의 `himari_now` 문장)는 `SLEEP_RULE`로 옮긴다.

**하루 돌아보기 입력**의 `quiet_hours`는 "오늘 밤 잠 칸"으로 바꾼다.

## 9. 먼저 말 걸기

- **조용한 시간을 잠으로 바꾼다.** HIMARI가 자는 동안(`asleep`, `half_asleep`)에는 wake를 열지 않는다. 깨어 있으면 시각과 상관없이 지금 규칙(기기에 사용자가 있음, 간격, 하루 횟수)을 따른다.
  - **미리 알림(사용자가 부탁한 것)만은 자는 중에도 연다.** 알람에 깬 것처럼 반쯤 깬(`half_asleep`) 턴으로 말하고, 잠꼬대처럼 잠을 끊지 않는다.
  - 새벽 3시에 방송을 보며 깨어 있으면 먼저 말할 수 있다.
  - 사용자가 자고 있으면 기기 입력이 없으니 지금 규칙으로 걸러진다.
  - `HIMARI_PROACTIVE_QUIET`는 삶이 꺼졌을 때만 쓴다.
- **새 계기 `together`(약속 시각):** `together` 칸이 시작할 때 연다. 기기에 사용자가 있을 때만 연다. 미리 알림(reminder)처럼 간격과 하루 횟수를 넘는다. 다만 미리 알림과 달리 사용자의 조용히(`quiet_until`)는 넘지 않는다. 약속은 HIMARI 쪽에서 꺼내는 것이라서다. 사용자가 없으면 열지 않고, 30분 뒤 §5.4로 간다.
- 일어났다는 계기는 두지 않는다. 아침 인사는 지금의 자유 wake가 한다.

## 10. 모델

- **내놓는 모델은 둘이다.** `HIMARI_MODELS=deepseek/deepseek-v4.1-flash-1017=low,openai/gpt-6-luna`이다.
  - 기본(`HIMARI_MODEL`), 반려 기본, 기억 작업 모델이 모두 deepseek 1017이다. 지금 운영 기본 모델은 luna라 바뀐다.
  - 목록에서 빠진 모델을 고른 옛 대화는 지금 규칙대로 기본 모델로 돈다(`ResolvedModel.fallback`).
  - 코드의 모델 목록(`KNOWN_CAPABILITIES`)은 지우지 않는다. 되살리기 쉽게 하려는 것이다.
- **luna를 반려 모델로 켠다**(소유자 결정 2026-11-26). `companion=True`, `free_wake=True`로 켠다.
  - 떨어졌던 확인은 자유 wake의 "직전 wake 말 되풀이"(V3-P90 §7.5, 6번 중 4번) 하나다. 그 규칙과 wake 알고리즘은 이 단계와 그 뒤에 어차피 바뀐다.
  - 알려진 위험으로 적어 둔다.
- **예비 모델 `HIMARI_BACKUP_MODEL=openai/gpt-6-luna`(새 설정).** 모든 LLM 호출이 대상이다. 턴의 Run, wake, 잠꼬대, 일기, 작업, 기억 정리, 정사 추리기, 세계가 모두 들어간다.
  - **넘어가는 때:** 첫 모델이 **답을 하나도 내지 않고** 실패했을 때다(`NativeNoResponse`). 연결 실패, HTTP 408·429·5xx, 스트림 첫 바이트 전의 공급자 오류가 여기에 든다. 그때 같은 입력을 예비 모델로 다시 준비해 한 번 보낸다.
  - **넘어가지 않는 때:**
    - 답이 오다 끊긴 때(`NativeUncertain`)는 지금처럼 실패로 둔다. 이미 화면에 나간 글이 있을 수 있어서다.
    - HTTP 400·401·402·403도 넘기지 않는다. 우리 쪽 잘못이거나 계정 문제이고, 예비 모델도 같은 키를 쓴다.
    - 모양이 틀린 답도 넘기지 않는다. 그건 우리가 고칠 일이다.
  - **기록:** 대화가 고른 모델은 바꾸지 않는다. 실제로 답한 모델과 "예비"를 Run과 삶·기억 기록에 남긴다. Web의 Run 정보에 "예비 모델(luna)로 답함"이 보인다.
- **혼자 하는 호출의 모델**(9단계 §4.1 `mind_model`)은 **하루 세션의 모델**이다. "자유 wake로 확인된 모델이 아니면 기억 작업 모델"이라는 갈래는 없앤다.

## 11. Windows 앱

- **입력 없음으로 자는 것을 없앤다.** `SleepPolicy`는 남기되 뜻을 **사용자 자리 비움**(입력 없음, 잠금, 화면 꺼짐)으로 바꾼다.
  - 서버에 보내는 값은 그대로다(`sleep` 칸, 호환을 위해 이름 유지). 서버는 그것을 먼저 말 걸기와 화면 Tool의 "자리에 없음"에만 쓴다. 지금과 같다.
  - 자리 비움 동안 HIMARI는 자지 않고 지금 하는 일의 모습이나 평소 대기 동작을 한다.
- **HIMARI의 잠은 서버에서 온다.**
  - `GET /api/device`와 `hello`에 `himari: {sleep: "awake"|"drowsy"|"asleep"|"half_asleep"}`가 들어간다.
  - 바뀌면 스트림 이벤트 `himari_sleep`이 온다.
  - 앱은 이것으로 잠 애니메이션(하품, 잠)을 튼다.
- **자는 HIMARI를 클릭하면 쿡 찌르기**(`POST /api/device/poke`)다. 지금은 클릭하면 바로 깨는데, 이제 깨우기 셈 1이다(§5.5).
- **앱의 대화는 오늘의 하루 세션이다.**
  - "새 대화" 단추를 없앤다.
  - 서버가 세션을 바꾸면 스트림이 알리고 앱이 따라간다.
  - 지난 대화 창은 날짜별 하루 세션을 보여 준다.
- **다시 빌드해야 한다.** 옛 앱은 입력이 없으면 여전히 자는 모습을 보인다. 서버 쪽 잠과는 따로라 해롭지는 않다.

## 12. Web

- **대화 목록:** 하루 세션은 날짜 제목과 "하루" 표시를 단다. 닫힌 세션은 입력란을 막는다.
- **자는 동안 받은 메시지:** "자는 동안" 표시를 단다(주인만). 잠꼬대 답은 보통 답처럼 보인다.
- **22:00 일기:** 그 세션 타임라인에 접힌 줄로 보인다(주인만, §7).
- **Settings → HIMARI → 일정표(새):**
  - 오늘부터 7일의 칸을 종류별로 보여 준다. 고치고 지울 수 있고, 잠 칸은 옮기기만 된다.
  - 취소·놓친 칸과 이유도 보인다.
  - 아래에 **잠 기록**(최근 14번: 잠든 때와 방법, 깬 때와 방법, 메시지와 잠꼬대 수, 정리했는지)을 둔다.
- **모델 고르기:** 둘만 나온다.
- 지금 Settings → HIMARI의 일정(`plan`) 묶음은 일정표로 옮긴다.

**층.**
- 잠과 일정표의 순수 규칙(잠 칸 놓기, 상태 넘기기, 깨우기 셈, 정리 조건, 한계)은 `life/day.py`(새, LLM·입출력 없음)에 둔다.
- 잠 정리와 일기는 `life/worker.py`가 돈다.
- 메시지를 받을 때 잠을 보는 것은 Driver가 Data에서 잠 상태를 읽어 한다.
- Tool은 `tool/schedule.py`(새)이다.
- 예비 모델은 Run과 삶·기억 작업이 공급자를 부르는 자리에서 하나의 도움 함수로 한다.
- 세부는 구현 계약에서 정한다(9단계 §14처럼, 구현 전).

**스키마 v29(예정).**
- `life_entries`에 `minutes`, `plan_kind`, `plan_state`, `reason`을 더한다.
- `conversations`에 `day_session`(연 날짜), `closed_at`을 더한다.
- 새 표 `sleeps`(잠 기록)와 지금 잠 상태를 둔다.
- 사용자 메시지에 "자는 동안 받음" 표시를 둔다.
- Run, 삶 기록, 기억 정리에 실제로 답한 모델을 둔다.
- 있는 `plan` 행은 `arc_id`가 있으면 `work`, 없으면 `own`이고, 모두 60분이다.

## 14. 비용

- **하루 세션:** 대화 기록이 하루만큼만 쌓이므로, 몇 주짜리 대화를 압축하며 잇던 지금보다 줄거나 같다.
- **일기:** 그날 세션 길이만큼 입력이 늘지만 앞부분이 캐시된다. deepseek 1017 기준으로 하루 몇 센트 안이다.
- **잠꼬대:** 짧은 답 하나다. 밤에 깨울 때만 생긴다.
- **일정표 Tool:** 대화 중 가끔이다. Tool 설명이 시스템 글에 더해지지만 캐시된다.
- **예비 모델:** 실패할 때만 돈다.

## 15. 하지 않는 것(v0.1)

- **꿈, 낮잠.** 잠 칸은 밤에 하나다.
- **일어날 때 먼저 말 걸기.** 지금의 자유 wake에 맡긴다.
- **Web 다른 대화의 잠.** 하루 세션에만 잠 규칙이 있다(D6).
- **세계가 일정표를 고치기.** 세계는 사건만 정하고, 일정은 HIMARI가 바꾼다.
- **사용자의 수면 추정**(기기 입력으로 "사용자가 잔다"를 아는 것).
- **luna 실제 모델 확인.** 소유자 결정으로 표시를 켜고, 써 보며 본다.
- **잠 깊이의 연속값**(점수가 시간에 따라 줄어드는 모형). 셈과 두 깊이로 시작한다.

## 18. 구현 계약 (구현 전에 정한 것, 2026-11-26)

코드를 읽고 설계를 자리에 맞췄다. 구현이 이것과 다르게 가야 하면 §19에 적고 바꾼다.

### 18.1 층

- 새 패키지는 만들지 않는다. 다른 패키지는 `himari.<pkg>.api`와 `common`만 import하므로(층 규칙), **여러 곳이 쓰는 타입**(잠 상태, 메시지 답 방식, 일정 칸 종류)은 `data/api.py`에 둔다.
- **잠과 일정표의 순수 규칙**은 `life/day.py`(새것, 입출력 없음)이다. 기본 잠 칸 놓기, 잠 상태 계산, 깨우기 셈, 정리 조건, 약속 놓침이 여기 있다.
- **일정표 한계 검사**는 Data가 쓸 때 한다(`data/rules.py`, Data 안쪽). Tool, Web, 삶 작업, 하루 지기가 모두 Data를 거쳐 쓰므로 한 곳에서 막힌다. 거부는 `DataError`이고 메시지는 모델이 읽고 고칠 수 있는 영어 한 문장이다.
- **하루 지기**(`life/keeper.py`의 `DayKeeper`, 새것)가 상태를 넘긴다. 잠들기와 일어나기, 칸 놓기, 약속 놓침, 정리 시작을 맡는다. `bootstrap`이 붙인다.
  - Control은 `life`를 import할 수 없다. 그래서 Driver는 `control/api.py`의 포트 `DayGate`(Protocol)로만 묻고, `bootstrap`이 `DayKeeper`로 채운다. 9단계 `MindLink`와 같은 방식이다.
  - 먼저 말 걸기 규칙(`proactive`, 순수)은 `Situation`에 들어온 값만 본다.

### 18.3 순수 규칙 (`life/day.py`)

- `place_sleep(night, rng) -> (time_of_day, minutes)`: 23:00–02:00 10분 단위, 끝 07:00–10:00, 시작 + 5시간보다 이르면 그때, 끝 12:00 상한.
- `sleep_view(now, slot, sleep, state) -> SleepView`(`data/api.py` 타입). 상태(`awake`·`drowsy`·`asleep`·`half_asleep`), 깊은 잠인지, 잠 칸까지 남은 분, 오늘 밤 칸, 마지막 잠 요약, 자는 동안 받은 메시지 수와 시각 범위가 들어간다.
- `answer_message(view, sleep, now) -> AsleepAnswer | None`: 깨어 있으면 `None`. 아니면 §5.5 표(깊은 잠 3, 얕은 잠 2, 10분 초기화)를 따른다. 쿡 찌르기도 같은 셈이다.
- `due(now, slot, sleep, state, running) -> list[Transition]`: 다음을 낸다.
  - 잠들기: 칸 시작, Tool, 약속 놓침. 일이 돌고 있으면(`running`) 기다린다.
  - 칸 끝의 일어나기.
  - 깨운 뒤 20분 조용하면 다시 잠들기.
  - 칸 끝까지 1시간 안에 깨우면 그날 일어나기(칸 끝을 지금으로).
  - 약속 놓침.
  - 정리 시작(깨지 않은 3시간, 지난 정리 뒤 36시간이면 1시간).
- 모두 시계와 난수를 인자로 받는다.

### 18.4 Control

- **`DayGate`**(포트):
  - `answer(scope, origin) -> AsleepAnswer | None`: 하루 세션이 아니면 `None`. 메시지를 받을 때 셈을 기록하고 답 방식을 돌려준다.
  - `view(scope) -> SleepView | None`: 턴의 Current State용.
  - `day_session(scope) -> bool`.
- **메시지 받기**(`runner.submit` → `driver.accept`):
  - 답 방식이 `none`이면 메시지를 `while_asleep=none`으로 기록하고 **일을 시작하지 않는다.** `JobStatus`는 지금 닫힌 대화에서 받은 입력처럼 "받았고 답 없음"이다.
  - `mumble`이면 반쯤 깬 턴이다. Run은 1번이고 Tool은 없다.
  - `wake`면 보통 턴이다.
  - 답 없는 사용자 메시지가 이어지는 대화 기록은 지금도 생기는 모양이다(닫힌 대화에서 받은 입력). Composer가 그대로 그린다.
- **`RequestOptions`**:
  - `day_session: bool`. 참이면 `capabilities`에 `"day_session"`이 들어가고, 일정표 Tool은 `requires="day_session"`이다.
  - `half_asleep: bool`. 참이면 Tool 목록이 비고 `SLEEP_RULE`의 반쯤 깬 문장이 적용된다.
- **Tool 문맥**의 `persona_id`는 9단계처럼 Driver가 넣는다.
- **예비 모델**(§10): `_run_loop`에서 `NativeNoResponse`이고 `retryable(error_code)`이면 그 턴의 남은 Run을 예비 모델로 한다. 단 예비 모델이 설정되어 있고, 지금 모델이 예비 모델이 아니고, 이 턴에서 아직 넘어가지 않았을 때만이다.
  - 실패한 Run은 지금처럼 기록에 남는다.
  - 예비 모델은 내놓은 모델(`ModelCatalog`)에 있어야 한다.
  - `retryable`은 `provider/api.py`의 순수 함수다. `connect_failed:*`, `http_408`, `http_429`, `http_5xx`, `provider_error_*`가 참이다.
- 하루 세션의 닫힌 대화에 온 메시지는 Application이 거부한다(`409 day_closed`).

### 18.5 Prompt

- `PromptInputs`에 `schedule: tuple[LifeEntry, ...] | None`(오늘·내일, 취소·놓침 포함), `sleep: SleepView | None`, `day_before: DayBefore | None`을 더한다. 모두 하루 세션에서만 채운다.
- runtime state에 `himari_schedule`, `himari_sleep`, `himari_day`(`before`)를 둔다. `himari_now.asleep`은 `SleepView`에서 온다. 하루 세션이 아니면 `asleep`이 없다.
- 시스템 글: `SCHEDULE_RULE`, `SLEEP_RULE`은 반려 절의 `LIFE_RULE` 다음에 두고, `day_session`일 때만 넣는다. `LIFE_RULE`의 "asleep이면 짧게, 막 깬 듯이" 문장은 `SLEEP_RULE`로 옮긴다.
- 자는 동안 받은 사용자 메시지는 시각 줄을 늘 달고, 그 줄에 "(while you slept)"를 붙인다. `TIME_NOTE`에 한 구절을 더한다.
- 일기 입력: `SelfComposer.session_input(inputs, task, data)`. 하루 세션의 다음 턴 입력(대화 기록과 압축 요약 포함, Tool 없음) 맨 끝에 일기 과제와 자료를 사용자 차례로 붙인다.

### 18.6 Tool (`tool/schedule.py`, 새것)

- `schedule_read`, `schedule_write`, `schedule_cancel`, `go_to_sleep`이다(§4.3). 모두 `requires="day_session"`이고 `persona_id`가 없으면 거부한다.
- 쓰기는 지금 Tool처럼 `ToolOutcome`의 효과로 Data에 간다. `origin=himari`이다.
- 하루 20번 한도는 `origin=himari`로 오늘(사용자 자정부터) 고쳐진 칸의 수로 센다.
- `go_to_sleep`은 두 가지를 한다. 오늘 밤 칸의 시작을 지금(10분 단위로 올림)으로 옮기고, `day_state.sleep_requested_at`을 쓴다. 하루 지기는 그 턴의 일이 끝나면 잠들게 한다(`how_fell=tool`).

| `life/work.py` | 작업 시간 = 칸의 `minutes`(없으면 60). `WORK_MINUTES`는 기본값으로만 남는다 |
| `life/review.py` | 입력의 `quiet_hours` → `sleep`(오늘 밤 칸). 일정 답에 `minutes`(선택, 기본 60)를 받는다. 잠 칸과 겹치는 일정은 **그 일정만** 버리고 기록한다(답 전체를 버리지 않음). 세션 문맥이면 오늘의 `episodes`를 뺀다 |

- **일기 때**(`write_at` 22:00): 그 시각 전에 잠들었으면 잠들 때다. 하루 지기가 잠들기를 적용하면서 `worker.write(principal)`을 깨운다.
- **일기 입력:** `MindLink.session_input(principal)`(새것, `bootstrap`)이 하루 세션의 다음 턴 입력을 준다. Driver에 `turn_inputs(scope) -> PromptInputs`(다음 턴이 볼 것, 예산 맞추기 전)를 열어 그것을 쓴다.
  - 하루 세션이 없거나, 입력이 모델 문맥 예산을 넘거나, 실패하면 지금처럼 대화 기록 없는 혼자 하는 호출로 쓴다.
  - 쓴 세션은 `life_writes.conversation_id`에 남는다.
- **혼자 하는 호출의 모델:** `mind_model`은 하루 세션의 모델이다. 하루 세션이 없으면 기본 모델이다. 자유 wake 갈래는 없앤다.
- **예비 모델:** 같은 일·날짜(작업은 칸)의 바로 앞 시도가 답 없이 끝났고 `retryable`이면, 이번 시도는 예비 모델로 한다. 다음 회차(10분)에 넘어간다.

### 18.8 Memory

- 닫힌 하루 세션은 조용한 시간(10분)을 기다리지 않고 바로 정리 대상이다(`memory_due`에 `closed_at`).
- 예비 모델은 삶 작업과 같은 방식이다(바로 앞 시도가 답 없이 끝났으면 예비).
- 잠꼬대 답과 자는 동안 받은 메시지도 지금처럼 입력에 들어간다. 다른 처리는 없다.

### 18.9 먼저 말 걸기

- `Situation.himari_asleep: bool | None`. `None`이면 삶이 꺼진 것이고 조용한 시간을 쓴다. 참이면 `REMINDER` 말고는 `himari_asleep`으로 막는다.
- **`REMINDER`는 자는 중에도 연다.** 그 wake 턴은 `half_asleep`이고 잠을 끊지 않는다.
- **`WakeKind.TOGETHER`**(새 계기): `together` 칸이 시작한 지 10분 안이고 그 칸의 wake가 아직 없을 때 연다. 키는 `together:<entry_id>`이다.
  - 막는 것: 기기, 일, 기기 자리 비움, 사용자 조용히, 말하는 중(`TALKING`, 이미 와 있음).
  - 간격, 하루 횟수, 답 없는 wake로는 막지 않는다.
- **wake가 가는 대화**는 하루 세션이다(없으면 연다). `recent_companion_conversation`을 쓰던 곳(`scheduler recent`, `mind_model`, `remarks`, `try_wake`, `device_state`)을 모두 바꾼다.

### 18.10 Bootstrap과 설정

- `Application.day_session(principal, *, open=True)`: 열린 하루 세션, 없으면 연다. 제목은 "11월 27일 (금)"이다. 반려 기본 모델을 쓰는 대화로 만든다.
- `DayKeeper`를 붙인다. ticker `day`(60초), runner의 일 끝 리스너가 그 사람을 다시 보게 한다. 정리 콜백은 기억 정리 깨우기와 삶 작업 깨우기다.
- **스트림 이벤트**(Web과 기기 모두): `himari_sleep {sleep}`, `day_session {conversation, title, closed}`.
- **`HIMARI_BACKUP_MODEL`**(새 설정): `HIMARI_MODELS`에 있어야 한다. 없으면 시작을 거부한다. 비우면 예비 없음이다.
- `openai/gpt-6-luna`의 능력에 `companion=True`, `free_wake=True`를 켠다(소유자 결정 2026-11-26).
- 운영 설정(배포 때)은 이렇게 바꾼다.
  - `HIMARI_MODEL=deepseek/deepseek-v4.1-flash-1017`
  - `HIMARI_MODELS=deepseek/deepseek-v4.1-flash-1017=low,openai/gpt-6-luna`
  - `HIMARI_BACKUP_MODEL=openai/gpt-6-luna`
  - 기억 작업 모델과 반려 기본 모델은 그대로 둔다.

### 18.11 Web API

| 자리 | 바꿈 |
| --- | --- |
| `GET /api/conversations` | 항목에 `day_session`(날짜 또는 null), `closed`(bool) |
| `POST /api/conversations/{id}/messages` | 닫힌 하루 세션이면 `409 day_closed`. 답 없이 받은 메시지는 `202`에 `{"asleep": "none"}` |

### 18.12 Web 화면

- **대화 목록:** 하루 세션에 날짜 제목과 "하루" 표시를 단다. 닫힌 세션은 입력란을 막고 "닫힌 하루"라고 보인다.
- **타임라인:** 사용자 메시지의 "자는 동안"(잠꼬대·깨움·답 없음을 구분), 접힌 "일기를 씀" 줄을 보인다.
- **Settings → HIMARI:**
  - 일정 묶음을 **일정표**로 바꾼다. 7일, 종류 표시, 시작과 길이, 취소·놓침과 이유, 쓰기·고치기·지우기를 둔다. 잠 칸은 옮기기만 된다.
  - 그 아래에 **잠 기록**을 둔다.
  - 지금 상태 줄에 `SleepView`를 보인다.
- 스트림 `himari_sleep`, `day_session`을 받아 다시 읽는다.

### 18.13 Windows 앱

- `SleepPolicy`는 자리 비움만 계산하고 서버에 지금처럼 보낸다. 캐릭터 애니메이션의 잠(`SetSleeping`)은 서버의 `himari.sleep`(`asleep`·`half_asleep`)으로만 켠다. `drowsy`면 가끔 하품한다.
- 서버가 `features.day_session`을 말하지 않으면 지금 동작 그대로다(옛 서버).
- 자는 HIMARI를 클릭하면 `POST /api/device/poke`다. 자리 비움을 푸는 동작(`WakeNow`)은 그대로 한다.
- "새 대화" 단추를 숨긴다(`day_session`일 때). 대화는 `recent_conversation`과 `day_session` 이벤트를 따른다.
- 계약 시험(`Himari.Companion.ContractTests`)을 고친다.

### 18.14 구현 순서

서버(Python, Web API 포함)와 화면(Web, Windows)을 두 갈래로 나눈다. 화면 갈래는 §18.11의 모양에 맞춰 만들고, 서버 갈래에 합친다. 단계마다 전체 시험을 돌린다.

1. **Data v29**와 타입, 일정표 한계(`data/rules.py`), In-memory 저장소.
2. **순수 규칙** `life/day.py`와 시험.
3. **일정표 Tool**, `RequestOptions.day_session`, Prompt(`himari_schedule`·`himari_sleep`·규칙).
4. **하루 세션과 잠:** `DayKeeper`, `DayGate`, 메시지 받기의 답 방식, 반쯤 깬 턴, 쿡 찌르기, 스트림, 하루 세션으로 바꾼 wake와 기기.
5. **삶:** 세션 문맥 일기, 세계 때, 작업 길이, 하루 돌아보기 일정, 기억 정리의 닫힌 세션, 먼저 말 걸기(`himari_asleep`, `TOGETHER`, 자는 중 미리 알림).
6. **모델:** `retryable`, Driver와 삶·기억의 예비 모델, `HIMARI_BACKUP_MODEL`, luna 능력.
7. **Web API** 마무리.
8. (화면 갈래) **Web 화면, Windows 앱.**
9. 실제 모델 확인(§16), 문서(이 문서 §19, 결정 기록, 로드맵, status).

## 19. 구현에서 정한 것

### 19.x 화면 갈래

Web과 Windows 앱(§18.12, §18.13)을 만들며 정한 것이다. 서버와 합칠 때 API 모양을 맞춘다.

- **Web 글은 영어다**(9단계의 "Thought"처럼). 하루 → `Day` 표시, 닫힌 하루 → 입력란 자리에 "A closed day: read only. …", 자는 동안 → 사용자 말 아래 `While asleep · no answer`/`· mumbled`/`· woke HIMARI`, 일기 → 접힌 줄 `Wrote the diary · <시각>`(펼치면 일기 글), 일정표 → `Schedule`, 잠 기록 → `Sleep log`.
- **일정표 모양:** 서버가 준 일정을 날짜별로 묶어 이른 날부터, 날 안에서는 시작 순으로 보인다(지난 날짜의 취소·놓친 칸도 그대로). 빈 날은 제목을 두지 않는다. 날 제목은 `YYYY-MM-DD`와 today/tomorrow.
- **고치기 범위:** 새 칸의 종류는 `own`·`together`, 열린 프로젝트가 있으면 `work`(프로젝트를 고름)다. `sleep`은 새로 쓰지 않는다. 잠 칸은 날짜·시작·길이만 옮기고(단추 "Move", 지우기 없음), 작업 칸은 종류와 프로젝트가 그대로, 나머지는 `own`↔`together`만 바꾼다. 취소·놓친 칸은 고치지 않고 지우기만 된다. `reason`은 Web에서 쓰지 않는다.
- **지금 상태 줄:** `Sleep: Awake · sleeps at 23:30` / `Drowsy · sleeps in 20 min` / `Asleep (deep) · wakes at 07:10` / `Half asleep`. `himari_now.asleep`의 "Asleep"은 `sleep`이 없을 때만 보인다.
- **예비 모델 표시**(§10 "예비 모델(luna)로 답함")는 §18.12에 없어 Web에 따로 두지 않았다. Run의 `model`에 실제 모델이 남는다.
- **Web이 읽는 모양(§18.11에서 열려 있던 것):**
  - `GET /api/life`의 `sleep`: `{state, deep?, minutes_to_sleep?, tonight?: {day, time, minutes}}`. `sleeps[]`: `{fell_at, how_fell, woke_at, how_woke, messages, mumbles, closed_day}`(최신 먼저).
  - `POST /api/life/plans`: `{day, time, minutes, plan_kind, text, arc_id?, persona_id}`. `PUT /api/life/plans/{id}`: 같은 칸에 `revision`(`persona_id` 없음). 거부는 `409 plan_refused`, 그 밖에 `revision_conflict`, `persona_changed`도 지금 삶 항목처럼 읽는다.
  - 대화 이벤트의 `diary`: `{sequence, kind: "diary", created_at, text}`(`text`는 일기 글).
  - 스트림(`/api/events`) `himari_sleep`이 오면 삶을, `day_session`이 오면 목록·그 대화·삶을 다시 읽는다.
- **Windows 졸림:** `drowsy`면 평소 잔동작(30–90초 간격) 자리에 하품을 넣는다.
- **Windows 쿡 찌르기:** 클릭은 쿡 찌르기와 함께 평소처럼 입력창도 연다. 답이 `none`이면 잠 동작을 처음부터 다시 틀어 뒤척임을 보인다(따로 그림 없음). `mumble`·`wake`는 서버의 작업과 `himari_sleep`으로 보인다.
- **Windows 하루 세션 따라가기:** 새 세션(`day_session`, `closed: false`)으로는 지금 대화가 없거나 닫힌 하루면 늘 옮기고(초안도 함께), 사용자가 고른 다른 대화면 입력 중이 아닐 때만 옮긴다. `hello` 때는 지금 대화가 닫힌 하루이거나 목록에 없던 하루 세션이면 옮긴다.
- **Windows 닫힌 하루에 보내기:** 먼저 `GET /api/device`로 오늘 세션을 연다(그 호출이 세션을 연다고 봄). 그 사이 닫혀 `409 day_closed`면 기록되지 않은 것으로 보고 글을 입력창에 되돌린 뒤 오늘 대화로 옮긴다. 자동으로 다시 보내지 않는다.
- **Windows 상태 글:** 하루 세션 서버에서는 답하는 중의 "새 대화를 열 수 있습니다"를 "히마리가 답하는 중이에요."로 바꿨다.
- **Windows 앱은 이 환경에 .NET SDK가 없어 빌드·실행하지 않고 썼다.** 계약 시험(`DaySession`, `CharacterAnimator`의 졸림·뒤척임, `day_closed` 분류)을 더했다. 빌드와 실기 확인이 남았다.
