## 1. 목표와 범위

- **작업 콘솔을 앱으로:** v3 Web의 작업 콘솔(V3-P102)을 브라우저 탭이 아니라 기기의 앱 창으로 쓴다(WebView2). 브라우저로 여는 것도 그대로 된다.
- **hub 실행기를 앱에서 켜고 끈다:** 기본은 **앱을 켜면 실행기도 켜지고, 앱을 정상 종료하면 앱이 켠 실행기도 꺼진다**. 묶이지 않게 끌 수 있다. 앱이 비정상 종료하면 실행기는 남는다(§5.5).
- **반려 앱과는 따로(소유자 2026-11-18):** 반려 앱(V3-P83, 캐릭터·말 걸기·화면)은 다른 개념으로 두고, 나중에 가능하면 합친다. 그래서 이 앱은 합치기 쉬운 모양으로 만든다(§8).
- **범위 밖:** Windows 밖(macOS·Linux 데스크톱), 앱 설치 꾸러미와 자동 업데이트, hub 자체를 실행 파일 하나로 묶기, 기기 등록(`runner setup`)·터널 설정을 앱에서 하기, 실행기 확인 창(hub `local` 방식의 tkinter 창)을 이 앱으로 옮기기(모두 나중).

## 2. 지금

- 반려 앱 `clients/windows/Himari.Companion`: .NET 10 WPF(+ WinForms 트레이), WebView2(답변 읽기 창, 데이터 폴더 `%LOCALAPPDATA%\HIMARI\reader`), 설정 `%LOCALAPPDATA%\HIMARI\window.json`, 기기 토큰은 Windows 자격 증명 관리자.
- hub 실행기(hub 홈마다 하나): `himari-hub runner start`(창 없는 백그라운드, 기록 `<hub 홈>\runner.log`), `runner stop`(`runner.stop` 파일을 두고 최대 105초 기다린 뒤 처음 읽은 pid를 강제 종료: 실행기가 맡은 작업을 끝내고 결과를 보내는 데 `RUNNER_STOP` 90초, 여유 15초). **떠 있는지의 기준은 `runner.lock`**(hub `background.running`: 잠금을 잡을 수 없으면 떠 있음), `runner.pid`는 그 프로세스가 누구인지를 알릴 뿐이고 잠금을 잡은 직후에는 아직 없거나 이전 값일 수 있다. hub는 로그인 시 자동 시작을 2026-11-16에 빼고 "통합 기기 앱이 `runner start`를 부른다"로 남겼다(hub `f4e3b49`).
- 지금 hub의 `start`·`stop`은 앱이 쓰기에 모자라다: `start`는 15초 안에 잠금을 못 보면 런처의 pid를 돌려주고, 동시에 두 번 부르면 한쪽이 다른 쪽 실행기의 pid를 받을 수 있다. `stop`은 그때 떠 있는 실행기에 멈춤을 요청하므로 확인과 요청 사이에 실행기가 바뀌면 다른 것을 끈다. 새 실행기는 시작할 때 남아 있던 `runner.stop`을 지워 막 보낸 요청을 잃을 수 있다. 상태를 묻는 `running()` 자체가 잠금을 잠깐 잡으므로 그 순간 시작하는 실행기가 "이미 떠 있음"으로 끝날 수 있다. → §9의 H9·H10·H14·H15·H16으로 고친다.
- hub 홈은 `HIMARI_HUB_HOME` 또는 `%USERPROFILE%\.himari-hub`. 이 PC(laptop)에서는 저장소 폴더에서 `uv run himari-hub …`로 돈다.

## 3. 앱 구성

새 프로젝트 `clients/windows/Himari.Workbench`(WinExe, `net10.0-windows10.0.17763.0`, WPF + WebView2, 반려 앱과 같은 판).

| 부분 | 하는 일 | 화면 의존 |
| --- | --- | --- |
| `RunnerSupervisor` | 실행기 상태 읽기, 켜기·끄기(한 번에 하나), 앱이 켠 인스턴스 기억 | 없음(합칠 때 그대로 옮김) |
| `WorkbenchSettings` | `%LOCALAPPDATA%\HIMARI\workbench.json` 읽기·쓰기 | 없음 |

| `SettingsWindow` | 서버 주소, hub 명령·홈, 연동, 로그인 시 시작 | WPF |

- **사용자마다 하나(모든 로그온 세션을 통틀어):** 이름 붙은 Mutex `Global\HIMARI.Workbench.<사용자 SID>`(현재 사용자만 열 수 있는 ACL). 이 Mutex를 쥔 프로세스만 `workbench.json`을 쓰고 실행기를 관리한다. 그래서 설정 쓰기와 소유권(`owned_instance`·`pending_instance`)은 한 프로세스 안에서만 바뀌고, 세션 사이의 경합이 없다.
- **두 번째 실행:** 같은 세션이면 이름 붙은 파이프 `HIMARI.Workbench.<SID>`(현재 사용자만, 받는 말은 "창 보이기" 하나)로 첫 앱에 창을 보이게 하고 끝난다. 첫 앱이 다른 Windows 세션(원격 데스크톱 등)에 있으면 창을 옮길 수 없으므로 "다른 Windows 세션에서 이미 켜져 있습니다"를 보이고 끝난다. 첫 앱이 답하지 않으면(5초) "이미 켜져 있지만 답하지 않습니다".
- **창을 닫으면 트레이로:** 창의 X는 숨김. 앱 종료는 트레이의 "종료"(또는 Windows 로그오프·종료). 처음 숨길 때 한 번 "트레이에서 계속 돕니다"를 알린다.

## 4. 작업 콘솔 창

- WebView2가 설정의 **서버 주소**(`https://…`, 반려 앱과 같은 서버)를 연다. 데이터 폴더는 `%LOCALAPPDATA%\HIMARI\workbench\webview`(반려 앱의 읽기 창과 나눔). 로그인은 지금의 운영자 로그인 그대로이고 쿠키는 이 데이터 폴더에만 남는다.
- **출처 비교:** 서버 주소와 이동할 URI를 `Uri`로 파싱해 scheme·host(소문자, IDN은 punycode)·port(기본 포트 채움)를 비교한다. 문자열 앞부분 비교는 쓰지 않는다.
- **이동 제한:** 최상위 이동(`NavigationStarting`, 리디렉션 포함 `IsRedirected`)과 프레임 이동(`FrameNavigationStarting`)은 서버와 같은 출처만 허용하고 나머지는 취소한다. `NewWindowRequested`(링크의 `target=_blank`, `window.open`)는 늘 앱 안에 새 창을 열지 않고 처리한다:
  - 같은 출처: 지금 창에서 연다.
  - 다른 출처이고 scheme이 `https`이고 **사용자 동작으로 생긴 요청**(`NewWindowRequestedEventArgs.IsUserInitiated`)일 때만: 기본 브라우저로 넘긴다(`Process.Start` + `UseShellExecute`, 넘기기 전에 다시 파싱한 절대 `https` URI만). 사용자 동작이 아닌 `window.open`은 막는다. 넘기기는 2초에 한 번까지(반복 팝업 막기).
  - 그 밖(`http`, `file:`, `ms-*:`, 사용자 프로토콜 등): 막고 상태 줄에 "열지 않음: <scheme>"을 잠깐 보인다.
  - 이동 취소된 최상위 다른 출처 `https`도 같은 규칙으로 기본 브라우저에 넘긴다(사용자가 누른 링크일 때만: `NavigationStarting.IsUserInitiated`).
- **서버 주소의 scheme:** `https`만. loopback `http://127.0.0.1`·`localhost`는 설정의 "개발자 모드"에서만 받는다.
- **권한:** 카메라·마이크·위치·알림 등 WebView2 권한 요청은 모두 거절한다(작업 콘솔은 쓰지 않음). 파일 고르기(첨부)와 내려받기는 WebView2 기본 동작 그대로.
- **인증서 오류는 넘기지 않는다**(`ServerCertificateErrorDetected`를 허용하지 않음). 사설 인증서를 쓰면 Windows 인증서 저장소에 넣어야 한다고 설정에 적는다.
- 개발자 도구와 기본 오른쪽 메뉴의 "검사"는 꺼 둔다(개발자 모드에서만 켬).
- **WebView2 Runtime이 없으면:** 창 자리에 "WebView2 Runtime이 필요합니다"와 설치 안내 링크(기본 브라우저로)를 보인다. 실행기 관리(상태 줄, 트레이)는 그대로 된다.

## 5. 실행기 관리

### 5.1 hub 명령과 홈

- **hub 명령:** 설정의 실행 파일(절대 경로) + 인자 목록 + 작업 폴더. 처음 켤 때 설정 마법사가 정한다(§5.6). 기본은 `uv`(그때 `PATH`에서 찾아 **절대 경로로 저장**) + `["run", "--project", "<hub 폴더>", "himari-hub"]`, 작업 폴더는 hub 폴더. 로그인 시 자동 시작처럼 `PATH`가 다른 환경에서도 같게 돌도록 실행 때마다 `PATH`를 찾지 않는다.
- 명령은 셸을 거치지 않고 인자 목록으로 실행한다(`ProcessStartInfo.ArgumentList`, `UseShellExecute = false`, `CreateNoWindow`). 사용자 입력을 명령 문자열로 이어 붙이지 않는다.
- **설정은 신뢰하는 로컬 입력이다:** hub 명령의 실행 파일은 이 앱이 그대로 실행하는 임의 프로그램이다. 설정 파일은 사용자 프로필 아래(`%LOCALAPPDATA%`)에 있어 그 사용자와 관리자만 바꿀 수 있고, 이 앱은 Web·서버·다른 프로세스로부터 설정을 받지 않는다. 설정 창은 실행 파일·인자·작업 폴더·hub 홈을 늘 전부 보이고, 실행 파일이나 hub 홈을 바꾸면 확인을 받는다. 앱이 켠 실행기가 떠 있는 동안 hub 홈이나 명령을 바꾸려면 먼저 끄게 한다(다른 홈의 실행기를 잃지 않게).
- **hub 홈:** 기본 `%USERPROFILE%\.himari-hub`, 설정에서 바꿀 수 있다. 앱 하나는 hub 홈 하나만 관리한다. 바꾸면 실행할 때 `HIMARI_HUB_HOME`으로 넘긴다.
- **비밀:** 이 앱은 hub의 토큰(`runner.token` 등)을 읽지 않고, 토큰을 인자·환경 변수·설정에 넣지 않는다(hub는 홈의 파일에서 스스로 읽음). 읽는 hub 파일은 상태 파일(H9)과, 사용자가 "기록"을 누를 때 기본 편집기로 여는 `runner.log`뿐이다.
- **오류 출력:** hub 명령이 실패하면 표준 오류의 마지막 줄을 200자까지 보인다. hub는 출력에 토큰을 쓰지 않지만(hub 원칙), 앱은 보이기 전에 `Bearer `·`token=`·`Authorization` 뒤의 값을 `…`로 가린다. 앱의 기록(`%LOCALAPPDATA%\HIMARI\workbench\workbench.log`)에는 명령의 종료 코드와 이 가린 줄만 남긴다.

### 5.2 상태

상태 줄에 보이는 것과 켜고 끄는 결정을 나눈다.

- **보이기(자주, 파일만):** 5초마다(창이 보이면 2초마다) 상태 파일 `<hub 홈>\runner.state.json`(H9)을 읽는다. 파이썬을 띄우지 않는다. 잠금 파일은 건드리지 않는다.
- **결정(드물게, hub에게 물음):** 켜기·끄기 전, 앱이 켜질 때, 상태 파일이 오래됐거나 깨졌을 때 `<hub 명령> runner status --json`(H14)을 부른다. 이것이 기준이다. H14는 잠금과 인스턴스가 같은 실행기의 것인지 확인한 뒤에만 인스턴스를 돌려준다(§9). 확인하지 못하면 `running: true, instance: null`이고, 앱은 이것을 "떠 있음 · 누구인지 모름"으로 보이며 자동 동작을 하지 않는다.

| 상태 | 판단 |
| --- | --- |
| 꺼짐 | `status`: `running: false` |
| 켜는 중 | 이 앱의 `runner start`가 아직 끝나지 않음 |
| 떠 있음 · 연결됨 / 연결 안 됨 | 상태 파일이 새것(`updated_at`이 15초 안)이고 `instance`가 마지막 `status`의 인스턴스와 같음 → 그 `connected` |
| 떠 있음 · 연결 모름 | `status`는 떠 있다고 하지만 상태 파일이 없거나, 오래됐거나, 깨졌거나, 인스턴스가 다름(그때 `status`를 한 번 더 부르고, 그래도 다르면 이 상태) |
| 끄는 중 | 이 앱의 `runner stop`이 아직 끝나지 않음 |
| 확인 불가 | `status`가 실패함(명령 없음·시간 초과·출력 깨짐). 이때는 자동 켜기·끄기를 하지 않는다 |
| 오류 | 마지막 `start`·`stop`이 실패함(마지막 줄을 보임). 다음 `status`가 성공하면 그 결과로 바뀜 |

- 떠 있는 실행기마다 "앱이 켠 것" / "다른 곳에서 켠 것"(터미널, 다른 세션의 앱, 이전 판)을 함께 보인다(§5.3의 `owned_instance`와 같은지).
- pid로 판단하지 않는다. pid는 보이기용으로만 쓴다.

### 5.3 켜기와 소유권

- **한 번에 하나:** `RunnerSupervisor`는 켜기·끄기·상태 확인을 한 줄로 세운다(앞 동작이 끝나야 다음). 앱 안의 동시 `start`·`stop`은 없다. 앱 밖(터미널)과의 경합은 hub가 잠금과 인스턴스로 가린다. **앱 종료와 세션 종료는 이 줄 밖에서** 곧바로 한다(§5.5): 저장된 `owned_instance`·`pending_instance`에 멈춤 요청 파일을 쓰고, 줄에는 "끝나는 중"을 표시해 그 뒤로 새 동작을 시작하지 않는다. 진행 중인 `start`가 그 뒤에 끝나도 그 결과는 설정에 쓰기만 하고(설정 쓰기는 앱 안의 잠금 하나로 직렬) 아무것도 켜거나 끄지 않는다. 그 실행기는 이미 써 둔 자기 멈춤 요청을 보고 끝난다.
- **켜기:**
  1. **앱이 인스턴스 id를 만든다:** `<부팅 id>.<기한>.<GUID>`. 부팅 id는 Windows `BootId`(`HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Memory Management\PrefetchParameters`, 부팅마다 오름), Linux `/proc/sys/kernel/random/boot_id`. 기한은 지금의 가동 시간(Windows `GetTickCount64`, Linux `CLOCK_BOOTTIME`) + 30초를 밀리초로. 이 id를 `workbench.json`에 `pending_instance`로 먼저 적는다(앱이 도중에 죽어도 다음에 알아보도록). 기한과 부팅 id가 id 안에 있으므로 앱·hub·실행기가 같은 값을 본다(hub가 따로 정하지 않음).
  2. `<hub 명령> runner start --instance <id> --json`(H10). hub는 id의 형식을 검사하고 그대로 실제 실행기에 넘긴다. **실행기는 잠금을 잡은 뒤, 상태 파일을 쓰기 전에 id의 부팅 id가 지금과 같고 가동 시간이 기한 전인지 확인하고, 아니면 잠금을 놓고 아무것도 쓰지 않고 끝난다.** 기한은 벽시계가 아니라 가동 시간이라 시계가 바뀌어도 같다. 앱이 id를 적은 뒤 `uv` 실행 등이 늦어져도 기한은 늘어나지 않는다. 그래서 기한이 지난 뒤에 그 id로 잠금을 쥔 채 남는 실행기는 없다(잠금을 잡고 확인하기까지의 아주 짧은 사이에는 `status`가 `instance: null`을 줄 수 있고, 아래 규칙은 그때 아무것도 지우지 않는다). `start`는 결과가 확정될 때만 답한다:
     - 성공: 그 실행기가 잠금을 잡고 상태 파일(같은 `instance`)을 쓴 것을 확인 → `{"instance", "pid", "started_at"}`.
     - `{"error": "running", "instance": …}`: 다른 실행기가 이미 떠 있음. 띄운 자식이 끝난 것을 확인한 뒤 답한다.
     - `{"error": "failed", "exit_code": …}`: 자식이 잠금을 잡기 전에 끝남.
     - 15초 안에 확인하지 못하면 `start`가 띄운 자식(과 그 자식)을 끝내고, 끝난 것을 확인한 뒤 `{"error": "cancelled"}`. 끝내지 못했으면 `{"error": "unconfirmed"}`.
  3. 성공이면 `owned_instance = id`로 옮기고 `pending_instance`를 지운다. **그 밖의 답(`running`·`failed`·`cancelled`·`unconfirmed`)이나 답 없음에서는 `pending_instance`를 남기고** 아래 규칙으로만 지운다. `start`가 끝낸 것은 자기가 띄운 프로세스이고, 가상환경의 `python.exe`처럼 런처가 진짜 실행기를 또 띄우는 경우(hub `background.start`의 주석) 그 진짜 실행기가 나중에 잠금을 잡을 수 있기 때문이다. 그래도 그 실행기는 기한이 지나면 잠금을 잡자마자 끝나므로(위 2), 기한 뒤의 확인이 마지막 답이 된다.
- **남은 `pending_instance`의 처리:** `status`의 인스턴스가 그 id면 소유로 옮긴다. **지우는 것은 기한이 지난 뒤의 `status`가 `running: false`이거나 확인된 다른 인스턴스를 줄 때뿐이다**(그 뒤로 그 id가 잠금을 잡아도 바로 끝남). `instance: null`이나 `status` 실패면 시간과 상관없이 남긴다. id의 부팅 id가 지금과 다르면(재부팅) 그 id의 실행기는 뜰 수 없으므로 지운다. 지우기 전까지는 자동 켜기를 하지 않고 "켜는 중(확인 대기)"으로 보인다.
- **앱이 켜질 때:** `pending_instance`를 위처럼 먼저 처리한다. `owned_instance`가 있고 `status`의 인스턴스가 같으면 그대로 "앱이 켠 것"이다(앱이 비정상 종료한 뒤 다시 켜진 경우). 꺼져 있거나 다른 인스턴스면 `owned_instance`를 지운다. `status`가 `instance: null`이거나 실패하면 그대로 두고 나중에 다시 확인한다.
- **연동(기본 켬, 설정 "앱과 함께 실행기 켜고 끄기"):**
  - 앱이 켜질 때: 위 확인 뒤 실행기가 꺼져 있으면 켠다. 떠 있으면(누가 켰든) 그대로 둔다.
  - 앱이 정상 종료할 때(트레이 종료): 소유한 인스턴스와, 있으면 `pending_instance`에 멈춤 요청 파일을 하나씩 만든다(§5.4. 아직 뜨지 않은 pending 인스턴스는 뜨자마자 자기 요청을 보고 끝남). 소유한 실행기가 요청을 받은 것(`stop_ack`)을 5초까지 본 뒤 앱은 끝난다. 실행기는 맡은 작업을 정리하고 스스로 끝난다(최대 90초 남짓). 앱은 강제 종료를 기다리지 않는다: 다음에 켜질 때 그 실행기가 아직 떠 있으면 §5.3대로 이어 받고 상태 줄에 "끄기를 요청했지만 아직 떠 있음"을 보인다. 다른 곳에서 켠 실행기는 건드리지 않는다.
  - 연동을 끄면 앱은 켜고 끄기를 사람이 누를 때만 한다.

### 5.4 끄기

- **조건부 멈춤(H15):** `<hub 명령> runner stop --instance <id> --json`. 멈춤 요청은 **요청마다 새 파일**이다: `<hub 홈>\runner.stop.d\<인스턴스 id>.<임의 값>`을 새로 만든다(이미 있는 파일을 덮지 않으므로 동시 요청이 서로를 지우지 않음). 실행기는 그 폴더를 보고 자기 id의 파일만 따르며, 따른 파일만 지운다. 자기 id의 파일은 시작할 때 남겨 따른다(시작 직후, 또는 뜨기 전에 온 요청). **다른 id의 파일은 그 대상이 다시는 뜰 수 없을 때만 지운다:** 파일 이름의 id에서 부팅 id가 지금과 다르거나 기한이 지났을 때(그 뒤로는 그 id가 잠금을 잡아도 바로 끝나므로). 아직 기한 전인 다른 id의 요청(막 시작하려는 pending 실행기에게 앱이 남긴 것)은 남긴다. 형식이 맞지 않는 파일은 지운다.
- **대상 없는 멈춤(터미널의 `runner stop`):** hub가 먼저 H14로 지금 떠 있는 인스턴스를 확인해 그 id로 요청한다. 인스턴스를 모르면(`instance: null`: 막 시작하는 중이거나 옛 실행기) 1초씩 10초까지 다시 확인하고, 그래도 모르면 `unconfirmed`로 끝낸다. 그래서 "누구든"(`any`) 요청은 없다.
- **옛 실행기(H15 이전):** 상태 파일을 쓰지 않으므로 H14가 `instance: null`을 준다. 터미널의 `runner stop --legacy`만 옛 `runner.stop` 파일을 쓴다(사람이 옛 실행기임을 알고 고름). 새 실행기는 옛 `runner.stop`을 따르지 않고, 시작할 때 지운다. 앱은 옛 실행기를 끄지 않는다(§5.2의 "누구인지 모름"). 요청을 받으면 상태 파일을 `stopping`과 받은 요청 이름(`stop_ack`)으로 쓴다: 이것은 "받음"이지 "멈춤"이 아니다. 멈춤은 잠금이 풀린 것으로만 확인한다.
- **시간:** 멈춤을 받은 실행기는 맡은 작업을 정리하고 결과를 보내는 데 `RUNNER_STOP`(지금 90초)까지 쓴다. `runner stop`은 그 뒤 15초를 더 기다리고(지금처럼 최대 105초) 강제 종료로 간다. 상태 줄은 그동안 "끄는 중(작업 정리, 최대 1분 45초)"을 보인다.
- **강제 종료(H15):** 시간 안에 잠금이 풀리지 않으면, hub는 상태 파일을 다시 읽어 **그 `instance`가 요청한 id와 같은지** 먼저 본다(105초 사이에 대상이 끝나고 다른 실행기가 떴을 수 있음). 다르면 끄지 않고 `other_instance`(대상은 끝난 것)로 끝낸다. 같으면 그 상태의 pid로 **프로세스 핸들을 열고**, 그 핸들로 읽은 생성 시각이 같은 상태의 `started_at`(실행기가 자기 핸들에서 읽어 적은 값)과 같을 때만 그 핸들로 끝낸다. 인스턴스·pid·생성 시각을 한 번 읽은 상태 하나에서 가져오므로 서로 다른 실행기의 값이 섞이지 않는다. 핸들을 쥔 동안에는 pid가 재사용되지 않으므로 확인과 종료 사이에 대상이 바뀌지 않는다. 핸들을 열지 못하거나 생성 시각이 다르면 끄지 않고 `unconfirmed`.
- **실행기 아래의 프로세스 전부 (Windows):** 실행기는 시작하자마자, 아무것도 띄우기 전에 **자기 자신을** Job Object(`KILL_ON_JOB_CLOSE`, 그 Job의 핸들은 실행기만 쥠)에 넣는다(H15). 그 뒤 실행기가 띄우는 모든 프로세스(터널, 에이전트, 그 손자)는 만들어지는 순간 OS가 같은 Job에 넣으므로, "만들고 Job에 붙이기 전"의 틈이 없다. 에이전트마다 두는 지금의 Job(hub `acp.py`, 일시 정지 → 붙이기 → 재개)은 그 안의 중첩 Job으로 그대로 둔다(작업 하나를 취소할 때 쓰임). 실행기가 어떤 식으로든 끝나면 마지막 핸들이 닫혀 OS가 Job 안의 모든 프로세스를 끝낸다. 자기를 Job에 넣지 못하면 실행기는 시작하지 않고 상태 파일 없이 오류로 끝난다.
- **Linux는 이 설계의 범위 밖이다.** 이 앱은 Windows 앱이고, Linux 기기(`linux` 실행기)는 지금처럼 터미널이나 서비스로 돈다. H15를 Linux에서 쓸 때 강제 종료는 핸들(`pidfd`)로 신원을 확인한 실행기 프로세스만 끝내고, 결과는 `killed`가 아니라 `runner_killed`(실행기는 끝났지만 에이전트 세션과 터널이 남았을 수 있음)로 돌려준다. 실행기 아래 나무 전체를 Linux에서 안전하게 정리하는 방법(cgroup 등)은 hub의 따로 된 과제로 둔다(§11).
- **결과(하나):** `stopped`(잠금이 풀린 것을 확인), `killed`(강제 종료 뒤 잠금이 풀린 것을 확인), `not_running`, `other_instance`(다른 인스턴스가 떠 있어 손대지 않음), `unconfirmed`(요청은 했지만 멈춤을 확인하지 못함, 또는 강제 종료 대상을 확인하지 못함), Linux에서만 `runner_killed`(아래).
- **앱이 끄는 경우:** 연동으로 끌 때는 늘 `owned_instance`를 넘긴다. 소유를 확인하지 못하면(`status` 확인 불가, 인스턴스 모름) **끄지 않고** "실행기를 끄지 못했습니다(확인 불가)"를 남긴다.
- **사람이 누르는 끄기:** 대상을 보이고 확인을 받는다: "실행기 laptop(앱이 켠 것 / 다른 곳에서 켠 것, pid N)을 끕니다. 진행 중인 작업은 실패할 수 있습니다." 그때 `status`로 읽은 인스턴스를 넘긴다(그 사이 바뀌면 `other_instance` → 다시 보이고 묻기). 결과를 그대로 보인다(`unconfirmed`면 "끄기를 요청했지만 확인하지 못했습니다").
- 끝나면(`stopped`·`killed`·`not_running`) 그 인스턴스가 `owned_instance`였으면 지운다.

### 5.5 비정상 종료, 로그오프, Windows 종료

- **앱이 비정상 종료하면** 실행기는 계속 돈다(창 없는 별도 프로세스, 감시자를 두지 않음). 다음에 앱이 켜지면 §5.3의 확인으로 다시 "앱이 켠 것"으로 이어 받는다. 그 사이에는 실행기가 앱 없이 돈다는 것을 받아들인다.
- **로그오프·Windows 종료(`SessionEnding`):** 파이썬 명령을 띄우지 않는다(끝날 시간이 없을 수 있음). 앱이 직접 멈춤 요청 파일을 새로 만든다(H15 형식, 이름이 겹치지 않으므로 다른 요청을 덮지 않음): `owned_instance`에 하나, `pending_instance`가 있으면 그것에도 하나(그 실행기가 나중에 뜨면 자기 요청을 보고 바로 끝남). 그 뒤 최대 5초 동안 상태 파일의 `stop_ack`가 그 요청인지 보고 끝난다. 이 5초는 최선의 노력이다: 실행기가 요청을 받았는지, 그 뒤 스스로 끝나는지, Windows가 먼저 끝내는지는 보장하지 않는다.
- 그때 실행기가 맡고 있던 작업과 프로젝트 요청이 어떻게 되는지는 서버와 연결 상태에 따라 다르다(서버가 실행기 연결이 끊긴 것을 알아야 정리됨). 이 앱은 그것을 보장하지 않으며, 그 결과는 작업 콘솔(Web)에서 본다.
- 다음 로그인에서 앱이 켜지면 이전 실행기가 남아 있는지(`status`) 보고, 남아 있고 소유한 인스턴스면 그대로 이어 받는다.
- **로그인 시 시작:** 설정 "Windows에 로그인하면 앱 시작"(기본 끔). `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`의 값 하나(`HIMARI Workbench`, 앱의 절대 경로를 따옴표로). 켜 두면 연동에 따라 실행기도 켜진다(hub가 로그인 시작을 이 앱에 맡긴 자리).

### 5.6 처음 설정과 오류 회복

설정이 없거나 hub 명령이 동작하지 않으면 마법사를 연다.

1. **서버 주소:** `https`인지(§4), 열리는지.
2. **hub 명령:** `uv`를 `PATH`에서 찾으면 그 절대 경로를 채우고, 없으면 실행 파일을 직접 고르게 한다. hub 폴더(`pyproject.toml`이 있는 곳)를 고른다.
3. **확인:** `<hub 명령> runner status --json`을 실행한다. 실패하면 단계와 마지막 줄을 보인다: 실행 파일 없음, hub 폴더가 아님, 의존성 설치 실패(`uv`의 출력), H14가 없는 옛 hub("hub를 새로 받으세요").
4. **기기 등록:** `status`의 `registration`(H14)을 본다. `missing`이면 "이 기기는 아직 실행기로 등록되지 않았습니다. 터미널에서 `himari-hub runner setup`을 먼저 하세요", `broken`이면 hub가 준 이유(설정을 읽지 못함, 서버 주소 없음, 토큰 파일이 비었거나 읽을 수 없음 등)를 보이고, 둘 다 실행기 켜기를 막는다. `ok`는 실행에 필요한 것이 갖춰졌다는 뜻이지 서버에 붙는다는 뜻은 아니다: 연결은 켠 뒤 상태 파일의 `state`로 따로 보인다. 터널 설정(`runner tunnel`)도 터미널에서 한다.
5. 끝나면 연동 설정을 고른다(기본 켬).

경로에 공백·한글이 있어도(예: `D:\00_프로젝트\Himari-v4`) 인자 목록과 작업 폴더로만 넘기므로 따옴표 문제가 없다. §10에서 시험한다.

### 5.7 보이는 곳

- **상태 줄**(창 위쪽, 한 줄): "실행기: 연결됨 · laptop · 앱이 켠 것" + 켜기/끄기 + "기록"(`runner.log`를 기본 편집기로) + 설정. 오류·확인 불가면 빨간 글과 마지막 줄.
- **트레이:** 아이콘 툴팁에 실행기 상태. 메뉴: 작업 콘솔 열기, 실행기 켜기/끄기, 설정, 종료. 상태가 "연결됨"에서 다른 것으로 바뀌면 한 번 알림(5분에 한 번까지).
- 작업 콘솔(Web)은 지금처럼 hub에서 본 기기 연결(`runner_connected`)을 보인다. 이 앱은 Web에 실행기 상태를 알리지 않는다.

## 6. 보안 경계

- **이 앱이 더하는 권한은 이 기기에서의 켜기·끄기뿐이다.** Web 페이지나 서버가 이 앱에 명령을 보내는 길은 없다: 앱은 네트워크에 아무것도 열어 두지 않고(두 번째 실행용 파이프는 같은 사용자만, "창 보이기"만 받음), WebView2에 앱 기능을 넘기지 않는다(`AddHostObjectToScript`·`WebMessageReceived` 처리를 두지 않음).
- **그러나 실행기를 켜는 것은 이 기기에 원격 실행을 여는 일이다.** 떠 있는 실행기는 hub 서버가 보내는 작업을 받아, 등록된 프로젝트 폴더에서 로컬 에이전트(와 에이전트가 실행하는 프로세스)를 돌린다. 이것은 이 앱이 아니라 기존 hub의 권한이고, 그 신뢰 경계는 hub 서버의 인증, 이 기기의 실행기 토큰, 기기에 등록된 프로젝트 폴더, 프로젝트의 권한 묶음과 승인 정책, 기기의 프로젝트 요청 허가 방식(V3-P103)이다. 앱은 연동이 기본으로 켜져 있다는 것과 이 뜻을 처음 설정(§5.6)에서 한 번 보인다.
- 앱은 hub의 토큰과 v3의 운영자 비밀을 다루지 않는다. 작업 콘솔의 로그인은 WebView2 쿠키로만 남는다(브라우저와 같음).
- `workbench.json`에는 서버 주소, hub 명령(실행 파일·인자·작업 폴더), hub 홈, 설정, `owned_instance`·`pending_instance`만 둔다.

## 7. 설정 파일

- `workbench.json`이 없으면 마법사(§5.6). 깨졌으면 덮어쓰지 않고 `workbench.json.broken-<시각>`으로 옮긴 뒤 마법사를 열고 알린다.
- 쓸 때는 같은 폴더의 `.tmp`에 쓰고 `File.Replace`(없으면 `File.Move`)로 바꾼다.

## 8. 반려 앱과 합칠 때를 위한 경계

- **같은 기술, 같은 자리:** 반려 앱과 같은 .NET·WPF·WebView2 판, 같은 `clients/windows` 아래. 합치면 `RunnerSupervisor`·`WorkbenchSettings`를 반려 앱으로 옮기고 작업 콘솔 창을 메뉴 하나로 붙인다.
- **실행기는 한 앱만:** 반려 앱에는 합칠 때까지 실행기 관리를 넣지 않는다.
- **옮겨진 뒤의 옛 앱:** 옛 작업 앱은 켜질 때 `workbench.json`이 없고 `workbench.json.migrated`가 있으면 마법사를 열지 않고 "HIMARI 앱으로 옮겨졌습니다"를 보이고 끝난다(이 검사는 처음 판부터 넣는다). 그래서 옮긴 뒤 합친 앱이 꺼져 있을 때 옛 앱을 켜도 실행기를 따로 관리하지 않는다.
- **합칠 때의 인계:** 합친 앱도 같은 Mutex `Global\HIMARI.Workbench.<SID>`를 실행기 관리의 열쇠로 쓴다. 그래서 옛 작업 앱과 합친 앱 중 하나만 실행기를 관리하고, 옮기는 동안 옛 앱이 켜질 수 없다(Mutex를 못 얻고 끝남). Mutex를 쥔 채로: `workbench.json`을 읽어 서버 주소·hub 명령·홈·`owned_instance`·`pending_instance`를 자기 설정에 쓰고(원자적), 그 뒤 `workbench.json`을 `workbench.json.migrated`로 바꾼다. 도중에 죽으면 다음에 같은 일을 처음부터 다시 한다(두 파일이 다 있으면 `workbench.json`이 기준: 다시 해도 결과가 같음). 소유는 옮긴 뒤 §5.3의 확인을 거친다. 떠 있는 실행기는 끄지 않고 이어 받는다. Mutex를 얻지 못하면(옛 앱이 켜져 있음) 합친 앱은 실행기 관리 없이 "작업 앱을 종료하세요"를 보인다.
- **설정은 따로:** 합칠 때까지 `workbench.json`과 `window.json`을 섞지 않는다.
- **트레이 아이콘 둘:** 두 앱을 함께 켜면 아이콘이 둘이다. 합칠 때까지 받아들인다.
- **WebView2 데이터 폴더는 따로**(`workbench\webview`, `reader`): 합쳐도 그대로 둘 수 있다.

## 9. hub에 필요한 것

| id | 무엇 | 크기 |
| --- | --- | --- |
| H9 | 실행기가 `<hub 홈>\runner.state.json`을 씀: `{"instance", "pid", "started_at"(실행기가 자기 프로세스 핸들에서 읽은 생성 시각), "updated_at", "state"("starting"·"connected"·"disconnected"·"stopping"), "stop_ack"(받은 멈춤 요청 이름), "name", "server"(호스트만), "error"(한 줄)}`. 잠금을 잡은 뒤 처음 쓰고, 상태가 바뀔 때와 5초마다(`updated_at`) 원자적으로(`.tmp` → `replace`) 쓴다. 끝날 때 지운다. 토큰·경로는 넣지 않는다 | 작음 |
| H10 | `runner start --instance <id> --json`: id는 앱이 만든 `<부팅 id>.<기한>.<GUID>`(§5.3), hub는 형식만 검사해 그대로 실행기에 넘기고(환경 변수), 실행기는 잠금을 잡은 뒤 상태 파일을 쓰기 전에 부팅 id와 기한을 확인해 아니면 잠금을 놓고 끝난다. `--instance` 없는 `runner start`는 hub가 같은 형식으로 만든다. `start`는 §5.3의 확정된 결과 하나만 돌려준다(확인 못 하면 띄운 자식을 끝내고 `cancelled`, 그것도 못 하면 `unconfirmed`). `--instance` 없이는 지금처럼 동작(id는 hub가 만듦) | 중간 |
| H14 | `runner status --json`: `{"running", "instance", "pid", "started_at", "registration"("ok"·"missing"·"broken"), "why"}`. **전이 잠금 `runner.transition.lock`(막히는 잠금, 2초까지):** 실행기는 ⓐ `runner.lock`을 잡고 기한을 확인하고 상태 파일을 처음 쓰는 일, ⓑ 끝날 때 상태 파일을 지우고 `runner.lock`을 놓는 일을 각각 이 잠금을 쥔 채 한다. 상태 확인은 이 잠금을 쥔 채 ① `runner.lock`을 막히지 않게 잡아 본다: 잡히면 꺼짐(바로 놓음, 남은 상태 파일은 무시). ② 잡히지 않으면 지금 잠금을 쥔 실행기가 이미 ⓐ를 마치고 상태를 쓴 것이므로(ⓐ·ⓑ 도중에는 확인이 들어올 수 없음) 상태 파일의 `instance`가 그 실행기의 것이다. ③ 그래도 상태 파일의 pid로 핸들을 열어 생성 시각이 `started_at`과 같은지 본다. 상태 파일이 없거나 깨졌거나 생성 시각이 다르면(옛 판 실행기처럼 ⓐ를 따르지 않는 것이 잠금을 쥠) `instance: null`. 실행기가 강제로 끝나면 OS가 두 잠금을 모두 놓는다. `registration`은 `runner.json`을 읽고 서버 주소와 토큰 파일(비지 않고 읽을 수 있음)을 확인한 것이고 `broken`이면 `why`에 이유 | 중간 |
| H15 | 인스턴스 멈춤: 요청마다 새 파일 `runner.stop.d\<id>.<임의 값>`(`O_EXCL`), 실행기는 자기 id의 것만 따르고 따른 것만 지움, 시작할 때 다시 뜰 수 없는 id(부팅이 다르거나 기한이 지남)의 것과 옛 `runner.stop`을 지움, 받으면 상태 파일에 `stopping`·`stop_ack`. `runner stop --instance <id> --json`은 §5.4의 결과 하나, 대상 없는 `runner stop`은 H14로 인스턴스를 찾아 그 id로(모르면 `unconfirmed`), `--legacy`만 옛 파일. 강제 종료는 상태 파일의 인스턴스가 요청한 id이고 핸들로 신원(생성 시각)을 확인한 실행기만 그 핸들로(다르면 `other_instance`), 나무 전체는 실행기 자신을 넣은 Job(Windows: 자식은 만들어질 때부터 Job 안). Linux는 실행기만 끄고 `runner_killed` | 중간 |
| H16 | 상태 확인과 실행기 잠금의 경합: 실행기는 전이 잠금을 쥔 채 `runner.lock`을 잡으므로 확인과 겹치지 않는다. 다만 옛 판의 확인(전이 잠금을 모름)과 겹칠 수 있으니 `runner.lock`을 처음 잡지 못하면 2초 동안 다시 시도한다. `background.running()`과 `start`의 대기 중 확인도 H14의 절차로 바꾼다. **포그라운드 실행기(터미널의 `himari-hub runner`)도 같다:** 환경 변수로 받은 인스턴스 id가 없으면 잠금을 잡기 전에 같은 형식(`<부팅 id>.<기한>.<GUID>`)으로 스스로 만들고, 같은 전이 잠금·상태 파일·멈춤 요청을 쓴다. 그래서 `status`와 `stop`이 백그라운드와 포그라운드를 구분하지 않는다 | 작음 |

H14·H15의 핸들 확인은 Windows(`OpenProcess`·`GetProcessTimes`)와 Linux(`pidfd_open`, `/proc/<pid>/stat`의 시작 시각)에서 같은 뜻으로 구현한다. 모두 hub 홈 하나 안의 일이다. 옛 hub(H14 없음)에서는 마법사가 "hub를 새로 받으세요"로 멈춘다(pid로 짐작하는 길은 두지 않음).

## 10. 검사

- **hub(pytest):** H9 상태 파일(원자적 쓰기, 5초 갱신, 끝날 때 지움, `started_at`이 핸들의 생성 시각), H10(앱이 만든 id의 기한을 그대로 씀: `uv`가 늦어도 늘어나지 않음, 재부팅 뒤의 옛 id는 뜨지 않음, 인스턴스 전달, 확인 뒤 성공, 동시 `start` 둘 → 하나만 성공·하나는 `running`, 늦게 뜨는 자식 → `cancelled`, 가상환경 런처 아래의 진짜 실행기가 `cancelled` 뒤에 잠금을 잡아도 기한이 지났으면 바로 끝남, 기한이 지난 뒤 잠금을 잡은 실행기는 상태 파일을 쓰지 않고 끝남, 시계를 바꿔도 같음), H14(동시 확인 여럿과 시작·멈춤이 겹쳐도 잘못된 인스턴스를 돌려주지 않음, 잠금만 있고 상태 파일 없음 → `instance: null`, 죽은 실행기의 남은 상태 파일, pid 재사용 → `null`, `registration`의 세 경우), H15(동시 멈춤 요청 둘이 모두 남음, 뜨기 전에 온 자기 요청을 따름, 다른 실행기가 먼저 떠도 기한 전인 pending 요청을 지우지 않음, 105초 사이에 대상이 끝나고 다른 실행기가 뜨면 강제 종료하지 않고 `other_instance`, 옛 `runner.stop`을 따르지 않음, 대상 없는 `stop`이 인스턴스를 모르면 `unconfirmed`, 강제 종료 뒤 에이전트의 손자와 터널까지 끝남, 따른 것만 지움, 시작 직후 온 요청을 잃지 않음, 다른 인스턴스로 바뀐 뒤의 `stop` → `other_instance`, pid가 재사용된 프로세스를 끄지 않음, `stop_ack`), H16(상태 확인과 동시에 시작해도 실행기가 뜸, 포그라운드 실행기도 인스턴스·상태 파일이 있고 `stop --instance`로 멈춤), 전이 잠금(옛 실행기가 ⓑ로 끝나고 새 실행기가 ⓐ로 뜨는 사이의 확인이 어느 쪽 인스턴스도 섞지 않음), 실행기 자신의 Job(실행기를 띄운 직후·터널을 띄운 직후·에이전트를 띄운 직후에 실행기를 강제 종료해도 남는 프로세스가 없음, 자기를 Job에 넣지 못하면 시작하지 않음), Linux에서 강제 종료의 결과가 `runner_killed`.
- **`RunnerSupervisor` 단위 시험(가짜 hub 명령과 임시 hub 홈):** §5.2 표 전부(상태 파일 없음·오래됨·깨짐·다른 인스턴스, `status` 실패·`instance: null` → 자동 동작 없음), 켜기 중 앱 종료 → 다시 켜진 앱이 `pending_instance`로 확인(늦게 뜬 실행기를 소유로, 기한 전과 `instance: null`에서는 지우지 않고 자동 켜기도 안 함, 재부팅 뒤 지움), 시작 중 트레이 종료·로그오프에 pending 인스턴스로도 멈춤 요청(진행 중인 `start`를 기다리지 않고 5초 안에), 종료 뒤 끝난 `start`가 아무것도 켜지 않음, 비정상 종료 뒤 `owned_instance` 이어 받기, 소유한 것만 끄기, 확인 불가면 끄지 않음, 동작 직렬화, 인자 목록이 셸 없이 넘어감, 오류 줄 가리기.

- P1 시작을 확인하지 못한 뒤 늦게 뜬 실행기의 소유를 잃음 → 실행기는 발급 30초 뒤에는 뜨지 않고, `start`는 확인 못 하면 자식을 끝내 결과를 확정(`cancelled`), `pending_instance`는 그 인스턴스가 보이거나 30초가 지난 뒤에만 지움, 그동안 자동 켜기 없음(§5.3, H10).
- P1 강제 종료의 pid 재사용 → 핸들을 먼저 열어 생성 시각으로 신원을 확인하고 그 핸들로 끔, 자식도 같은 식, 확인 못 하면 `unconfirmed`(§5.4, H15).
- P1 세션 사이의 소유권과 설정 쓰기 경합 → Mutex를 `Global\…<SID>`로 해 사용자마다 한 프로세스만 설정을 쓰고 실행기를 관리(§3).
- P1 상태 확인의 잠금과 실행기의 잠금을 구별하지 못함 → 확인끼리 `runner.probe.lock`으로 한 줄로 서고, 인스턴스는 핸들의 생성 시각이 맞을 때만, 아니면 `instance: null`(H14, §5.2).
- P1 멈춤 요청 파일의 경합 → 요청마다 새 파일, 따른 것만 지움, "받음"(`stop_ack`)과 "멈춤"(잠금 풀림)을 나눔, 로그오프 5초는 최선의 노력(§5.4, §5.5, H15).
- P2 새 창의 외부 링크가 사용자 동작으로 제한되지 않음 → `IsUserInitiated`일 때만, 2초에 한 번(§4).
- P2 합칠 때의 인계가 원자적이지 않음 → 같은 `Global` Mutex를 쥐고 옮기며 `pending_instance` 포함, 다시 해도 같은 결과(§8).
- P2 등록 판정이 실행 가능성을 보장하지 않음 → `registration`의 `ok`·`missing`·`broken`과 이유, 연결은 따로(§5.6, H14).

### 3차 (rev. 3 → rev. 4): NOT_READY, P1 넷, P2 둘

- P1 잠금을 잡은 뒤 상태를 쓰기 전에 멈춘 실행기 때문에 `pending_instance`를 잘못 지움 → 기한은 잠금을 잡은 뒤에 확인(가동 시간 기준), pending은 기한 뒤의 `running: false`나 확인된 다른 인스턴스에서만 지우고 `instance: null`이면 남김(§5.3, H10).
- P1 `any` 요청과 옛 `runner.stop`이 새 실행기를 잘못 멈춤 → `any`를 없애고 대상 없는 멈춤도 인스턴스를 찾아 그 id로, 옛 파일은 `--legacy`만 쓰고 새 실행기는 따르지 않음(§5.4, H15).
- P1 직접 자식만 끄면 손자가 남음 → Windows는 에이전트가 이미 Job에 있고 터널도 Job에 넣어 실행기 하나를 끄면 나무 전체가 끝남, Linux는 프로세스 그룹 확인(§5.4, H15).
- P1 시작 중 정상 종료·로그오프 → pending 인스턴스에도 멈춤 요청(뜨자마자 끝남), 트레이 종료는 요청만 하고 실행기가 스스로 끝남(§5.3, §5.5).
- P2 옮긴 뒤 옛 앱을 다시 켜면 따로 관리함 → `workbench.json.migrated`를 보고 끝남(§8).
- P2 지금 hub의 멈춤 대기 시간이 30초가 아니라 105초 → 고치고 상태 줄 문구와 트레이 종료 동작을 그에 맞춤(§2, §5.3, §5.4).

### 4차 (rev. 4 → rev. 5): NOT_READY, P1 셋, P2 하나

- P1 다른 실행기가 시작하며 아직 뜨지 않은 pending 실행기의 멈춤 요청을 지움 → 다른 id의 요청은 그 id가 다시 뜰 수 없을 때(부팅이 다르거나 기한이 지남)만 지움(§5.4, H15).
- P1 앱의 기한과 hub의 기한이 따로 정해짐 → 앱이 부팅 id와 기한을 id 안에 넣어 만들고 hub·실행기는 그대로 씀(§5.3, H10).
- P1 강제 종료가 요청한 인스턴스인지 보지 않음 → 상태 하나에서 인스턴스·pid·생성 시각을 읽어 인스턴스가 다르면 `other_instance`(§5.4, H15).
- P2 동작 직렬화와 시작 중 종료가 충돌 → 앱 종료·세션 종료는 줄 밖에서 곧바로 멈춤 요청을 쓰고, 그 뒤 끝난 `start`는 아무것도 켜지 않음(§5.3).

### 5차 (rev. 5 → rev. 6): NOT_READY, P1 둘, P2 하나

- P1 잠금 확인과 상태 파일 읽기 사이에 실행기가 바뀌면 옛 인스턴스를 돌려줄 수 있음 → 실행기의 잠금 잡기·상태 게시와 상태 지우기·잠금 놓기, 상태 확인을 전이 잠금 하나로 한 줄로(H14).
- P1 터널을 Job에 넣기 전에 자식이 생길 수 있음 → 에이전트처럼 일시 정지로 만들어 Job에 붙인 뒤 재개, 실패하면 터널을 열지 않음(§5.4, H15).
- P2 포그라운드 실행기의 인스턴스가 정의되지 않음 → 같은 형식의 id를 스스로 만들고 같은 상태·멈춤 규칙을 씀(H16).

### 6차 (rev. 6 → rev. 7): NOT_READY, P1 셋
