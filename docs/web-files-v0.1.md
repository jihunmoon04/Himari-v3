## 1. 범위

이 문서가 정하는 것(§3~§9):
1. **탐색기**: 서버의 폴더 트리와 파일 미리보기.
2. **폴더에서 대화 열기**: 그 폴더를 작업 위치로 쓰는 대화가 있으면 그것을, 없으면 새 대화를 연다.
3. **웹 편집기**: 텍스트 파일을 열어 바로 고치고 저장한다. 충돌 감지와 직전 판 보관을 둔다.

방향만 적는 것(§10):
4. 편집 중 에이전트 부르기(선택 영역 참조, 수정 diff).
5. PDF 필기(iPad)와 에이전트에게 넘기기.

이 문서가 바꾸지 않는 것:
- 에이전트의 쓰기 범위. 여전히 대화에 붙인 Workspace 안만이다. 웹 편집기의 쓰기는 **소유자 자신의 행동**이고 대화의 쓰기가 아니다(§7.1).
- runner의 숨김 목록과 Sandbox. 웹도 runner를 거치므로 같은 숨김 목록이 읽기·쓰기 모두에 적용된다.
- 소유자 principal 밖. 머신 Environment가 없는 principal에게는 이 화면이 없다.

## 2. 다른 도구는 어떻게 하나 (2026년 기준, 제가 아는 범위)

- **VS Code(원격 포함)**: 탐색기·편집기·터미널·에이전트 패널이 한 창이다. 편집기는 저장 시 디스크 내용이 바뀌었으면 "비교/덮어쓰기"를 묻는다. 로컬 기록(Local History)으로 직전 판을 되돌린다.
- **Cursor·Windsurf·Claude Code IDE 연동**: 열린 파일과 선택 영역을 에이전트 맥락으로 넘기고, 에이전트 수정은 diff로 보여 받아들이게 한다(§10의 방향).
- **code-server·GitHub Codespaces**: 브라우저에서 같은 경험을 준다. 다만 서버 전체 권한의 셸·확장 실행이 함께 와서 HIMARI의 경계(runner·숨김 목록)와 맞지 않는다. 그래서 그대로 들이지 않고 필요한 부분만 만든다.

## 3. 화면 (소유자 방향: 지금 웹의 디자인을 잇는다)

### 3.1 원칙

- **지금 웹의 틀을 잇는다.** 사이드바, 가운데 대화, 줄 메뉴(…), 팝오버, 대화상자를 그대로 쓴다. 새로 더하는 것은 **오른쪽 파일 패널** 하나다.
- **색·글꼴·간격·모서리는 기존 토큰만 쓴다**(`app.css`의 `--bg`, `--sidebar-bg`, `--surface-*`, `--border-subtle`, `--mono`, `--radius-*`, `--space-*`). 테마(light·warm·dark)를 그대로 따른다.
- **IDE 장식은 넣지 않는다**: activity bar, status bar, minimap, 탭 막대, 여러 칸 분할, 파일 아이콘 테마.
- 꼭 필요한 동작만 눈에 띄게 둔다: 폴더에서는 **대화 열기**, 파일에서는 **저장**. 나머지는 줄 끝 "…" 메뉴에 넣는다.
- **부품으로 만든다.** 폴더 목록, 파일 보기, 편집기는 어느 자리에든 놓을 수 있는 부품이다(가운데 면, 오른쪽 패널, 나중의 다른 배치). 배치를 바꿔도 부품은 다시 만들지 않는다.

### 3.2 구조: 대화는 가운데, 파일은 오른쪽 패널

```
┌────────┬──────────────────────┬─────────────────────┐
│ 사이드바 │ 대화 (지금 그대로)       │ 파일 패널             │
│ 대화 목록│                      │ 폴더 목록 → 파일 편집   │
│ Files  │ 입력창                 │ (너비 조절·전체 확장)   │
└────────┴──────────────────────┴─────────────────────┘
```

- 대화 옆에 작업물 패널이 붙는 모양이다(ChatGPT Canvas, Claude의 Artifacts와 같은 계열). 지금 웹의 에이전트 화면에 그대로 붙는다.
- **대화 위 막대의 "파일" 버튼**을 누르면 오른쪽 패널이 열리고, 그 대화의 작업 폴더를 보인다. 다시 누르면 닫힌다.
- **패널 안**
  - 처음에는 폴더 목록(§3.3)이다. 파일을 누르면 같은 패널이 그 파일의 보기·편집기(§3.4)로 바뀐다. 위의 경로 줄로 폴더에 돌아간다.
  - 너비는 경계를 끌어 바꾼다. 넓은 화면의 기본은 화면의 45%이고, 30~70% 사이다.
  - **확대** 버튼(기존 `side-expand`/`side-contract` 아이콘)으로 패널이 가운데 면 전체를 덮는다. 대화는 다시 줄이면 돌아온다.
- **대화 없이 파일만 볼 때**
  - 사이드바의 **New Chat 아래 "Files"** 한 줄(기존 `side-folder` 아이콘)을 누른다. 가운데 면에 같은 폴더 목록 부품이 열린다.
  - 거기서 **대화 열기**(§6)를 누르면 그 대화가 가운데에 열리고, 그 폴더는 오른쪽 패널로 옮겨 간다.
- **좁은 화면**
  - 휴대폰에서는 패널이 전체 화면으로 덮는다. 위 막대 버튼으로 대화와 오간다.
  - iPad 가로나 노트북처럼 넓은 화면에서는 나란히 놓인다(기준 너비는 구현 때 정한다).

### 3.3 폴더 목록 (부품)

- 한 번에 폴더 하나를 보는 목록이다(Finder 목록 보기나 Drive 웹처럼). 트리는 펼치지 않는다.
- **위**: 경로 이동 줄(`~ › projects › himari`, 누르면 그 폴더로).
  - 가운데 면에서는 오른쪽에 **대화 열기** 버튼(New Chat과 같은 모양)과 옆 화살표(그 폴더의 대화 목록, §6.1)를 둔다.
  - 패널에서는 이미 대화가 옆에 있으므로, 그 자리에 "이 대화에 붙이기"를 둔다(그 폴더가 이 대화의 폴더가 아닐 때).
- **목록**: 대화 목록과 같은 줄 높이·hover·선택 모양이다. 폴더가 먼저다. 크기와 수정 시각은 옅은 글자로 오른쪽에 둔다.
- **줄 끝 "…"**
  - 폴더: 대화 열기, 이 대화에 붙이기, 폴더 등록, 새 파일, 새 폴더
  - 파일: 다운로드, 경로 복사, 삭제
- **목록 위의 작은 줄**: 최근 연 폴더와 등록한 폴더. 처음 들어오면 홈(`~`)이다(패널에서는 대화의 작업 폴더).
- 빈 폴더, 느린 폴더(Drive), 못 여는 폴더는 지금의 빈 상태·안내 문구 모양으로 보인다.

### 3.4 파일 보기·편집기 (부품)

- 편집 면은 테두리 없는 흰 면이고, 고정폭 글꼴(`--mono`)을 쓴다. 줄 번호는 옅게 둔다.
- **위 막대**: 파일 이름, 저장 상태 점(지금의 상태 점과 같은 모양), **저장** 버튼, "…".
  - "…"에는 이전 판, 다운로드, 경로 복사, 삭제가 들어간다.
- 여러 파일을 탭으로 띄우지 않는다. 최근 연 파일은 폴더 목록의 "최근" 줄에서 다시 연다.
  - 저장하지 않은 파일이 있으면 다른 파일로 가거나 패널을 닫을 때 묻는다.
- 충돌, 이전 판, diff는 지금의 대화상자 모양으로 띄운다.
- 에이전트가 이 대화에서 파일을 바꾸면, 열린 파일에 "바뀜" 표시가 뜬다(§5.3). 폴더 목록은 Run이 끝날 때 다시 읽는다.

### 3.5 왜 이 구조인가

- **rev. 1(3단: 탐색기 | 편집기 | 대화)**: VS Code와 거의 같다. 소유자가 원하지 않는 IDE 모양이고, 세 칸이 늘 떠 있어 좁은 화면에서 맞지 않는다.
- **rev. 2(가운데 파일 화면 + 오른쪽 drawer의 대화)**: 대화 화면을 drawer에서도 띄울 수 있게 지금의 대화 코드(app.js)를 크게 고쳐야 한다. 입력창도 두 곳에 생긴다.
- **rev. 3(이 구조)**
  - 지금의 대화 화면을 그대로 두고, 새로 만드는 것은 파일 패널과 그 부품뿐이다.
  - 입력창이 늘 옆에 있어서, 4단계(편집 중 에이전트 부르기)는 선택 영역을 그 입력창에 참조로 붙이면 된다(§10.1).
  - 에이전트가 고치는 파일이 옆 패널에서 바로 보인다.
  - 5단계(PDF 필기)는 패널을 전체로 키워 쓰고, 줄이면 대화로 돌아온다(§10.2).

## 4. 구조

```
브라우저 ──(쿠키 세션)──▶ HIMARI Web (himari-v3) ──(runner 소켓, SO_PEERCRED)──▶ himari-runner (coder)
                              │ 경로 잠금(PathLocks), 직전 판 보관(HIMARI 데이터)
```

- 웹 API는 **runner의 연산을 그대로 감싼다.** HIMARI(`himari-v3`)는 사용자 파일을 직접 열지 않는다(V3-P74 §4.2와 같다).
- 웹 API는 소유자 principal(머신 Environment가 있는 principal)만 쓴다. 다른 principal에는 `404`다.
- 경로는 실제 경로다. `~`는 runner가 사용자 홈으로 푼다(§5.1).

## 5. 탐색기 (1단계)

### 5.1 목록

`GET /api/machine/list?path=<경로>&after=<커서>` → `{path, parent, entries[], next, workspace}`

- runner `list`를 확장한다(검수 B3).
  - 지금은 1,000개에서 자른 뒤 정렬한다. 그래서 큰 폴더는 어떤 항목이 빠질지 정해져 있지 않다.
  - **바꿀 것: 폴더의 항목을 전부 열거해 정렬한 뒤 나눈다.** 정렬은 폴더 먼저, 그다음 이름(바이트 순)이다.
    - 열거할 때는 이름과 종류만 읽는다(`scandir`의 `d_type`, 모르면 `lstat`).
    - 크기·수정 시각은 돌려줄 한 쪽(500개)에 대해서만 읽는다. 그래서 큰 폴더도 정렬 비용은 이름 수에 비례한다.
  - 열거 상한은 100,000개다. 넘는 폴더는 목록을 주지 않고 "항목이 너무 많은 폴더(하위 폴더를 열거나 `run_command`를 쓰세요)" 오류를 준다. 일부만 보여서 무엇이 빠졌는지 모르는 상태를 만들지 않는다.
- **커서로 나눈다**(`offset`이 아니다).
  - `next`는 이번 쪽 마지막 항목의 정렬 키(종류, 이름)다. 다음 쪽은 그 키보다 뒤의 항목이다.
  - 쪽을 넘기는 사이 폴더가 바뀌어도 **중복은 생기지 않는다.**
  - 이미 지나간 자리에 새로 생긴 항목은 새로 고칠 때까지 보이지 않는다. 지워진 항목은 다음 쪽에 나오지 않는다.
  - 화면은 "새로 고침"으로 처음부터 다시 읽는다.
- 항목: 이름, 종류(파일·폴더·링크·기타), 크기, 수정 시각.
  - 링크는 따라가지 않는다. 연다면 runner가 실제 경로로 풀고 다시 검사한다.
- 숨김 항목은 목록에 나오지 않는다(지금과 같다).
- `workspace`: 이 폴더가 등록된 폴더면 그 id와 이름, 아니면 `null`. 메뉴의 "폴더 등록/대화 열기"에 쓴다.
- Drive(`fuse.rclone`) 폴더는 느릴 수 있다. 목록 요청의 시간 한도는 15초이고, 넘으면 "느린 폴더" 오류를 준다.

### 5.2 파일 보기

`GET /api/machine/file?path=<경로>` → 텍스트면 `{path, text, identity, size, editable}`, 아니면 `{path, kind, size}`

- 텍스트 판정: UTF-8로 풀리고 NUL이 없으면 텍스트다. 편집 가능한 크기는 **1 MiB까지다(Q3).** 더 크면 읽기 전용으로 앞부분만 보인다.
- `identity`: runner의 `[dev, ino, size, mtime_ns]`. 저장할 때 충돌 감지에 쓴다(§7.2).
- 이미지(검수 N3): **사용자 폴더에 이미 있는 PNG·JPEG·GIF·WebP도 미리 본다.**
  - runner가 연 디스크립터를 V3-P67의 이미지 경로(Sandbox 안 Pillow, 같은 형식·픽셀 한도)에 넘긴다.
  - HIMARI가 다시 만든 JPEG/PNG만 화면에 나간다. 원본 바이트는 그대로 보이지 않는다.
  - 형식이 다르거나 한도를 넘으면 다운로드만 된다.
  - SVG는 이미지로 그리지 않고 텍스트로 보인다.
- 그 밖(PDF 포함): 크기와 종류만 보이고, **다운로드**로 받는다. 다운로드 응답은 `Content-Disposition: attachment`, `Content-Security-Policy: sandbox`, `nosniff`다. PDF를 화면에 그리는 일은 5단계다(§10.2).
- 파일 내용은 HTML로 해석하지 않는다. 텍스트는 편집기의 글자로만 들어간다.

### 5.3 바뀐 것 알기

- 열린 폴더 목록은 **대화의 Run이 끝날 때**(기존 live 이벤트)와 사용자가 새로 고칠 때 다시 읽는다.
- 열린 파일은 브라우저 창이 보이는 동안 5초마다 runner `stat`(새 연산, 디스크립터 없이 identity만)으로 확인한다. 바뀌었으면 편집기에 알린다(§7.2).
- 파일 감시(inotify)는 이번에 넣지 않는다. Drive에서는 믿을 수 없고, runner에 상태가 생긴다.

## 6. 폴더에서 대화 열기 (2단계)

### 6.1 어떤 대화를 여나

"이 폴더의 대화" = **이 폴더를 작업 위치로 쓰는 machine 대화**(activation의 기본 Binding이 이 폴더의 등록 Workspace인 대화). 붙어만 있는 대화는 넣지 않는다. 휴지통의 대화는 뺀다.

- **버튼 본체**: 이 폴더의 대화 중 **가장 최근에 활동한 것**을 연다. 없으면 새 대화(§6.2).
- **옆 화살표**: 이 폴더의 대화 목록(최근 순, 제목·마지막 활동)과 "새 대화".
- 기준은 **정확히 이 폴더**다. 하위 폴더에서 누르면 그 하위 폴더의 대화다. 상위 폴더의 대화를 함께 보여 줄지는 Q2.
- 대화 자신의 폴더(`~/HIMARI/conversations/<id>`)에서 누르면 그 대화를 연다(등록 없이).
- Data: `list_conversations_working_in(principal, workspace_id, limit)` 하나를 더한다.
  - SQL은 `activations.default_binding_id → bindings.workspace_id`을 잇는다. 기존 인덱스(`bindings_by_workspace`)를 쓰고, 대화의 마지막 활동 순으로 준다.
  - **DB 판은 그대로 v13이다**(표·열 추가 없음). 메모리 백엔드도 같은 함수를 둔다.

### 6.2 새 대화

1. 폴더가 등록되지 않았으면 등록한다. V3-P74의 `_register(reuse=True)`라서, 같은 폴더가 다른 경로로 이미 등록돼 있으면 그것을 쓴다. 이름은 폴더 이름이다.
2. 대화를 만든다(machine).
3. 그 폴더를 붙이고 작업 위치로 정한다.

- 등록이나 붙이기가 실패하면 만든 대화를 지운다. 등록은 남겨 둔다(해롭지 않고, 다음에 다시 쓴다).
- 사용자가 누른 것이므로 V3-P74 Q4("붙이기는 사용자만")와 맞다.

### 6.3 이 대화에 붙이기

지금 열린 machine 대화에 그 폴더를 붙이고 작업 위치로 정한다. 2단계의 `attach_workspace(path=…)`를 그대로 쓴다.

## 7. 웹 편집기 (3단계)

### 7.1 어디를 쓸 수 있나 (소유자 결정 2026-10-25)

- 웹 편집기는 **`coder`가 쓸 수 있는 곳이면 어디든** 바로 편집한다. 대화에 붙였는지, 등록했는지와 상관없다.
- 단, 다음은 막는다.
  - 숨김 목록(홈의 점 항목, HIMARI 데이터·설정, runner 설정). 웹 세션을 빼앗겨도 인증 정보와 셸 설정은 바꾸지 못하게 하기 위해서다.
  - runner 설정의 `writable_under` 밖.
- 구현: runner의 쓰기 연산에 `write_roots`로 **그 파일의 폴더**를 넘긴다. runner는 지금처럼 그 폴더를 다시 검사한다: 실제 경로, 숨김 아님, 디스크 파일시스템, `writable_under` 안.
  - 쓰기 연산의 모드는 §7.7에서 정한다(검수 B1·B2). 로그에는 웹 저장임을 남긴다(`origin: "web"`, 경로와 크기만).
- 에이전트의 범위는 그대로다. 웹 편집기로 쓸 수 있다고 해서 그 폴더가 대화의 Workspace가 되지는 않는다.

### 7.2 충돌 감지

- 파일을 열 때 받은 `identity`를 저장할 때 함께 보낸다. runner는 rename 직전에 같은지 확인하고, 다르면 `CHANGED`로 아무것도 쓰지 않는다(V3-P74의 `edit_file`과 같은 장치).
- `CHANGED`면 편집기가 세 가지를 묻는다: **비교**(디스크 판과 내 판의 diff), **디스크 판 불러오기**, **덮어쓰기**(새 identity로 다시 저장).
- §5.3의 확인으로 저장 전에도 "디스크에서 바뀜" 표시가 뜬다.

### 7.3 에이전트 작업과 겹칠 때 (Q1)

- 권고: **웹 저장은 경로 잠금을 기다리지 않는다.**
  - 에이전트의 `run_command`는 대화의 모든 폴더를 최대 600초 잡는다. 웹 저장이 그동안 멈추면 편집기로 쓸 수 없다.
  - 대신 원자적 저장(임시 파일 → rename)과 `identity` 검사로 같은 파일의 동시 수정을 잡는다.
  - 그 폴더에서 에이전트 명령이 돌고 있으면 편집기에 "에이전트 작업 중" 표시를 띄운다.
- **남는 한계(검수 N2)**: `identity` 검사가 모든 동시 수정을 잡지는 못한다.
  - 명령이 파일을 **연 채로 제자리에 쓰는 중**이면, 웹의 rename 뒤 그 명령의 쓰기는 이름이 없어진 옛 파일(inode)로 간다. 경로에서 보면 그 쓰기는 없어진다.
  - rename 직전 검사와 rename 사이의 아주 짧은 틈도 남는다.
  - 대신 이전 판은 **바뀌기 전 그 inode에서** 복사한다(§7.4). 그래서 명령이 그 사이 거기에 쓴 내용은 이전 판에 남아 되찾을 수 있다.
  - 화면의 "에이전트 작업 중" 표시는 이 상황을 미리 알리기 위한 것이다.
- 대안: 웹 저장도 잠금을 잡는다(최대 10초 기다린 뒤 "에이전트 작업 중이라 저장하지 못함"). 더 엄격하지만 긴 빌드 중에는 저장할 수 없다.

### 7.4 직전 판 보관 (Q4, 검수 B2)

보관 장소: HIMARI 데이터 폴더(`himari-v3` 소유, 명령에서 숨김).
- 파일별로 최근 판들을 둔다. 30일 또는 전체 200 MiB 중 먼저 닿는 쪽에서 오래된 것부터 지운다.
- Data 표를 쓰지 않고 파일로 둔다(판 폴더마다 색인 JSON). DB 판은 그대로다.
- 1 MiB 넘는 파일은 웹에서 편집하지 않으므로 보관하지 않는다.

**저장 프로토콜.** 저장, 충돌 검사, 이전 판 확보는 runner의 한 연산 안에서 일어난다.

1. **미리 확인(HIMARI)**: 보관소에 쓸 수 있고, 여유가 파일 크기 + 16 MiB 이상인지 본다. 아니면 **저장하지 않고** "이전 판을 보관할 수 없어 저장하지 않음"을 돌려준다.
2. **runner `write` (`mode: "replace"`, `expected` 필수)**
   1. 이름의 지금 파일을 **읽기 전용으로 연다**(링크 따라가지 않음).
   2. 그 디스크립터의 identity가 `expected`와 같은지 본다. 다르면 `CHANGED`, 아무것도 쓰지 않는다.
   3. 임시 파일에 새 내용을 쓰고 fsync한다.
   4. rename 직전에 경로의 identity를 다시 확인한다(같은 inode인지).
   5. rename한다.
   6. 응답에 새 identity와 함께 **열어 둔 옛 파일의 디스크립터**를 넘긴다(`SCM_RIGHTS`).
3. **보관(HIMARI)**: 받은 디스크립터에서 옛 내용을 복사해 판으로 남긴다.
   - 이 디스크립터는 rename으로 교체된 바로 그 inode다. 그래서 보관한 판이 실제로 교체된 내용과 같다.
   - 백업을 먼저 하고 저장하는 방식에서 생기는 "백업한 것과 교체된 것이 다름" 경합이 없다.

실패 처리:
- `CHANGED`: 아무것도 쓰지 않았고 아무것도 보관하지 않는다.
- 미리 확인 실패: 저장하지 않는다.
- 3단계 복사가 실패(미리 확인 뒤 디스크가 찼을 때 등): 저장은 이미 끝났다. 편집기에 **"저장됨, 이전 판은 보관하지 못함"** 경고를 띄우고 로그에 남긴다. 드문 경우이고, 저장을 되돌리면 그것이 또 하나의 경합이 된다.
- 새 파일(§7.7의 `create`): 옛 내용이 없으니 보관하지 않는다.

삭제도 같다:
- runner `delete`에 `expected`를 받는다. 웹은 확인 창을 띄울 때 `stat`으로 그 identity를 받아 둔다.
- 지울 파일을 먼저 열어 identity를 확인한 뒤 unlink한다.
- 그 디스크립터를 돌려줘 판으로 남긴다.

편집기의 "이전 판" 목록에서 보고, diff를 보고, 되돌린다. 되돌리기도 저장이라 그 직전 판이 다시 남는다.

### 7.5 그 밖의 파일 작업 (Q5)

- 권고 범위(3단계)
  - 새 파일: runner `write`의 `create` 모드(§7.7)로 빈 파일을 만들고 연다. 같은 이름이 있으면 `EXISTS`다.
  - 새 폴더(검수 N1): **runner에 `mkdir`을 더한다.**
    - 한 단계만 만든다. 부모는 있어야 한다.
    - 이미 있으면 `EXISTS`다.
    - 부모는 쓰기 연산과 같은 검사를 받는다: 실제 경로, 숨김 아님, 디스크 파일시스템, `writable_under` 안.
    - 권한은 `0755`다.
    - `write`의 `create_parents`는 쓰지 않는다. 빈 폴더를 정확히 하나 만드는 계약이 아니라서다.
  - 파일 삭제: 확인 창을 띄운 뒤 runner `delete`(파일만, `expected` 필수)를 한다. 지운 내용은 §7.4에 보관한다.
- 뒤로 미루는 것: 이름 바꾸기·이동, 폴더 삭제, 여러 파일 한꺼번에. runner 연산과 검사(링크·숨김·하위 전체)가 새로 필요하다.

### 7.6 편집기 (Q6)

- 권고: **CodeMirror 6**.
  - 가볍다. 모바일·iPad 입력이 좋다. 언어 강조와 검색, diff(merge 확장)가 있다.
  - 빌드한 번들을 KaTeX처럼 `static/codemirror/`에 넣는다(`LICENSE`, `SOURCE`에 판과 빌드 방법). 페이지 CSP를 넓히지 않는다(`eval` 불필요).
- 대안: Monaco. VS Code와 같은 경험이지만 수 MB이고 worker가 필요하다. 모바일이 약하다.
- 저장: `Ctrl/Cmd+S`와 저장 버튼, 저장 안 된 표시. 자동 저장은 기본으로 끈다. 탭은 두지 않는다(§3.3). 편집기 색은 기존 토큰으로 만든 테마다(§3.1).

### 7.7 저장 API와 한도

- `PUT /api/machine/file` `{path, content, expected}` → `{path, identity, previous_kept}`: 있는 파일 바꾸기
- `POST /api/machine/file` `{path, content}` → `{path, identity}`: 새 파일

runner `write`에 **`mode`를 명시한다**(검수 B1). 지금의 동작(`expected`가 없으면 확인 없이 만들거나 바꿈)은 에이전트 Tool이 쓰는 그대로 두고, 웹은 아래 두 모드만 쓴다.
- `mode: "replace"`: `expected`가 반드시 있다. §7.4의 프로토콜이다. 파일이 없으면 `CHANGED`다.
- `mode: "create"`: **배타적 생성**이다.
  - 임시 파일에 쓰고 fsync한 뒤 `renameat2(RENAME_NOREPLACE)`로 이름을 붙인다. 이름이 이미 있으면 `EXISTS`이고, 아무것도 바뀌지 않는다.
  - 이 플래그를 지원하지 않는 파일시스템(일부 FUSE, 예: rclone)에서는 `O_CREAT|O_EXCL`로 이름을 먼저 잡고 내용을 쓴다. 이름 선점은 원자적이다. 쓰는 동안 잠깐 내용이 덜 찬 새 파일이 보일 수 있고, 쓰기에 실패하면 그 파일을 지운다.
- `expected: null`을 "새 파일"로 읽지 않는다. 기존 계약과 섞이지 않게 모드로만 구분한다.

본문 한도: 이 두 경로만 1 MiB + 여유다(지금 전역 256 KiB). runner로는 디스크립터로 넘긴다. JSON 안 `content`는 runner에서 256 KiB까지라서다.

## 8. 보안

### 8.1 무엇이 넓어지나

- 지금도 모델은 숨김 목록 밖을 읽을 수 있다. 이번에는 **웹 세션이 숨김 목록 밖을 직접 읽고 쓴다.** 웹 세션을 빼앗기면 `coder`의 숨김 아닌 파일이 드러나고 바뀔 수 있다.
- 막는 것
  - 숨김 목록: 인증 정보, 셸 설정, HIMARI 데이터는 웹으로도 안 된다.
  - 소유자 principal만 쓴다.
  - 기존 세션 장치: `SameSite=Strict` 쿠키, Origin 검사, CSP.
  - 직전 판 보관(§7.4)으로 되돌릴 수 있다.
- 남는 것: 세션을 빼앗기면 숨김 아닌 파일의 내용이 새어 나갈 수 있다. 쓰기는 되돌릴 수 있지만 읽기는 되돌릴 수 없다.

### 8.2 내용이 실행되지 않게

- 파일 내용은 화면에서 실행되지 않는다.
  - 텍스트는 편집기의 글자로만 들어간다.
  - 이미지는 HIMARI가 다시 만든 것만 보인다.
  - 나머지는 다운로드(`attachment` + `sandbox` CSP + `nosniff`)로만 받는다.
- 경로·파일 이름은 DOM에 글자로만 넣는다(`textContent`).

### 8.3 실수 막기

- 삭제·덮어쓰기는 확인을 거치고, 직전 판이 남는다.
- 대화 폴더를 지우는 것은 지금처럼 대화 삭제(V3-P65)로만 한다.

## 9. 단계와 검증

1. **탐색기(읽기)**: runner `list` 정렬·페이지, `stat`; 웹 API `list`·`file`·다운로드; 폴더 목록·파일 보기 부품, 오른쪽 파일 패널과 사이드바 Files(§3.2~§3.4), 파일은 읽기 보기.
2. **폴더에서 대화 열기**: Data `list_conversations_working_in`, 웹 API, 메뉴(최근 대화·목록·새 대화·이 대화에 붙이기).
3. **웹 편집기**: CodeMirror 6, 저장·충돌·직전 판·새 파일·삭제, 바뀜 표시, 에이전트 작업 중 표시.

검증:
- **runner**
  - 목록: 큰 폴더(열거 순서와 이름 순서가 다른 수만 개)에서 이름순 앞 항목이 첫 쪽에 나옴. 쪽 사이에 항목을 더하고 지워도 중복 없음. 100,000개 넘으면 오류. 숨김 항목 없음. 링크.
  - `write` `create`: 이미 있는 이름이면 `EXISTS`이고 내용이 그대로임. `RENAME_NOREPLACE`가 없는 파일시스템의 대체 경로.
  - `write` `replace`: `expected` 없으면 거부. 돌려받은 디스크립터가 교체 전 내용임. 검사와 rename 사이에 바뀌면 `CHANGED`.
  - `delete`도 같은 확인을 함.
  - `mkdir`: 있으면 `EXISTS`, 부모 없음, 숨김, `writable_under` 밖.
  - 기존 에이전트 Tool의 `write`(모드 없음) 동작은 그대로임.
- **웹 API**
  - 소유자가 아닌 principal은 `404`.
  - 숨김 경로는 읽기·쓰기 모두 `404`(있는지 말하지 않음).
  - `writable_under` 밖은 쓰기 거부.
  - 1 MiB 넘는 저장은 거부.
  - `CHANGED`면 아무것도 쓰지 않고 아무것도 보관하지 않음.
  - 보관소에 쓸 수 없으면 저장하지 않음. 저장 뒤 복사가 실패하면 경고.
  - 사용자 폴더의 이미지 미리보기는 다시 만든 JPEG/PNG만 나감.
  - 새 파일이 이미 있으면 거부.
  - 다운로드 헤더.
- **대화 열기**
  - 작업 위치로 쓰는 대화만, 최근 순, 휴지통 제외.
  - 다른 경로로 등록된 같은 폴더.
  - 대화 자신의 폴더.
  - 실패하면 만든 대화를 지움.
  - 두 Data 백엔드에서 같은 결과.
- **편집기(브라우저 스모크)**
  - 열기 → 고치기 → 저장.
  - 바깥에서 바꾼 뒤 저장하면 충돌 창.
  - 직전 판 되돌리기.
  - 휴대폰 너비에서 파일 화면과 대화 오가기.
  - light·warm·dark 테마에서 파일 화면과 편집기의 색이 기존 토큰을 따름.
- **호스트**: 실제 runner로 숨김 파일(`~/.ssh`, `/etc/himari-runner`)을 웹 API로 읽기·쓰기 시도해 거부되는지.

## 10. 다음 단계 (방향만)

### 10.1 편집 중 에이전트 부르기 (4단계)

- 편집기에서 선택 영역이나 파일을 **참조**로 대화 메시지에 붙인다.
  - 참조 = 경로 + 줄 범위 + 내용 해시.
  - 모델에게는 참조와 선택한 내용이 같이 간다. 해시가 다르면 "그 사이 바뀜"을 알린다.
- 버튼 위치: 선택 영역 위 작은 메뉴("에이전트에게 묻기"), 단축키.
- 에이전트가 고친 결과
  - 에이전트가 이 대화에서 고친 파일 목록과 diff를 편집기에 보여 준다.
  - 수정은 이미 디스크에 쓰여 있다. 그러니 "받아들이기"는 표시만 지우고, "되돌리기"는 직전 판(§7.4와 같은 저장소)을 쓴다.
  - 파일 Tool의 쓰기마다 직전 판을 남기는 일이 필요하다.

### 10.2 PDF 필기 (5단계)

- 보기: pdf.js로 페이지를 그린다(번들을 `static/`에 넣는다).
- 필기: 페이지 위에 필기 층을 둔다.
  - iPad Safari의 Pointer Events가 펜 필압·기울기를 준다. 펜 입력만 받아서 손바닥 닿음을 무시한다.
  - 도구: 펜·형광펜·지우개·되돌리기.
- 저장
  - 필기를 PDF 표준 ink 주석으로 써 넣는다(pdf-lib). 다른 앱·Drive에서도 보인다.
  - 원본은 직전 판(§7.4)에 남는다. 크기 한도는 편집기와 따로 정한다(PDF는 1 MiB를 넘기 쉽다).
- 에이전트에게 넘기기
  - 필기가 들어간 페이지(또는 고른 영역)를 이미지로 만들어 메시지에 붙인다(V3-P67 이미지 첨부).
  - 그림을 읽는 모델이면 손글씨를 읽는다.
  - "PDF 페이지 → 이미지"는 Sandbox 안에서 만든다. 문서 도구(V3-P70)에 렌더러가 있는지 구현 때 확인한다.
