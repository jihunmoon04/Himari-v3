# Web에서 hub 프로젝트와 기기 폴더 다루기 (V3-P103 설계 초안 v0.1)

> 2026-11-18 · rev. 9(Codex 설계 검수 8차 NOT_READY 반영, §12) · **설계 초안** · 대상: v3 `cb56a53`(V3-P102 작업 콘솔 운영 중), hub `f1f5119`(프로젝트 요청 구현, 운영 배포 전)
> 앞 문서: [작업 콘솔](web-console-v0.1.md)(V3-P102), hub [프로젝트 요청 설계](https://github.com/jihunmoon04/himari-hub/blob/main/docs/projects-v0.1.md), hub [user 경로 계약 v1](https://github.com/jihunmoon04/himari-hub/blob/main/docs/user-api-v1.md) §4.6·§5.2

## 1. 목표와 범위

- **Web에서 hub 프로젝트를 만들고, 기기 폴더를 더하고 빼고, 프로젝트 설정을 바꾼다.** hub는 이 일을 user 경로의 op로 이미 받는다(hub #39). v3는 그 op를 중계하고 화면을 붙인다.
- **HIMARI(모델)가 요청한 것은 사용자가 Web에서 허가한다.** 모델의 `hub_project_request`는 hub에서 `waiting_user`로 멈추고, 허가는 user 경로로만 된다. v3는 그 요청을 받은 승인 화면과 대화 안의 카드로 보인다.
- **범위 밖:** HIMARI 자체 프로젝트(대화를 프로젝트에 묶기, 작업 단위), 기기 앱(→ [V3-P104](workbench-v0.1.md)), hub의 허가 방식 바꾸기(그 기기에서만 함).

## 2. hub가 주는 것 (요약)

자세한 것은 hub 계약 §4.6·§5.2.

- **허가 방식(기기마다, 그 기기에서만 정함):** `off`(원격 등록을 받지 않음, 빼기는 받음), `local`(그 기기 화면의 확인 창에서 사용자가 폴더를 고름, 짝 코드), `user`(user 경로의 요청·허가가 곧 허가, roots 아래만).
- **요청 상태:** `waiting_user`(모델의 요청) → `waiting_device`(5분) → `applying` → `done`, 또는 `refused`·`expired`·`failed`·`cancelled`, 그리고 `lost`(claim 뒤 결과를 모름: 사용자가 정리). 종류는 `create`·`add_folder`·`remove_folder`.
- **op:** `project_request`, `project_requests`, `project_request_answer`, `project_request_cancel`, `project_request_resolve`(펜스, 기기를 잃었을 때만 `force`), `project_folder_remove`(즉시 빼지 않고 `remove_folder` 요청을 만듦), `project_set`, `project_adopt`, `runner_dirs`. `projects`의 `runners[]`에 `approve`·`folders`.
- **목록 스트림:** `project_request`(바뀐 요청 하나, `rev`)와 `projects`(본문 없음, 다시 읽으라는 신호). 처음은 늘 `sessions`, 둘 다 SSE `id` 없음.
- 끝난 요청은 hub에 30일 남는다(`lost`는 정리될 때까지).

계약 v1에 더하기다(H11은 고침).

| id | 무엇 | 왜 |
| --- | --- | --- |

| H12 | user `project_requests`에 `ids`(최대 50, 그 이상은 v3가 나눠 보냄): 답은 `{"requests": [...], "missing": [id…]}`. `requests`는 상태와 상관없이, `missing`은 hub에 그 id가 없음(30일이 지나 지워짐)을 확인한 것 | 응답을 받지 못한 동작과 끊긴 동안 끝난 요청의 결과를 확인(§5) |
| H13 | `project_request`·`project_folder_remove`에 `client_key`(1~64자). hub는 키를 요청 행의 칸(유일 색인)으로 둔다. **같은 키의 호출은 한 줄로 선다:** hub(상주 서버 프로세스 하나)는 키마다 프로세스 안의 잠금을 두고, 찾기·검사·만들기를 그 잠금 안에서 한다. 그래서 같은 키의 두 번째 호출은 첫 호출이 만들거나 실패할 때까지 기다렸다가 아래를 처음부터 한다. **키를 먼저 찾는다:** 받은 입력(`key_time` 포함)을 정규화해 키로 찾고, 있으면 같은 op·같은 정규화한 입력일 때 그 요청을 그대로 돌려준다(끝났어도, 기기가 지금 끊겼거나 폴더가 이미 빠졌어도: 기기 상태 검사와 기기로 다시 보내기를 하지 않음). 다르면 400 `client_key_reused`. 없을 때만 지금의 검사를 하고 같은 트랜잭션에서 만든다(유일 색인은 hub가 여러 개 떠도 둘이 생기지 않게 하는 마지막 막이고, 지면 키를 다시 찾아 그 요청을 돌려준다). **키에는 v3 서버가 정한 발급 시각(`key_time`)이 붙는다:** 키가 없을 때 `key_time`이 hub 시계로 24시간보다 오래거나 5분보다 미래면 만들지 않는다(400 `client_key_expired`·`client_key_time`). 저장된 키와 `key_time`이 다르면 다른 입력이므로 `client_key_reused`(`key_time`만 바꿔 다시 보내도 우회되지 않음). 받는 범위(24시간 + 5분)가 키를 남기는 기간(30일)보다 훨씬 짧으므로, v3와 hub의 시계가 5분 넘게 어긋나지 않는 한 지워진 키로 새 요청이 생기지 않는다. v3와 hub는 같은 서버(또는 NTP를 쓰는 서버)에서 돈다. 키는 요청 행과 함께 끝난 뒤 30일에 지워지므로, 지워진 키로 늦게 다시 보내도 새 요청이 생기지 않는다 | `hub_unknown` 뒤 다시 보내도 요청이 둘 생기지 않음 |
| H17 | `project_request_resolve`를 요청 id마다 한 줄로: 정리를 시작할 때 원장의 요청 행에 `resolving = 1`을 조건부 갱신(`WHERE resolving = 0 AND state = 'lost'`)으로 쓰고 `rev`를 올려 `project_request` 이벤트를 낸다. 그동안 온 `resolve`(force 포함)는 409 `resolving`. **끝내는 일은 모두 한 트랜잭션 틀로:** 펜스의 결과와 기기의 늦은 완료 보고(hub `request_done`)는 같은 즉시 트랜잭션(`_immediate()`) 안에서 ① 요청 행을 다시 읽고 ② 아직 `lost`(기기 보고는 `applying`도)일 때만 `_settle`의 모든 부작용(`create`가 적용됐으면 프로젝트 만들기)과 끝 상태, `resolving = 0`, `rev` 올리기를 함께 쓴다. ③ 이미 끝나 있으면 부작용 없이: `resolving = 1`이면 `resolving = 0`과 `rev`만 쓰고, 지금 상태를 돌려준다. 그래서 진 쪽은 프로젝트를 만들지 않고, 요청의 끝 상태와 프로젝트가 어긋나지 않는다. 펜스가 실패·시간 초과로 끝나면 같은 틀에서 `WHERE state = 'lost' AND resolving = 1`로 `resolving = 0`과 `rev`만 쓴다. 이벤트는 트랜잭션이 끝난 뒤 낸다. hub가 다시 켜지면 남은 `resolving = 1`을 모두 0으로 쓰고 `rev`를 올린다(펜스는 프로세스와 함께 끝났으므로). user 뷰의 요청 레코드에 `resolving`을 더한다 | `hub_unknown` 뒤나 다른 탭에서 다시 정리해도 펜스가 겹치지 않음 |

없는 hub에서의 동작: H8 없음 → 보류 채택 화면을 보이지 않음. H12 없음 → 끊긴 동안 끝난 요청은 "결과 확인 불가". H13 없음 → `hub_unknown` 뒤 "다시 보내기"를 막고 목록을 다시 읽게만 함. H17 없음 → `hub_unknown` 뒤 정리 단추를 60초 막음(§4.1). H11은 v3와 상관없이 hub에서 고친다.

## 4. 서버 중계 (`/api/hub/…`)

지금의 중계 원칙(V3-P95, V3-P102 §6)을 그대로 쓴다: 운영자만(새 경로 모두 지금의 운영자 검사 함수를 거침), 종류마다 아는 칸만 크기 한도와 함께 다시 만들어 넘김, hub 400 → 409 `hub_refused`(문구 그대로), 연결 실패 → 503 `hub_unavailable`, 401·403 → 503 `hub_misconfigured`, 보냈지만 답을 못 받음 → 503 `hub_unknown`. 상태를 바꾸는 요청은 지금처럼 `OriginGuardMiddleware`를 거친다(쿠키로 오는 요청은 같은 출처만, 쿠키 없는 bearer는 운영자 CLI).

**프로젝트·기기 이름은 URL 경로에 넣지 않는다.** hub 이름 규칙은 `/`·`?`·`#`도 받으므로, 본문(JSON)이나 쿼리 값으로만 넘긴다. 요청 id(정수)만 경로에 둔다.

| v3 경로 | hub op | 비고 |
| --- | --- | --- |
| `GET /api/hub/project-requests` | `project_requests` | `open`(bool), `limit`, `ids`(쉼표, H12) |
| `POST /api/hub/project-requests` | `project_request` | `kind`, `project`, `runner`, `path`?, `create_dir`?, `agent`?, `client_key`·`key_time`(H13) |
| `POST /api/hub/project-requests/{id}/answer` | `project_request_answer` | `approve` |
| `POST /api/hub/project-requests/{id}/cancel` | `project_request_cancel` | |
| `POST /api/hub/project-requests/{id}/resolve` | `project_request_resolve` | `force`?, `outcome`?. 시간 제한 40초(펜스는 기기 답을 30초 기다림) |
| `POST /api/hub/projects/settings` | `project_set` | `project`, `agent`?, `profile`?, `preset`?(준 것만, null은 지움). 지금의 `PUT …/{project}/preset`은 그대로 둠 |
| `POST /api/hub/projects/remove-folder` | `project_folder_remove` | `project`, `runner`, `client_key`·`key_time`(H13) |
| `POST /api/hub/client-key` | — | v3 서버가 `{client_key(임의 128비트), key_time(서버 시계)}`을 만들어 줌. hub에 가지 않음 |
| `POST /api/hub/projects/adopt` | `project_adopt` | `project`, `runner` |
| `POST /api/hub/runner-dirs` | `runner_dirs` | 본문 `runner`, `path`?(경로가 접근 기록·프록시 기록의 URL에 남지 않게 POST 본문으로). 읽기지만 Origin 검사를 거침. 시간 제한 15초 |

- **요청 레코드(`REQUEST`, REST와 SSE에 같은 것):** `id`, `kind`, `project`, `runner`, `origin`, `path`, `create_dir`, `agent`, `why`(500자), `code`, `mode`, `state`, `rev`, `result_path`, `reason`, `resolving`(H17, 없으면 `false`), `created_at`, `decided_at`, `expires_at`, `claimed_at`, `ended_at`, `same_name_on`.
  - **`same_name_on`은 화면이 쓰지 않는다.** hub가 요청 행이 아니라 지금의 보류 목록에서 계산하는 칸이라, 보류가 바뀌어도 요청의 `rev`가 오르지 않는다. 그래서 v3는 이 칸을 넘기기는 하되 화면은 `rev` 병합에 넣지 않고, 보류된 같은 이름은 늘 `projects`의 `runners[].held`(H8)에서 찾는다(`projects` 신호로 갱신됨). `rev`로 병합하는 것은 요청 행에서 오는 칸뿐이다.
- **`PROJECTS`:** `runners[]`에 `approve`(`mode`, `roots`, `why`), `folders`({이름: 경로}), `held`(H8). 기기 경로와 짝 코드는 운영자 화면에만 간다. v3는 이 칸들을 모델에게 주지 않는다(모델은 hub의 MCP로만 보고, 그것은 H11이 막는다).
- 로그에는 요청 id·상태·종류와 오류 종류(`hub_refused` 등)만 남긴다. 경로·짝 코드·hub 오류 문구(경로가 들어 있을 수 있음)는 남기지 않는다. 경로가 들어가는 값은 모두 본문으로 오가고(URL에 없음), 예외 기록에도 요청 본문을 넣지 않는다.

### 4.1 `hub_unknown` 뒤

| 동작 | 화면이 하는 것 |
| --- | --- |
| 요청 만들기, 폴더 빼기 | 같은 `client_key`·같은 본문으로 다시 보낼 수 있다(H13: 같은 요청이 돌아옴). H13이 없으면 다시 보내기를 막고 열린 요청을 다시 읽어 같은 `kind`·`project`·`runner`의 요청이 있는지 보인다 |
| 허가·거절, 취소 | 그 요청을 `ids`로 다시 읽는다(H12). 아직 그 전 상태면 다시 할 수 있다 |
| 정리(`resolve`) | `ids`로 다시 읽는다. `lost`가 아니면 그 결과를 보인다. `resolving: true`(H17)면 "기기에 묻는 중"으로 두고 다음 이벤트를 기다린다. `lost`이고 `resolving`이 아니면 다시 누를 수 있다. H17이 없는 hub면 첫 요청의 펜스가 아직 돌 수 있으므로 60초(펜스 30초 + 여유) 동안 단추와 `force`를 막는다 |
| 설정 바꾸기, 채택 | `projects`를 다시 읽어 바뀌었는지 보인다 |

**확인되지 않은 만들기·빼기는 새로고침을 넘어 남긴다.** 대화상자를 열 때 `POST /api/hub/client-key`로 v3 서버에서 `{client_key, key_time}`(서버 시계)을 받는다. 요청을 보내기 전에 `{client_key, key_time, 경로, 본문}`을 그 브라우저의 `sessionStorage`에 적고, 답(요청 id)을 받으면 지운다. (답을 받으면 그 id를 따라가는 id 목록(§5)에 먼저 넣은 뒤 지운다.) 화면이 다시 열리면 남은 것을 "확인되지 않은 요청"으로 보이고 같은 키·`key_time`·본문으로 다시 보낼 수 있다. 너무 늦었는지는 브라우저 시계가 아니라 hub가 `key_time`으로 판단한다(H13: 24시간이 지났으면 그 요청이 있었을 때만 돌려주고, 없으면 `client_key_expired`). 그 답이면 다시 보내기를 막고 열린 요청과 프로젝트를 다시 읽어 보인 뒤 버리게만 한다. 저장소를 쓸 수 없으면(사생활 보호 창 등) 이 회복 없이 위 표대로만 한다. 이 값에는 경로가 들어가므로 `localStorage`가 아니라 탭이 닫히면 지워지는 `sessionStorage`를 쓴다.

### 4.2 목록 스트림

v3는 hub 목록 스트림 하나를 브라우저들에 나눠 준다(V3-P102 §6). 거기에 두 이벤트를 더한다.

- **`project_request`·`projects`:** 받은 그대로(요청은 레코드를 다시 만들어) 모든 브라우저에 보낸다. v3는 들고 있지 않는다.
- **upstream이 다시 붙을 때와 폴링으로 내려갈 때:** 그 사이의 이벤트는 잃었을 수 있다. v3는 새 `sessions`를 보낼 때 `projects`를 한 번 보낸다.
- **폴링 동안:** v3는 30초마다 `projects`를 보낸다(그동안 프로젝트·기기·요청의 변화는 이것으로만 알림). 화면은 이것을 받을 때마다 §5의 다시 읽기를 한다.
- 브라우저 스트림의 인증 수명(연결마다 15초 다시 확인, 로그아웃이면 닫힘)은 지금 그대로 이 이벤트에도 적용된다.
- `sessions`·`changed`의 뜻과 순서는 바꾸지 않는다. 새 이벤트에는 `id`가 없다.

## 5. 화면 상태

- **`useHubRequests`:** id별 레코드 저장소 하나와, 화면이 따라가는 id들(카드가 보이는 것)을 들고 있는다. 열린 요청 목록은 저장소에서 상태가 열린 것을 고른 것이다(따로 들지 않음).
  - **병합 규칙 하나:** 스트림 이벤트든 REST 읽기 결과든 레코드가 오면, 저장소의 같은 id보다 `rev`가 클 때만 바꾼다(`same_name_on`은 저장하지 않음, §4). 그래서 늦게 도착한 오래된 읽기는 새 상태를 덮지 못하고, 읽는 동안 온 이벤트를 따로 모아 둘 필요도 없다(어느 순서로 와도 결과가 같음).
  - **목록에 없다는 것으로 지우지 않는다.** 열린 목록 읽기에 없던 열린 레코드는 그대로 두고 그 id들을 `ids`(H12)로 읽어 끝난 레코드를 받는다(위 규칙으로 병합). `missing`으로 온 id만 "결과를 확인할 수 없습니다"로 바꾼다. 읽기가 실패하면 그 레코드는 그대로 두고 다음 다시 읽기에서 또 묻는다.
  - **언제 읽는가:** 스트림을 열 때와 다시 연결할 때, `projects` 신호를 받을 때, 브라우저의 폴링 대체(아래) 주기마다 열린 목록과 따라가는 id 중 열린 것을 읽는다. 따라가는 id를 **새로 등록할 때**(대화 카드가 늦게 나타남 등) 저장소에 없거나 열린 상태면 그 자리에서 `ids`로 한 번 읽는다.
  - 저장소는 열린 레코드, 따라가는 id의 레코드, 끝난 지 10분 안의 레코드만 남기고 나머지는 버린다.
  - **따라가는 id는 새로고침을 넘어 남긴다:** 그 탭의 `sessionStorage`에 id 목록만(경로·코드 없이, 최대 50개, 오래된 것부터 버림) 적는다. 만들기·빼기의 답으로 id를 받으면 **먼저 이 목록에 넣고 나서** 확인되지 않은 요청(§4.1)을 지운다. 화면이 다시 열리면 이 목록을 읽어 위의 "새로 등록할 때"처럼 `ids`로 읽는다. 카드를 닫으면 목록에서 뺀다.
- **`projects` 신호:** `useHubProjects`를 다시 읽는다(읽는 중에 또 오면 끝난 뒤 한 번 더).
- **브라우저의 폴링 대체:** 지금 화면은 SSE가 거절되거나 끊기면 목록을 10초마다 직접 읽는다(V3-P102). 그동안에는 `projects`와 위의 요청 읽기도 같은 타이머로 한다. SSE가 다시 붙으면 그 타이머를 멈추고(둘이 돌지 않게) 위의 "다시 연결할 때" 읽기를 한 번 한다.

## 6. 화면

### 6.1 새 프로젝트

사이드바 Projects 머리에 **+** 단추 → 대화상자.

1. **이름:** hub 규칙(80자, 앞뒤 공백 없음, 인쇄 가능한 글자). 이미 있는 이름이면 그 자리에서 알린다.
2. **기기:** 연결된 기기 목록. 기기마다 방식(`local` "그 기기 화면에서 고름", `user` "여기서 고름(roots 아래)")을 보인다. `off`나 끊긴 기기, 요청을 받지 않는 기기(공유 토큰·옛 실행기: `approve.mode`가 `off`)는 흐리게 하고 이유(`why`)와 "그 기기에서 `himari-hub runner approve`"를 보인다.
3. **폴더:**
   - `local`: "폴더는 그 기기 화면에서 고릅니다." 선택으로 "새 폴더 만들기"와 "시작 위치"(제안).
   - `user`: 폴더 고르기(§6.5)와 "새 폴더 만들기"(고른 폴더 아래 이름 하나: 구분자·`.`·`..` 없음). 경로는 고른 결과로만 채운다.
4. **기본 에이전트**(선택).
5. **요청**(대화상자를 열 때 만든 `client_key`와 함께) → 요청 카드(§6.3). `done`이면 그 프로젝트 화면으로 옮긴다.

### 6.2 프로젝트 화면 `/project?name=<이름>`

이름은 쿼리 값으로(URL 인코딩). 사이드바 프로젝트 이름 옆 정보 단추로 연다.

- **설정:** 기본 에이전트, 프로필, 권한 묶음. 권한 묶음은 바꾸기 전에 확인을 받는다.
- **기기별 폴더:** 이 프로젝트를 가진 기기: 이름, 연결, 폴더(`folders`), **빼기**. 빼기는 `remove_folder` 요청을 만들고 그 카드(§6.3)를 보인다(그 기기가 `runner.json`에서 뺄 때 끝남). 확인 대화상자: "그 기기의 `runner.json`에서만 빠지고, 폴더와 작업 기록은 그대로입니다." `off` 기기에도 된다.
- **기기에 폴더 더하기:** §6.1의 2~3단계와 같은 대화상자(`kind: add_folder`).
- **보류된 폴더(H8):** 이 이름을 보류 중인 기기 + **채택**.
- **이 프로젝트의 열린 요청 카드.**

**사이드바의 보류 목록:** 프로젝트가 아직 없는 이름이 어떤 기기에서 보류 중이면(H8: 그 이름의 프로젝트가 `projects`에 없음) Projects 아래 "보류된 폴더"에 그 이름과 기기를 보이고 **채택**(그 이름의 프로젝트를 만들고 붙임)을 둔다. 채택은 그 기기가 연결돼 있고 지금도 그 이름을 알릴 때만 된다(아니면 hub 문구).

### 6.3 요청 카드

새 프로젝트 대화상자, 프로젝트 화면, 받은 승인 화면, 대화 안(§6.6)에서 같은 컴포넌트를 쓴다. 문구는 종류(`kind`)마다 다르다.

| 상태 | 보이는 것 | 할 수 있는 것 |
| --- | --- | --- |
| `waiting_user` | "HIMARI가 요청함", 이유(`why`), 기기, 종류, 경로 | 허가 / 거절 |
| `waiting_device`(local, 더하기) | "**{기기} 화면에서 폴더를 고르세요**", 짝 코드(크게), 남은 시간 | 취소 |
| `waiting_device`(user, 또는 빼기) | "기기가 확인하는 중" | 취소 |
| `applying` | 더하기 "기기가 등록하는 중" / 빼기 "기기가 빼는 중" | — |
| `lost` | 더하기 "기기에 등록됐는지 모릅니다" / 빼기 "기기에서 빠졌는지 모릅니다" | **정리**(§6.4) |
| `done` | 더하기: 결과 경로, 프로젝트로 가기 / 빼기: "빠졌습니다" | — |
| `refused`·`expired`·`failed`·`cancelled` | 이유(`reason`을 사람 말로, 모르는 값은 그대로) | 다시 요청(아래) |
| 확인 불가 | "결과를 확인할 수 없습니다(기록이 지워짐)" | 프로젝트 다시 읽기 |
| `lost`이고 `resolving`(H17) | "기기에 묻는 중" | — |

**다시 요청**은 종류마다 다른 길로, 늘 새 `client_key`로 한다. 보내기 전에 `projects`를 다시 읽어 지금 상태로 다시 확인한다.

- 만들기·더하기(`local`): 같은 기기·프로젝트·선택(새 폴더, 시작 위치)으로 대화상자를 연다. 폴더는 그 기기 화면에서 다시 고른다.
- 만들기·더하기(`user`): 같은 기기·경로로 대화상자를 열되, 경로는 폴더 고르기(§6.5)로 다시 확인한 뒤에만 보낼 수 있다(그 사이 지워졌거나 roots가 바뀌었을 수 있음).
- 빼기: 그 기기가 아직 이 프로젝트의 폴더를 알리고 있을 때만 `remove-folder`로 다시 보낸다. 이미 없으면 "이미 빠져 있습니다"를 보이고 보내지 않는다.
- 기기가 끊겼거나 방식이 `off`로 바뀌었으면(빼기는 `off`여도 됨) 대화상자에서 그 이유를 보이고 막는다.

### 6.4 `lost` 정리

1. **정리** → `resolve`(force 없이). 기기가 연결돼 있으면 기기가 lock 안에서 답하고 요청이 끝난다(최대 30초, 단추는 그동안 "기기에 묻는 중").
2. 기기가 연결돼 있지 않거나 답이 없으면(409) 문구를 보이고 단추를 그대로 둔다. 그 아래에 접힌 **"기기를 잃었을 때"**: 사용자가 고르고, 결과를 함께 적는다.
   - 더하기·만들기 — 적용 안 됨: "그 기기가 다시 켜져 실제로 등록돼 있었다면, 그 기기의 폴더는 기본 에이전트 없이 프로젝트가 됩니다(만들기일 때)." 적용됨: "기기에 없다면 폴더 없는 프로젝트가 남습니다(만들기일 때)."
   - 빼기 — 빠짐(`applied`): "기기에 남아 있다면 그 폴더는 다음 연결 때 다시 이 프로젝트의 폴더로 알려집니다." 안 빠짐(`not_applied`): "기기에서 빠져 있다면 다음 연결 때 목록에서 사라집니다." 빼기는 어느 쪽이든 원장에서 바뀌는 것이 없다(기기의 실제 상태가 다음 보고로 보임).
3. 모델은 정리하지 못한다(이 단추는 운영자 화면에만).

### 6.5 폴더 고르기 (`user` 방식)

`runner-dirs`로 루트 목록 → 한 단계씩 들어감(이름만, 숨김·링크는 기기가 뺌). 고른 경로를 그대로 `path`로 보낸다(서버는 해석하지 않고 기기가 검사). 시간 제한·오류는 문구로.

### 6.6 대화 안의 카드

HIMARI의 `<hub source>/hub_project_request` Tool 호출을 맡긴 작업 카드(V3-P102 §5.1)처럼 카드로 그린다. 결과의 요청 id를 따라가는 id로 등록한다(§5). 카드는 운영자 화면이므로 user 경로의 레코드(경로·코드 포함)를 보인다. `hub_project_requests` 호출은 지금처럼 Tool 블록이다.

### 6.7 받은 승인

지금의 목록 위에 **"프로젝트 요청"** 묶음: `waiting_user`(허가/거절)와 `lost`(정리). 탭 제목 대기 수에 `waiting_user` 수를 더한다.

## 7. 바꾸지 않는 것

- 운영자 로그인, CSP, 토큰을 브라우저·모델·Tool에 주지 않는 원칙(V3-P95). user 토큰은 서버만 든다.
- 모델이 허가·정리·설정·빼기를 하지 못하는 원칙(hub가 user 경로로만 받음).
- 기존 `PUT /api/hub/projects/{project}/preset`(이름이 경로에 들어가는 문제는 그대로 남음: 권한 묶음은 새 `settings`로도 바꿀 수 있음).

## 12. 설계 검수 (Codex)

### 1차 (rev. 1 → rev. 2): NOT_READY, P1 다섯, P2 셋

- P1 모델에 경로가 나감(hub의 MCP 응답이 user 뷰를 그대로 줌) → hub 버그로 H11(§3), v3는 운영자 화면에만(§4).
- P1 `hub_unknown` 뒤 다시 하기가 안전하지 않음 → H12(id로 읽기)·H13(`client_key`), 동작별 처리 표, 정리 중복 막기(§3, §4.1).
- P1 끊긴 동안 끝난 요청을 잃음 → 따라가는 id를 `ids`로 다시 읽기, 못 찾으면 확인 불가(§5, §6.3).
- P1 빼기의 상태와 `force`의 뜻이 빠짐 → 빼기도 요청 카드로 따라가고, 종류별 문구와 `force` 결과(§6.2, §6.3, §6.4).
- P1 이름과 URL 경로가 충돌 → 이름은 본문·쿼리로만, 화면 경로 `/project?name=`, 특수 문자 시험(§4, §6.2, §8).
- P2 폴링 동안 프로젝트 갱신 → 30초마다 `projects`(§4.2).
- P2 프로젝트 없는 보류 이름의 채택 → 사이드바 보류 목록(§6.2).
- P2 보안 검사 → 새 REST·SSE 모두 운영자만, Origin, 로그아웃 뒤 닫힘, 토큰·경로가 로그에 없음(§4, §8).

### 2차 (rev. 2 → rev. 3): NOT_READY, P1 다섯, P2 넷

- P1 H11이 요청만 다룸(`hub_projects`의 `approve.roots`, 자유 문구의 `reason`·`why`) → MCP 뷰를 따로: roots 빼고, 이유는 알려진 코드만, 오류 문구에도 경로 없음(§3 H11).
- P1 `client_key` 계약이 모자람(동시 요청, 다른 본문, 보존, 새로고침) → 요청 행의 유일 색인으로 원자적, 다른 본문 거절, 요청 행과 함께 지워짐, 확인되지 않은 요청을 `sessionStorage`에 남김(§3 H13, §4.1).
- P1 `hub_unknown` 뒤 다시 정리하면 펜스가 겹칠 수 있음 → hub가 요청마다 정리를 한 줄로(`resolving`, H17), 없는 hub에서는 60초 막음(§3, §4.1, §6.3).
- P1 늦게 등록한 따라가는 id를 바로 읽지 않음 → 등록할 때 `ids`로 바로 읽기, 50개씩 나눔(§5).
- P1 다시 읽기와 이벤트의 경합 → id별 저장소 하나와 `rev` 병합 규칙 하나, 목록에 없다는 것으로 지우지 않음(§5).
- P2 "id 없음"을 곧바로 지워짐으로 봄 → H12가 `missing`을 따로 돌려주고 그것만 확인 불가, 읽기 실패는 그대로(§3, §5).
- P2 브라우저의 폴링 대체에서 프로젝트·요청 갱신이 빠짐 → 같은 10초 타이머로 읽고 SSE가 돌아오면 멈춤(§5).
- P2 경로가 접근 기록에 남음 → `runner-dirs`를 POST 본문으로, hub 오류 문구와 요청 본문을 로그에 넣지 않음(§4, §8).
- P2 다시 요청의 입력이 종류마다 다름 → 종류별 길과 보내기 전 다시 확인(§6.3).

### 3차 (rev. 3 → rev. 4): NOT_READY, P1 셋

- P1 `resolving`이 중계 레코드에 없고 `rev`가 오르지 않아 병합에서 버려짐 → `REQUEST`에 `resolving`, 시작·끝 모두 원장에 조건부로 쓰고 `rev`와 이벤트, hub 재시작 때 풂(§3 H17, §4).
- P1 hub는 저장 전에 기기를 검사하므로 원 요청 뒤 기기가 끊기면 같은 키가 그 요청을 돌려주지 못함 → 키를 먼저 찾고, 있으면 기기 검사 없이 그대로 돌려줌(§3 H13).
- P1 `sessionStorage`의 키가 hub의 키보다 오래 살 수 있음 → hub는 키를 적어도 30일 남기고, 화면은 24시간 안에서만 다시 보냄(§3 H13, §4.1).

### 4차 (rev. 4 → rev. 5): NOT_READY, P1 셋, P2 하나

- P1 MCP `hub_projects`가 `projects[].path`도 줌 → H11에 더함(§3).
- P1 정리 중 기기의 늦은 완료와 펜스가 겹침 → 끝내는 쓰기는 모두 `WHERE state = 'lost'` 조건부로 `resolving`을 함께 풀고, 늦은 쪽은 실제 상태를 돌려줌(§3 H17).
- P1 브라우저 시계로 24시간을 재면 지워진 키로 새 요청이 생길 수 있음 → v3 서버가 `key_time`을 주고 hub가 자기 시계로 판단(§3 H13, §4, §4.1).
- P2 동시 재시도에서 검사 실패가 먼저 돌아갈 수 있음 → 검사 실패·색인 충돌 뒤 키를 다시 찾음(§3 H13).

### 5차 (rev. 5 → rev. 6): NOT_READY, P1 둘

- P1 v3 시계가 크게 앞서면 미래의 `key_time`으로 지워진 키가 다시 받아짐, `key_time`만 바꿔 우회 → 5분보다 미래면 거절, `key_time`도 키와 묶어 비교, 시계 오차의 전제를 적음(§3 H13).
- P1 검사 실패 뒤 다시 찾기만으로는 아직 저장 전인 첫 호출을 못 봄 → 같은 키의 찾기·검사·만들기를 hub 안의 키별 잠금으로 한 줄로(§3 H13).

### 6차 (rev. 6 → rev. 7): NOT_READY, P2 하나

- P2 id를 받은 직후 새로고침하면 따라가는 id를 잃음 → 따라가는 id 목록을 `sessionStorage`에 남기고, 확인되지 않은 요청을 지우기 전에 먼저 넣음(§4.1, §5).

### 7차 (rev. 7 → rev. 8): NOT_READY, P1 하나

- P1 조건부 갱신만으로는 `_settle`의 부작용(`create`의 프로젝트 만들기)이 진 쪽에서도 돌 수 있음 → 다시 읽기·판정·부작용·`resolving` 풀기·`rev`를 한 즉시 트랜잭션으로, 진 쪽은 부작용 없이 지금 상태만(§3 H17).

### 8차 (rev. 8 → rev. 9): NOT_READY, P2 하나

- P2 `same_name_on`은 보류 목록에서 계산돼 `rev` 없이 바뀜 → 화면은 이 칸을 병합하지 않고 `projects.held`(H8)에서 찾음(§4, §5).
